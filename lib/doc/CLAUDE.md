# lib/doc — Builder document store

The normalized, undoable source of truth for the blueprint domain. Every module, form, and field the builder edits lives here, keyed by UUID.

## Boundary rule

The store is private. Consumers must go through the named domain hooks in `hooks/` — never import the store file directly from outside this package.

Consumers get narrow, memoized hooks with predictable selector shapes; no component passes a raw selector function to a Zustand hook for this store. This boundary keeps undo/redo semantics sane and lets the internal store shape evolve without touching call sites.

## The write surface

`applyMany(mutations: Mutation[]): MutationResult[]` is the mutation-applying write action on the store. Every result entry is `undefined`; reducers expose no side-channel metadata. There is no `apply` / `applyWithResult` — single-mutation dispatches wrap as `applyMany([m])`. A field ID has exactly one mutation representation: `updateField { uuid, targetKind, patch: { id } }`. The builder hook may expose a user-gesture method named `renameField`, but it only runs the shared form-local sibling verdict and dispatches that canonical update command. Moving a field preserves its id; destination sibling collisions reject before reduction instead of auto-renaming.

`commitDoc(next, commands)` is its gated-dispatch twin: `useBlueprintMutations`' gate runs the batch through `prepareMutationCandidate` once, then `evaluatePreparedMutationCandidate` validates without receiving or re-running the mutations; on a pass it publishes that exact frozen candidate directly rather than proxying and finalizing the app through a second Immer transaction. One reducer run per UI dispatch and authoritative transaction attempt, and the committed doc is exactly the doc the gate validated. Builder validity is preserved by induction from its valid store snapshot: `incrementalValidationScope` classifies only mutation families whose complete dependency footprint is known, the validator runs every app-wide + lookup rule and every touched form/module rule, and any unknown/structural/cross-scope batch falls back to the absolute whole-document gate. A control that has already run that candidate gate off-thread may register an exact `(doc snapshot, lookup snapshot, mutation batch)` prevalidation certificate; the Builder reuses only that identical candidate, while admission still runs and every stale or different batch falls back to validation. One publication either way, so the batch is one undo step. Every other writer (agent stream, replay, compound session actions) stays on `applyMany`.

**Every reducer is deterministic.** A mutation carries the identities it installs rather than minting them on the way past, so applying a batch twice reaches the same document. That is what lets a batch be persisted, replayed, and folded onto a peer's state; a kind that minted identity inside the reducer could never be any of those, which is why `duplicateField` is gone — `duplicateFieldMutations` plans the clone's uuids at the gesture and the batch is ordinary `addField`s.

**The store QUEUES the exact admitted batches it commits.** `applyMany` / `commitDoc` record every write except one arriving inside a REPLAY bracket (`beginRemoteApply` — an inbound remote frame, a reload reseed, an SA stream frame), so an edit the author makes WHILE a run streams still queues. Recording happens BEFORE the `set()`, because `set()` notifies `useAutoSave` synchronously and a queue filled afterwards leaves every save one edit behind. `takeCommandBatches` hands the ordered original segments to the reconciler at PUT time; `peekCommandBatches` answers "is there anything unsaved". The batches are never flattened: a batch-exclusive semantic command, its predecessors, and its successors retain separate admission, batch ids, retry, acknowledgement, and conflict fate. `commandQueueRevision` is the non-persisted monotonic notification that also catches rename followed by inverse before autosave: the aggregate optimistic Blueprint returns to its exact starting bytes while both semantic row-moving commands still owe ordered persistence. Equality can never elide either command. Persistence replays exactly what the author dispatched instead of re-deriving it by diffing two documents.

Catalog member order is exact state. `addCaseProperty.after` names `null` for first or an existing same-type predecessor; omission alone means append. Admission rejects a missing, removed, wrong-type, or self anchor. This is what lets a granular remove/add inverse restore the exact original property bytes at the beginning, middle, or end without a whole-catalog replacement. Ordinary undo derives an inverse only after replaying the exact recorded non-rename forward command proves the endpoint; rename undo carries the explicit inverse relation directly. Generic endpoint diff never guesses rename intent.

Module placement is the one tier-aware sequence. `addModule.module.parentModuleUuid`
is absent for a root or names a root parent, and its `after` anchor belongs to
that destination's sibling group. `moveModule.parentModuleUuid` has three
deliberately different wire states: omitted preserves the module's current
sibling group (including historical rows and stale narrow reorders), `null`
explicitly promotes it to the root, and a UUID explicitly reparents it under
that root. `after` is then interpreted only inside the selected group (`null`
first; an existing sibling after it). Moving a root within the root group
carries its complete child block; a root that still has children cannot become
a child. Parent removal refuses until earlier commands have promoted or removed
every child. Sequence and target admission simulate those rules in batch order,
so a child birth racing a parent removal or a cross-group/stale anchor is a
conflict rather than a reducer no-op. The reducer remains total for historical
replay, while `diffDocsToMutations` emits evacuation/reparent moves before
parent removal and child removals before their parent.

**Undo is a COMMAND LOG, not a snapshot stack.** Each authored write also records `{ forward, inverse }` — the batch applied, and the delta back — gated on `suppressionDepth` rather than the replay bracket, because "is this one undo step" (a whole SA run is one; hydration is none) is a different question from "did the author just do this". `undo()` applies the inverse through the ordinary write path, so it queues for persistence like any other edit; `undoBatch()` / `redoBatch()` let the caller run the commit gate first. A command carries its own anchors, so a peer's insert cannot move where an undo lands and the history never needs rebasing.

The public `Mutation` union has one strict `mutationSchema`, used identically by builder, SA/MCP, commit, accepted rows, events, streams, diffs, undo, and replay from the canonical baseline. Mutation rows before that baseline are archived audit data and never parse through the current schema. There is no `replaceForm`: a whole-form result decomposes into `updateForm` plus granular field changes. There are no `notify*` mutations or reducer metadata channels.

Localization uses that same replayable dialect: `relabelSourceLanguage`,
`addLanguage`, `removeLanguage`, `setDefaultLanguage`, `setTranslation`, and
compare-and-set `reviewTranslation`. `relabelSourceLanguage` and `addLanguage`
carry an `AppLanguageIdentity` object; the other kinds reference an existing
language by its tag. There is no `updateLanguage` kind: names and directions
are derived from the identity, so no mutation edits them, and the
language-identity migration keeps persisted rows free of the old shape. The
raw `addLanguage` mutation
installs an empty target map; a product
gesture or tool that offers “copy from” composes it with explicit
`setTranslation` mutations in ONE admitted batch, so provenance and exact
per-unit values are durable rather than reducer-minted. A translation write must
name an existing current unit and carry its exact source fingerprint; prose
writes preserve protected references. `reviewTranslation` additionally fences
the prior value and fingerprint so a reviewer cannot silently bless a source or
peer edit they did not inspect. The shared tool fence separately echoes the
current source fingerprint for both set and review, while review also compares
the prior explicit entry. Each complete mutation batch prunes overlay entries
whose unit owner no longer exists exactly once after its structural endpoint is
known; individual translation writes never rebuild the whole inventory. Source
edits retain the same unit id and make its entry out of date. App-wide
case-property rename is the one semantic cascade:
it rewrites matching protected prose tokens in target entries, remaps the
semantic case-property-option unit ids, and advances the fingerprint only for
entries that were current before that rename.

The Builder's selected worker-language lens is ambient only inside
`BuilderLocalizationProvider`. Named entity hooks project app/module/form/field
display text through that context, and `useBlueprintMutations` lowers edits of
existing worker-facing slots into reviewed `setTranslation` commands before
the ordinary commit gate. Mixed edits keep their structural portion canonical
and restore source text carried by localized whole-value editor snapshots, so
an unrelated option or column change cannot copy a target label into the source
document. A target cannot create an optional string whose source slot does not
yet exist; the author creates that source content under the source lens first.
Agent, MCP, replay, hydration, autosave folding, and direct reducer callers sit
outside this context and continue to consume the canonical mutation dialect
with no ambient language behavior.

Every semantic merge unit has one final payload. A field stores its exclusive `optionsSource` inside the field/update patch. `updateColumn` carries exactly one content, sort, tile, or visibility payload; content replacement preserves the other independently-owned facets from fresh state. `moveColumn` changes one named Results/Details sequence, and `addColumn` names its placement in both. Search presence, per-setting changes, owner-only provenance, and final-input cleanup are explicit `updateModule` semantic payloads. Case-operation add/remove use `caseOperationChange`; every existing-operation scalar, write, link, or order edit uses only `caseOperationPatch`. After-submit links are entities of the form with their own four kinds — `addFormLink {formUuid, link, after?}`, `updateFormLink {formUuid, uuid, patch}`, `removeFormLink {formUuid, uuid}`, `moveFormLink {formUuid, uuid, after}` — and `updateForm` has no `formLinks` key, so two authors editing different links merge and a reorder is an anchor, never a rewritten array. No payload is paired with a duplicate whole-object body for another reducer.
**Clearing an optional slot uses an explicit `null`, never `undefined`.** A clear must survive two serialization hops: the SSE `data-mutations` wire and the persisted jsonb (both are `JSON.stringify`, which DROPS `undefined`-valued keys). An `undefined`-valued clear applies in memory but round-trips through neither — it never reaches the client doc store, and the next auto-save re-writes the stale value. `null` survives both. So `updateField`, `updateModule`, and `updateForm` all blank a property by setting it to `null`: each reducer applies its patch key-by-key, deleting the slot on `null` or `undefined` (only `null` round-trips). Their patch schemas make the CLEARABLE (`.optional()`) slots `null`-accepting (`clearablePartialPatch` in `types.ts` mirrors `partialOf` in `lib/domain/fields`), so a `null`-clear parses; the edit-tool schema reserves `null` for "clear". This null-as-delete rule is scoped to these three patch reducers — do NOT extend it to `setConnectType`, whose slot is genuinely `.nullable()` and stores `null` as a real value. `form.connect` is optional in a final `Form`, so the raw `updateForm` mutation uses `null` to remove the whole block; committed documents store either absence or a complete Connect configuration, never `connect: null`. That raw mutation is emitted only inside `connectTargetState.ts`'s complete app-wide plan: the public SA/MCP `updateForm` tool cannot change participation. A required slot (`id` / `name` / `type`) stays non-nullable in the patch schema, so a stray `null` for it is a parse error rather than a corrupting assign — `updateModule` / `updateForm` apply their patch without a final whole-entity re-parse. Media slots — field message media, module/form menu media, app logo — clear through dedicated mutation kinds (`setFieldMedia` / `setModuleMedia` / `setFormMedia` / `setAppLogo`) instead. Each carries an explicit nullable wire value, and the reducer deletes the optional property on `null`; canonical documents never store own properties whose value is `undefined`. Media is deliberately excluded from the generic field-edit surface. (A concrete array survives JSON whole, so a wholesale `{ options: [...] }` / `{ caseListConfig: {...} }` patch can clear a NESTED key by omitting it from the rebuilt object — that wholesale-replace path needs no per-key null and stays on `updateField` / `updateModule`.)

`mutationWireRegistry.ts` is the executable grammar review surface for that
contract. It assigns every final top-level kind an explicit ownership mode,
derives every semantic leaf/variant from `mutationSchema`, and separately
classifies every nullable leaf as clear, stored null, or first-position.
Checked-in snapshots pin both inventories, including omission semantics and the
fact that an own `undefined` is always invalid. A new kind, patch key, nested
case-operation arm, Search operation, column payload, select source, or
nullable leaf therefore fails CI until its final meaning is reviewed.

## Doc-shaped helpers colocated here

Pure functions that read or produce a `BlueprintDoc` (or a subtree of one) live in this package alongside the store:

- `fieldPath.ts` — path ↔ UUID projection (`resolveFieldByPath`, `getFieldPath`) for friendly XPath parsing/printing. The document, mutations, and SA/MCP tool addresses use UUIDs.
- `scaffolds.ts` — atomic born-valid `Mutation[]` builders for the builder's in-tree "add module / add form" affordances (`caseListModuleMutations` / `surveyModuleMutations` / `formScaffoldMutations`). Module scaffolds accept a destination `parentModuleUuid` plus sibling `after` anchor and land the whole born-valid module subtree at that exact one-tier position; omission means root append. The UI twin of the SA's `createModule` / `createForm`: each lands the entity TOGETHER with the minimal contents the validator requires, so the whole batch passes the commit gate as one candidate. A case-list module is born as a VIEWER — a `caseListOnly` module with a `Name` column and its case type declared in the catalog, NO form (a name-only registration form is valid wire, so there's no reason to force one); a new case type is declared via `declareCaseTypeMutations` (the granular `declareCaseType` kind, idempotent), since a formless viewer has no `case_name` field to auto-register it. `scaffolds.ts` also owns the case-type DECLARATION CHOKEPOINT (`declareCaseTypeForField`): the reducer does not auto-create an absent type on a field write (which would clobber a concurrent declaration), so every `caseWrite`-setting surface — the SA add/edit assembly, the MCP field handlers, `useBlueprintMutations` add/edit, `caseListModuleMutations`, and `formScaffoldMutations` — prepends a `declareCaseType` for a field writing to an undeclared type, and the gate rejects a leftover writer via `CASE_WRITE_UNKNOWN_TYPE`. A per-surface test (`__tests__/multiplayerMerge.test.ts`) exercises each field-birth chokepoint against an absent-type doc so a new surface that skips the declare fails CI. A survey module is born WITH one survey form (a single text question) — NOT bare: a module with no forms and no case list is a hard, build-blocking error in CommCare (`NO_FORMS_OR_CASE_LIST`, regardless of case type), so the only valid formless shape is a `caseListOnly` viewer. `formScaffoldMutations` lands a form with its default first field (`registration` → an explicit `{ caseType, property: "case_name" }` writer; otherwise one text question). Dispatched through `useBlueprintMutations`' `createCaseListModule` / `createSurveyModule` / `createForm`.
- `caseSelectionMutations.ts` — the one planner for **Case selection** on all
  three editors. `planCaseSelectionChange` is the one-module leaf: `undefined`
  means the canonical one-case document and emits an explicit `selection: null`
  clear through `setCaseListMeta`; a multiple shape carries its complete
  `{kind, maximum}` value. Enabling it also removes only
  `tile.persistOnForms` in the SAME mutation because that presentation needs one
  scalar case, while preserving the Results tile, grouping, placements, and
  every peer-authored facet. `planCaseSelectionTransition` follows the
  transitive, bidirectional same-case/no-custom-datum form-link component and
  any required case-list-only parent/child consumer. It proposes every actual
  linked-module setting first, requires their exact identities back as
  confirmation, and only then returns one atomic mutation batch. A link or
  topology that selection alone cannot repair returns its UUID-owned blocker
  and no mutations. The ordinary commit verdict still judges the exact
  candidate with `incrementalValidationScope`; the planner coordinates known
  selection dependencies but never replaces the validator or commits a repair
  prefix.

`scaffolds.ts` also owns `emptyBlueprintDoc` — the ONE canonical spelling of
the empty document both app genesis and the change-set base loader reduce
from (a duplicate literal would fork the genesis digest) — and
`canonicalAppGenesis`, the construction batch the EXPLICIT-BLANK birth arm
reduces: `setAppName` (trimmed requested name or the real persisted fallback
`Untitled`) plus exactly the `surveyModuleMutations` shape, returning the
starter module/form/field UUIDs. This is not an optional template and its
mutations are not replay history: the genesis owner (`lib/db/appGenesis.ts`)
admits and prepares a birth batch exactly once outside its retryable
transaction, unconditionally evaluates the absolute verdict and
`exportReadinessFindings` under one locked lookup-definition context, then
stores the result as the immutable Project-bearing sequence-one baseline
beside the root, exact lookup/media projections, entities, and attributed
`fold-baseline` app change. A chat build's DESIGN-SLICE birth reduces its
reviewed genesis change set through that same owner instead of this starter.
Builder, MCP, tests, and construction fuzz consume the same shapes or exact
receipts. There is no persisted empty app, caller seed callback, parallel
direct-name authoring, or second starter reconstruction.
- `mutations/sequence.ts`: the one flat-sequence primitive shared by every collection except tier-aware module placement. **Sequence IS array position**: `moduleOrder` / `formOrder[m]` / `fieldOrder[p]`, the `columns` / `searchInputs` / `options` arrays, each form's `caseOperations`, each automation's addressable child arrays, and the six flat top-level collections' ordering arrays (users, organization levels, location properties, and automations) are the order, not a set to be sorted. Flat adds and moves use `spliceAfter(sequence, uuid, after)`, where `after` is the UUID this entity now follows, `null` means first and `undefined` means append. It is TOTAL and IDEMPOTENT, and both are load-bearing because reducers replay: it removes before re-inserting, so a re-applied move lands the same sequence. Live admission rejects an anchor that disappeared rather than accepting the primitive's total append fallback. Module reducers apply the same anchor vocabulary to sibling groups and rebuild canonical preorder as one operation. `anchorForIndex` remains an internal UI translator where a local gesture begins with a rendered index; no external authoring boundary accepts a position as identity. `predecessorOf` reads what an entity currently follows. `sequenceMovesTo(before, after)` derives the moves between two states for the authoritative document diff.
- `mutations/automations.ts`: the canonical automation grammar. Top-level add/update/remove/move is separate from `editAutomationItem`, whose collection discriminator covers criteria, setup guidance, updates, recipients, schedule events, and user-data filters. Schedule shape has its own set/update kinds. Full desired-state callers must use `automationChangesForUpdate` / `diffDocsToMutations`; those helpers preserve stable child identities and emit item-granular changes rather than replacing a whole automation over a peer edit. When one desired-state diff both adds and reorders automations or child items, its move pass compares against `arrivalsProjected(before, after)`, the exact sequence the preceding adds have produced, never the stale pre-add order. Event order is runtime-semantic, so replay equality here is a behavior contract, not cosmetic ordering. Every mutation validates target kind, global UUID admission, and sequence ownership before the reducer runs.
	The absolute automation validator re-parses every complete post-mutation automation through `automationSchema` before contextual checks. That is the shared aggregate gate for granular replay/concurrency outcomes: an empty final recipient/update/event set, duplicate singleton, invalid schedule combination, or recipient/location mismatch never commits through Builder, SA, or MCP even though each mutation envelope is individually canonical.
  `updateAutomation`, `removeAutomation`, and `moveAutomation` all carry and
  check `targetKind` in the total reducer itself, just like `updateField`:
  reconciler refolds can replay an already-admitted pending command after a
  peer removed its target and later reused the now-free UUID for the other
  union arm. A stale patch, removal, or reorder no-ops instead of changing the
  peer's new automation kind.
  Automatic-update property scopes follow HQ's automation resolver: `parent`
  means the canonical `parent` identifier even when its relationship is
  `extension`, while `host` means the declared extension host. Reference-index
  extraction and case-property rename must use that same resolution so an
  extension-backed parent can neither evade deletion guards nor miss a rename.
  Alert message-template `case.parent` remains a separate child-only HQ
  template context; its structural atom carries the target case type directly.
  The Builder's complete-rule editor also passes the JSON fingerprint it opened
  to `replaceAutomation` / `removeAutomation`. The hook compares it with the
  authoritative record and applies the derived batch in one synchronous call,
  closing the render-to-click race instead of relying only on a rendered
  conflict banner.
  The one collection with TWO sequences over one set is the case list: `caseListConfig.listColumnOrder` and `detailColumnOrder`, both required, both holding every column from birth regardless of visibility. `orderedColumns(config, surface)` (`lib/domain/modules.ts`) is the single home of "the columns of this screen, in order" — every emitter, canvas, and read surface goes through it, because when four of them derived it independently, each got it wrong at least once. Sequence never reaches CommCare: consumers read a surface's order and emit positionally.
- `fieldWalk.ts` exposes `orderedModuleUuids` / `orderedFormUuids` / `orderedFieldUuids` — the doc-shaped sequence walks shared by `summarizeBlueprint`, `searchBlueprint`, wire emitters, builder render hooks/search, and the chat signal grid. They read membership arrays directly; there is nothing to sort.
- `fieldParent.ts` / `fieldWalk.ts` / `searchBlueprint.ts` / `predicates.ts` — reducer-shaped utilities the store and UI share.
- `navigation.ts` — doc-aware `Location` resolution for the routing hooks.
- `kindConversionCascade.ts` — the property-centric conversion plan every kind-conversion surface consults (`planKindConversion`): a case-bound data-type flip — ANY flip, string-scalar, temporal, numeric, or the select↔text reshapes — converts every peer FIELD writer DERIVING the explicit `caseWrite` property's current type (derived-type selection, so a barcode/secret writer on a text property counts; one whose kind can't reach the target BLOCKS the plan with the peer named — the batch would otherwise bounce off the gate misreading a healthy property as broken) in the same gated batch, and re-declares a stale declared `data_type` via `setCaseProperty` (no field edit can otherwise satisfy `FIELD_KIND_PROPERTY_TYPE_MISMATCH`'s "change the property's data_type"). A case-operation writer blocks the gesture explicitly: its expression is a first-class writer but has no mechanical field-kind conversion, so the author must update/remove that operation before changing the property type. Stored rows are never the plan's business — `applySchemaChange` reshapes string↔array flips totally and casts every other transition per row, parking what cannot carry (holding its case). A flip whose per-row cast can fail (`castCanFail` in `lib/domain/casePropertyTypes.ts`) carries a `dataLossRisk` verdict on the plan; the CONSUMERS gate consent on it — the builder's `ConvertImpactDialog` and the SA `editField`'s needs-confirmation round both count the real impact via the store's `conversionImpact` preview before dispatching — while the committed mutations stay consent-free (replay purity: undo and canonical replay re-run the migration unconditionally, and the review surface is the recovery path). Consent is scoped to the CONVERT gesture by design: a retype reached without one — a `caseWrite` retarget onto a property with rows of another type, a hidden writer's expression inference — has no gesture to hook, so it stays write-time-detected, parked + held, and reported (the toast, the parked note, Data to review), per the #252 design record. A conversion to `hidden` (agreement-exempt) converts only the addressed field and PINS an undeclared entry to the source kind's type when it was the last typed writer, so later expression inference can't retype the property under its existing rows. Peers resolve through the reference index's `declarersOf`, never an unindexed whole-doc search; callers whose same call retargets/clears `caseWrite` pass the field with that override applied. Consumed by the SA/MCP `editField` and `useBlueprintMutations.convertField` — same batch-building-layer-cascade discipline as `caseTypeRetirement`.
- `unwrittenProperties.ts` — the informational "where does this data come from?" derivation: a DECLARED catalog property appears iff something reads it from any registry slot (`referencingSlotsOf`) and no field or case operation writes it (`declarersOf`), standard properties and `case_id` excluded. Deliberately a FACT, never a finding — a no-writer read is a normal state (a viewer app over externally-managed cases is exactly this), so nothing gates, blocks, or asks for a fix. Memoized per doc reference like `effectiveCaseTypes`. Three consumers: the app-settings data-sources dialog (via `unwrittenPropertyCards` / `useUnwrittenPropertyCards` — the pre-rendered display projection), the blueprint summary's closing `<system_reminder>` block, and `getField`'s per-field reminder (`unwrittenPropertiesReadBy`). Read phrases render per audience (`ReadPhraseAudience`): the reminders speak the SA tool vocabulary (case-list column, search input, case-list filter), the dialog speaks the case workspace's authoring vocabulary (Cases available, search field, case information) with the builder's curly quotes — and the builder column phrases stay visibility-neutral because the index records only the slot, never which column or whether it is on-screen. Writer EXISTENCE is the whole check; never strengthen the copy past what is checked.
- `caseTypeRetirement.ts` — the orphaned case-type-record cascade every module-displacing surface consults: `planCaseTypeRetirementOnRemove` / `planCaseTypeRetirementOnRetype` decide, for a `removeModule` or a module case-type change, whether the displaced type's record retires in the same batch (orphaned + unreferenced), needs nothing (still owned), or blocks the batch with a person-readable reference list. Consumed by the SA/MCP `removeModule` + `updateModule` tools and this package's `useBlueprintMutations` — the cascade is an explicit granular `retireCaseType` mutation from the batch-building layer, NEVER a reducer side effect, so the authored command fully describes its effect and a concurrent edit to a DIFFERENT type merges rather than being clobbered.
- `formLinkMutations.ts` — the batch-building planners for a form's after-submit links (`planFormLinkAdd` / `planFormLinkUpdate` (rebases only the slots the editor changed; a slot a peer changed first refuses; a retarget that leaves the carried values alone drops the names the new destination never reads — the gate would refuse them as `FORM_LINK_DATUM_UNUSED` — and says so, `droppedDatums`) / `planFormLinkRemove` / `planFormLinkMove` (index → anchor at the landing) / `planSetFallback`), and `afterSubmitPlan`, the ONE reader of what runs when nothing matched: the terminal unconditional link when one exists, else `postSubmit` (explicit or the form-type default). Two rules keep every produced document admitted: a planner that would leave every link conditional with nothing stored (the first conditional link with no otherwise; removing the otherwise; turning it conditional) writes the form's current effective destination explicitly in the SAME batch and says so (`pinsFallback`), so a person never meets `FORM_LINK_NO_FALLBACK` and a tool's message names the pin; and a built-in destination is stored explicitly whenever links exist (the null-when-default shorthand applies only to a form with no links). Conditional means "prints to non-empty XPath", exactly as the validator reads it (`formLinkIsConditionalIn`).
- `formLinkReview.ts` — the pure verdicts a surface asks before it offers: `formLinkMoveVerdicts` (every destination index at once, so a drag and a keyboard move read one answer), `formLinkTargetVerdict` (self / cycle through `lib/domain/formLinkGraph.ts` with the edited link's own edge ignored / missing), `formLinkRequiredDatums` + `formLinkCarryVerdict` (the destination's selection datums and whether this form's entry can carry them automatically — asked of the projector the wire uses, `lib/commcare/formLinkProjection.ts`, never a second derivation; its `matched` entries name which source datum feeds which, so the copy can say "the case this form opened" vs "the case this form creates"), `formLinkManualCarryVerdict` (whether the carried-values editor may replace that automatic match with an explicit datum map; several-case collections refuse), `formLinkAddChoices`. `__tests__/formLinkReview.test.ts` pins every `ok` against the commit gate. This is one of the allowlisted `lib/doc` consumers of `lib/commcare` in `biome.json`.
- `hooks/useFormLinks.ts` / `hooks/useFormLinkFacts.ts` — the one read/write surface the builder's After-submit screens and the form-settings row share (the `useCaseOperations` shape): every write reads the store at invocation and commits through the inline gate; `useAfterSubmitPlan` is keyed on the exact slots the plan reads.
- `mutations/forms.ts::moveForm` carries every inbound form target with the form: a form target names its form AND the module holding it (the wire addresses `form_id` inside `form_module_id`), so a cross-module move rewrites each pointing link's `moduleUuid` in the same reducer step and the reference index re-extracts those source forms (`referenceIndex.ts` `moveForm` carriers). The pair is one thing, "go to this form"; a link never dangles because its destination moved.
- `formLinkDependents.ts` — what removing a form or module does to the after-submit links that point INTO it: `planFormLinkDependentsOnRemove` REFUSES with every source form named (SA and person voices), never cascades. A cascade can itself fail the gate (removing a terminal else re-exposes `FORM_LINK_NO_FALLBACK`), and a silently repointed link changes where people go without saying so. - Case-operation updates decompose into independent merge units: scalar operation slots, writes keyed by destination property, links keyed by identifier, and the order slot. The semantic patch schemas omit immutable operation UUIDs and reject empty operation/write/link patches, so an accepted granular event always has work and can never replace identity. A move names the operation it now follows, and an anchor cannot be shifted by a peer's insert — so there is no rank to fence, and `mutationTargetsInvalid` has nothing to check on a move beyond the mover existing. - `referenceIndex.ts` — the reference + declarations index behind `BlueprintDoc.refIndex` (shape + key vocabulary in `lib/domain/referenceIndex.ts`). Every write-path reference operation answers "who references X / who declares X" through its queries (`referencingCarrierUuids`, `declarersOf`) instead of walking the doc — a write-path reference scan is a defect. The index carries only structure something consumes — an unconsumed bucket maintained on every mutation is pure cost, so when a query loses its last consumer the bucket leaves both builders with it. Every root and nested identity bucket is also a null-prototype own record; `ensureReferenceIndex` recursively rebuilds an absent, ordinary-prototype, or partly unsafe index before incremental mutation trusts it, while read-only queries avoid an O(index) audit on every read by checking normalized roots and enumerating nested buckets through own-key primitives. Correctness is held by the incremental ≡ rebuild oracle: `buildReferenceIndex` doubles as the hydration builder and the fuzz oracle (`__tests__/referenceIndex.fuzz.test.ts` over raw mutation batches, plus the construction fuzz's parity assertion over real tool sequences), with a throttled dev-mode tripwire at batch end. Consumers: the field-ID/move rewriters in `mutations/fields.ts`, `caseTypeRetirement.ts`'s reference scan, `userMutations.ts`'s custom-property removal preflight, `identifierVerdicts.ts`'s peer-aware conflict scan, and `unwrittenProperties.ts`'s read + writer lookups (`referencingSlotsOf` / `declarersOf`). The chip resolve gate deliberately stays catalog-backed — the catalog is a superset of writer declarations (a type is declared explicitly via the `declareCaseType` chokepoint, and `ensureCatalogProperty` then appends a writer's property to that EXISTING declared type — it does not mint an absent type, which is what lets two members add different properties to one type and merge), and the validator's accept set reads the same catalog, so re-keying chips to live writers would create offer-then-reject drift.
- `userMutations.ts` — the batch-building planners for the three user collections (`lib/domain/users.ts`). Each collection is a uuid-keyed record PLUS its ordering array, and the two cannot disagree — `decomposeBlueprint` refuses to persist a doc holding an entity its sequence does not place. Adds append to that array; updates compare each UUID-keyed value bag and emit one `updateUserType.valuePatch` / `updatePersona.valuePatch` event per changed property. A value event therefore merges with a peer editing another property instead of replacing that peer's bag. Property removal FIRST queries the reference index and refuses with every exact `(carrier, slot)` occurrence while any UUID-backed XPath or Predicate leaf survives — relevant and required conditions on one field are two settings even when their friendly owner text matches; descriptions never deduplicate distinct slots. It never cascades a condition/calculation or degrades identity back to mutable text. Once unreferenced, cleanup travels as explicit granular mutations: one value clear for every role or persona that names the property, then the removal, in one batch. Removing a ROLE personas still hold is REFUSED with those personas named, because quietly unassigning them would change who those personas are without saying so. Removing a persona is just the blueprint removal: nothing in the blueprint references one, and every retained case row it owns stays stored with that `owner_id`, including rows of retired case types. The confirmation counts that exact owner-wide retained population before enabling Remove and explains that unfiltered data views may still show those rows; it offers neither deletion nor reassignment. This is Nova's design/test-data policy, not an analogy to HQ worker removal: HQ deactivation leaves cases while worker deletion soft-deletes them, and neither behavior dictates this lifecycle. These are the FIRST new top-level collections in the document, so they are the first vocabulary that mints new mutation discriminators rather than extending an existing kind; `docs/plans/complex-app/00-contracts.md` holds the program rule and what makes it safe (optional slots omitted when empty, explicit row-classifier branches, and the matrix pinning what it can prove).
