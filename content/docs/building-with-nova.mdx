## From a description to an app

When you describe an app, Nova works out who uses it, what it records, and how
people move through each task. It keeps those decisions in an **App plan** you
can read as the work develops. The same architect designs and builds the app,
with an independent colleague reviewing the plan before construction begins.
Nova asks when an answer would materially change the app and cannot reasonably
be assumed.

The plan can include forms, record lists and details, navigation, access, and
setup outside the app. A task such as reading visit history may need a list
rather than another form. Each form has its own required answers and validation;
those rules do not automatically spread to other forms using the same data.

When questions share facilities, products, or other values, Nova can use a
[Project data table](/docs/project-data). Planning and review leave Project data
unchanged. During construction, Nova creates the needed tables through the
usual Project data tools. Changing a table already shared by other apps needs
your request or confirmation of that wider effect.

The status above chat shows whether Nova is planning, reviewing, building, or
waiting for input. No placeholder app appears during planning. The first app
you see contains a complete, valid workflow; Nova saves further work in valid
updates. The builder stays read-only during the initial build, and unfinished
private changes never appear as saved app content. When an edit is rejected during
construction, Nova keeps the other accepted changes available so it can correct
the problem and continue.

Before finishing, a colleague inspects the saved app against your request and
the plan. Nova can evaluate forms with representative answers to check
conditions, validation, and proposed record values without submitting real cases.
A form check does not establish menu reachability or execute additional record
operations. Nova can also exercise a journey from app entry through selection,
answers, submission and the next task using disposable test records. These
journeys can reveal inaccessible menus and incorrect saved effects without
changing your live cases. They check Preview behavior; they do not prove native
device behavior, deployment, media uploads or every possible workflow.
Chat distinguishes these checks and other activities from completed
changes. A rejected edit appears as an unsuccessful activity, with no claim
that the change was saved. Nova uses the diagnostic details to make corrections
and explains any remaining issue in the conversation. It names anything it
could not verify.
Direct editing and Preview become available when the build finishes.

## Try the app in Preview

Screen readers announce question and section positions within their current
container. Hidden calculations and questions that do not currently apply are
skipped, including inside each repeated entry.

Preview checks each answer before submitting the form. Whole-number questions
accept integers; decimal questions also accept fractions. If an answer is
incomplete or has the wrong format, it stays visible beside a message so you
can correct it. Optional questions can be left empty.

Changing the Preview worker returns to app entry and clears the previous
worker’s form and record selection. You can then follow the new worker’s menus.
It does not change your Nova account or Project permissions.

Assigned places also supply built-in worker information, including the primary
place and its case-sharing group. Nova can use those values when records need to
pass between workers. Preview identities need place assignments for that check;
disposable journey assignments do not configure deployment workers or places.

The identity menu's **Test journeys** opens recorded agent checks. You can read
each step, the worker identity, visible questions and saved test effects. An
earlier-revision notice means the app has changed since that check. Reading a
journey does not switch your Preview identity or submit any forms. Ordinary
Preview uses your real case records; the recorded journeys use separate test
records. Disposable records and places do not appear in ordinary Preview, and
the recorded view cannot rerun submissions.

## Name new records

A registration form’s **Form settings** includes **Record name**, the name shown
in lists and record details. Choose an answer or combine answers in an expression.
Changing the name preserves the form’s other saved answers. Nova uses the same
naming setting when building through chat or the MCP API.

## Share a document with Nova

Nova prepares documents before using them in chat. In the file library,
**Reading** shows that work in progress and **Ready** means the document can be
used. If reading fails or the status cannot
be confirmed after several minutes, **Retry** lets you try again. Your uploaded
file stays in the Project's library. Opening a document that previously failed
does not start another read automatically.

Reattaching the same file later keeps the original design's sources intact.
If a source is removed or its content changes, Nova pauses work that depends on
the original version rather than continuing with different evidence.

The account menu's **Files** opens that library. While an app is open, it shows
files from the app's Project. Elsewhere, it follows your selected Project.
Project viewers can preview files; editors can also upload and delete them.
A ready document's information button explains what Nova reads; opening the
document lets you inspect the summary itself.

A document is ready only after its read finishes. An interrupted response stays
unavailable even if part of it looks complete. Nova preserves literal paths and
text examples in the returned summary. For large spreadsheets, the summary
names any sheets or formulas left unread because an extraction limit was reached.

## Resume an unfinished design

An app design that has not produced its first workflow appears under **Designs
in progress** on the app list. Choose **Resume** to return to the same
conversation and continue from its saved stage. Choose **Discard** when you no
longer want Nova to take that design further.

Nova saves its plan, conversation, and construction work as it goes. After an
interruption, it reconnects to that work, checks the current app, and continues.
Refreshing does not restart a turn's work allowance. If a turn reaches its limit,
its saved work remains available for the next message.
For edits to an existing app, chat explains when its work limit interrupted the
turn. Completed changes stay saved, and you can ask Nova to continue.

If you say more requirements are coming, Nova can keep the plan and wait. You
can also ask it to plan without building. A question or conversational pause
does not require you to restate earlier decisions.

The design has its own recovery address from the first chat turn. If an app was
created while an update was lost in transit, that address opens the saved app
instead of creating another copy.

## If a later step stops

Once Nova saves the first workflow, a later failure leaves that valid revision
intact. The initial-build editor stays locked while construction is unfinished.
**Resume build** continues from the saved plan, conversation, and work. It remains
available after refresh to Project members who can edit the app.

Nova distinguishes unfinished work from a completed app. It can keep correcting
private changes without exposing them as saved content, and a failed save does
not erase an earlier checkpoint. Setup outside Nova remains visible as work for
a person to complete.

## Start with a blank app

Choose **Start with a blank app** when you want to begin directly in the
builder. That path creates Nova's smallest valid Survey, Form, and Question
starter immediately, without the reviewed conversational design flow.

As the app grows, [submenus](./nested-menus.mdx) can group related modules under
one top-level menu. Nova supports one child level and keeps menu placement
separate from parent-case relationships.

## Text in your app

Nova checks app names, question text, translations and formula values before
saving. If pasted text contains a character CommCare cannot preserve, Nova names
the affected text so you can remove that character and try again. Accents,
non-Latin scripts and emoji are supported.

If Nova cannot save a wording change, your text stays open beside the reason so
you can correct it and try again. Rich-text tables keep images when you save
and reopen them, including cells that contain only an image.

Adding **Required** makes a question required immediately. Its condition is a
separate choice. A new blank hint closes when you press Escape, and changing
questions closes any optional editor you had just opened.

**Show when** affects the question's data as well as its visibility. When its
condition is false, the answer is omitted from submission and can read as blank
in other expressions. A **Hidden** field can carry a calculated or starting
value without displaying a question.

## XPath that will run in CommCare

When a formula needs correction, your draft and keyboard focus stay in the
editor so you can keep typing while its explanation is visible.

Nova checks formulas against the functions CommCare's device runtime actually
implements and the same formulas run in Preview. A function being part of
XPath 1.0 or XPath 2.0 is not enough by itself. Functions that CommCare does
not provide are refused while you edit, before they can cause a runtime error
for a worker.

Nova can also accept a small extension when it has an exact, tested translation
to the device runtime. For example, you may write `normalize-space(...)` in the
visual XPath editor; Nova exports an equivalent expression made from CommCare's
native functions. CommCare HQ case-search formulas are checked separately
because their server-side function list is different from the device's.

Nova never saves a formula that its owning Preview surface cannot faithfully
run. Existing apps keep that guarantee when support changes: Nova continues to
run their formulas or migrates them without changing their meaning. A defensive
Preview error is treated as a Nova bug and contained so the rest of the Builder
stays available; it is not an expected state the author needs to repair.

Lookup-table formulas use Nova's table and column references, which keep their
identity when a table tag changes. Raw XPath can use the stable `casedb` and
`commcaresession` instances, but it cannot name a lookup table by its mutable
wire tag.

A hidden value has one expression and a choice of when it runs. **Keep in
step** recalculates whenever a value it uses changes, and every time the form
opens, including when a worker resumes a saved form. **Set once** runs when the
form first opens and never again, which suits a timestamp or a fixed value.
Switching between them keeps your expression. A hidden value that saves to the
case the form opened is set by its calculation, so the case's stored value
never overrides it. When a hidden calculation saves to a date-and-time property,
Nova preserves its clock time in Preview and export. Choose a date property when
you only need the calendar day. A value that records an approval should have its
own property so later edits do not replace that event with the record's general
last-modified time.

A form's [After submit](/docs/form-links) links decide where the app goes once
the form is submitted, and their conditions run after the form has closed.
They can use the case the form just saved and worker information, but they
cannot read answers from the form that just closed. Nova refuses those
form-local references instead of exporting navigation that will fail on the
device.

## External setup

Some workflows depend on work outside the app, such as providing an existing
media asset or configuring an automation in CommCare HQ. Nova names those
prerequisites and never claims that it completed them.
Preview does not pretend to run external automations. One design session builds
one app in your current Project; if a request describes several apps, Nova asks
which one to build first.

## Return to an app screen

The Builder's address follows the screen and selected field, so a shared link
can reopen that location. Back and Forward return to screens without stepping
through every field selection. Your worker-language choice travels with the
link. An older link that names a form and a field from another form opens the
named form with no field selected.

Deleting a field selects the next visible field, or the previous one when it
was last. Deleting a group skips the questions removed with it. Undo and Redo
let you take back or restore those changes.

## Insert an answer or saved value into wording

While editing a label, hint, help text, choice label, or validation message,
**Insert reference** opens a picker of available answers and properties. You can
search by name or reference path, then choose a result to insert a chip. Typing
`#` also opens reference suggestions. The chip shows the value when the form runs
and preserves its target when you rename or move the referenced question.

Typing or pasting `#household/case_name` alone keeps it as literal text. To use
it as a value, select the exact reference text, choose **Convert to reference**,
and select the matching result. If it isn't available in this form, you can
search for another or leave the text unchanged.

Selecting a chip offers **Replace reference**. Its picker also offers
**Convert to text**, which keeps the current reference spelling as ordinary
wording. Deleting a chip removes the reference; undo restores it. Escape closes
an open picker first, leaving your wording available to edit.
