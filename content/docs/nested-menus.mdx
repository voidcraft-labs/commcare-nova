---
title: Organize an app with submenus
description: Group related modules under one menu while keeping each workflow complete and easy to find.
---

A submenu gives an app one extra level of navigation. A top-level module can
hold its own forms or case list and also open related child modules. App home
stays short, while the child workflows remain separate and easy to name.

Nova supports one submenu level. A child cannot contain another child, and a
top-level module that already has children cannot move under another module.
This is the same menu shape CommCare HQ can author and maintain.

## Choose a list or a grid

In **App settings → Menu layout**, choose how the first menu and the other
menus look. A list gives long names room. A grid makes the choices easier to
recognize by their pictures. On Android, workers can press and hold a tile
to hear its spoken label. On Web Apps, spoken labels play in a list.

In a menu’s settings, **Use a grid** saves its individual choice. You can set
it while the app shows lists or grids throughout. To use the saved choices,
choose **Choose per menu** for the other menus in App settings. If that menu
shows its forms inside its parent, the parent shows all its choices in one
grid. A menu that lists another menu's forms follows the layout for the other
menus. The first menu always uses the layout in App settings. Preview lets you
try the choices on either platform.

If an older app already has a layout someone chose in CommCare HQ, the next
publish there lists which choices it would replace. To keep them, match the
listed choices in App settings and the menus' settings, then publish again.
To use the layouts in Nova, tick **Publish over this** for that project space.

## Add or move a submenu

Use the app tree to add a submenu under an eligible top-level module. To move an
existing module, open its actions or **Menu placement** in module settings, then
choose a top-level destination. **Make top-level** returns a child to app home.

Moving a module keeps the module, its forms, and its links intact. Its address
does not change, so an open form or settings screen stays selected while the
breadcrumb updates to show the new path.

Every module still needs its own working content. A parent needs at least one
form or a valid case list, and a child follows the same rule. Child menus do not
turn an otherwise empty parent into a complete workflow.

A parent with only a case list can group child modules that use the same case
type. To group a child with a different case type, make the parent form-bearing
and give it a form so CommCare can keep both case selections distinct.

A child's form that creates a case of the type its parent's first form opens
can't sit under that parent: CommCare HQ would give the new case the place of
the case chosen in the parent, and the form couldn't open. Nova names the form
and invites you to move it to another menu, or to start the parent with a form
that doesn't open a case of that type. A registration form for that type
belongs in a top-level menu, which can show it in the first menu or offer it
from a case list.

Nova will not remove a parent while it still has children. Move or remove those
children first, then remove the parent.

## Show the same forms in another menu

A team can keep an intake form and a visit form under **Patients** and give clinic workers a shorter **Today’s visits** menu. Open **Add module** and choose **Forms from another menu**. Choose **Patients** as the source. In the new menu’s settings, choose which forms workers see. New forms in the source appear here too.

Open a form from either menu to edit its questions, translations and case updates. Workers reach the same form through both menus. Each menu has its own name, case list, search and display settings. Hiding a form in one menu keeps the form and all its existing submissions.

If the source menu has submenus, Nova adds a corresponding submenu under the new menu. You can edit its name, list and search there. Adding or removing a source submenu updates the corresponding menu too. To change which source supplies forms, open the parent menu’s settings. Nova names any form links to remove or reassign first.

## What people see in Preview

App home shows top-level modules only. Opening a parent shows its own forms
alongside its child menus. Opening a child keeps the complete menu path in the
breadcrumb.

If the parent starts by choosing cases, opening it shows its case list first,
as a device does, and its forms and child menus appear once a case is chosen. A child with the same case type
can keep the selection when both modules choose one case, or both choose several
cases and the child's maximum fits the complete set. A child with a different
case type uses every selected parent to find the combined set of related
children, then asks for its own selection.

A CCZ carries these selections as Preview runs them. CommCare HQ cannot yet
preserve two of these workflows: finding related cases from several selected
parents, and opening a same-case submenu whose selection limit is smaller than
its parent's. While an app uses either one, Nova names the menus involved and
holds back publishing and the CommCare HQ app file. Selecting one parent case,
or raising the submenu's limit to its parent's or more, makes the app ready for
CommCare HQ again. A CCZ is made for a project space the app is already
published to, so an app that uses one of these workflows and has never been
published runs in Preview only.

## Menu parents and case parents are different

A menu parent controls where a module appears. A case parent describes how two
case types are related and which case someone selects first. Changing one does
not change the other.

Selecting a parent first narrows existing child cases for followup and close
forms. In Preview the breadcrumb names each case chosen along the way, the
parent included, even when another menu's list chose it: the parent follows
the menu that asked for it, and selecting it returns to the list of its
children with the parent still chosen. Selecting any step keeps every case
named before it and lets go the ones after it, so a form you chose before its
cases asks for the parent again and then opens once you choose the case. Where
a parent has a parent of its own, Preview asks for each in turn, and **Back**
on a later parent's list returns to the list before it with that choice
undone, as a phone does. A basic registration form creates its primary case
without storing that selected parent as a case relationship.

For example, **Households > Visits** can be a menu path even if both modules
work with household cases. Or **Clients > Referrals** can be a menu path while
the referral case type is a child of the client case type. Nova keeps the
navigation path and the case relationship separate, then carries the right
selected cases when the workflow opens.

## Conditions and repeated views

A child is available only when its parent and the child itself are available.
Give each module the condition that belongs to it. Nova combines the path while
someone navigates, without copying the parent's condition into the child. A
parent that is off the menu takes its child menus off with it: no menu reaches
them, though each child keeps its own **Show on the menu** setting.

A form belongs to one module. Nova does not place one form under several menus.
When several modules should show the same case data in different ways, use
case-list filters and focused module design. When two workflows truly differ,
give each one its own form so its purpose stays clear.

After-submit links can still open another module or form. Those links choose
where to go after a form closes; they do not change the app's menu structure.
A form can link to a submenu only from a submenu whose parent has the same case
type; from anywhere else, link to the menu above it or a form inside it. See [After submit](./form-links.mdx) for that workflow.

A form in a child menu can also go to **Parent module** after submit: the
parent menu opens with the case it selected still selected, listing its own
forms and its child menus. That destination isn't offered while the parent
selects several cases, or while the parent is off the menu.

## Show a menu's forms in the menu above

A menu can show its forms in the menu above. You can turn on **Show its forms
in the menu above** in the menu's settings, and its forms appear on the app's
first menu, or in its parent menu for a submenu, with no entry for the menu
itself. It suits one or two forms people should reach without opening a menu,
such as a registration form on the first screen. The menu keeps its case type
and case list, so each form still opens the right case. Such a menu has no
screen of its own, so it can't have a search, a registration from its case list
or a deep link, and a link or an after-submit destination can't open it; you can
link and deep link to its forms. A form shown on the first menu can return to **Previous screen**. A link to one
of these forms can carry the selected record. If every form on the first menu
uses that selection, Android keeps the record when someone presses Back. A
second form that asks for the same selection then opens on the same record.
Web Apps opens the first menu with a fresh choice. When the same selection
could open a different kind of record, Nova shows which menu needs its own
screen. On a
screen that lists forms from more than one menu, people choose a case first only
when every form there opens the same case; otherwise they choose a form first.
