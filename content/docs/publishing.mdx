---
title: Publishing to CommCare HQ
description: What happens when you publish an app, how to turn it into something workers can open, and what you set up by hand on your project space.
---

Publishing sends your app to a CommCare HQ project space. Nova remembers where
it went, so you can come back at any time and see how far along it is. An app
you [brought in from CommCare HQ](./bringing-in-from-commcare-hq.mdx) publishes
back to the app it came from.

Question types carry through to the published form. For example, a Decimal
question remains a Decimal question when you open it on CommCare HQ.

Getting an app into workers' hands takes six stages. Nova completes the first
three, you make and release a version on CommCare HQ, and Nova confirms the
released app is ready for workers.

## The six stages

| Step | Who does it |
| --- | --- |
| **Checked** | Nova, before anything is sent |
| **Data in place** | Nova, when the app has tables or places |
| **On CommCare HQ** | Nova |
| **Version made** | You, on CommCare HQ |
| **Released** | You, on CommCare HQ |
| **Ready for workers** | Nova checks it |

Nova shows all of these in **App setup → Publishing**, one card per project
space this app has reached, filled in as far as you have got. A version you
made on CommCare HQ last week is one **Check status** away there, and you never
have to publish again just to find out where things stand. The card also holds
everything else a publish leaves behind: the workers list, the set-up-by-hand
notes, and, when you can edit the app and your connected API key reaches that
project space, a **Publish again** that opens the Publish dialog already
pointed at it.

The setup notes use your app's current names and ordering. Organization levels
appear with parents before children, and place totals stay with their level
when you rename it. Renaming or reordering something in Nova updates these
notes; changes you apply by hand on CommCare HQ still need to be made there.

**Publish** opens a dialog without leaving the builder or your place in Preview.
Choose a destination and app name, then **Continue** to **Review and publish**.
Nova checks the destination and shows any confirmations it needs before
**Upload** becomes available. **Back** returns to your destination choices.

**Published destinations** expands the short status rows for spaces the app
has already reached, with a link to **App setup → Publishing** for the full
picture. For a file download, choose the file type and destination details,
then **Continue** to review before downloading.

### Checked

Before anything leaves Nova, it checks what would stop the publish working: that
your API key can reach the project space you picked, that the app itself has
nothing outstanding, that you have confirmed what the project space's plan and
settings give the app, that the project space supports the app features that
need destination support, that the app already there is set to CommCare 2.57 or
later, that nothing Nova publishes there has changed in CommCare HQ since its
last publish, that no application profile there includes a language the app no
longer has, and that the app's Web App setting there matches where the app
runs ([A note on Web Apps](#a-note-on-web-apps)). If any required support is
missing, or Nova cannot confirm it, nothing is sent. The result names the
capability and the next step. A change made in CommCare HQ is yours to decide
on; see [Changes made in CommCare HQ](#changes-made-in-commcare-hq).

If Nova cannot confirm the complete list of project spaces your key can reach,
it reports the connection problem instead of showing an incomplete list. A
status check that cannot read reliable build or release information keeps the
last confirmed status.

#### What the project space's plan includes

Some of what an app uses comes with some CommCare HQ plans and not others: Web
Apps for an app that runs there, worker records, lookup tables, child cases,
links to other forms, Save to Case, locations, and Data Forwarding for a
CommCare Connect app. No API key can read a
project space's plan, so Nova asks you. The Publish dialog lists each one your
app needs and what goes wrong without it. **Details** shows the plans that
include it, the forms that need it, and options when it is unavailable. Tick
**This project space has it** for each one, and
publishing can go ahead. [Project-space compatibility](/docs/project-space-compatibility#plan-features)
lists them all.

Four project-space settings are asked about the same way, because no plan
decides them and no API reads them:

- **The flat location list**, for an app that reads the places in your
  organization. Phones and Web Apps both take that list by the project space's
  own setting, which sends it unless someone turned it off on its Location
  Fixture page.
- **A Connect forwarder**, for a CommCare Connect app. Its forms reach CommCare
  Connect only through a forwarder set up on CommCare HQ's Data Forwarding page.
- **Sync Cases On Form Entry turned off**, for an app that runs on Android and
  has a menu with Search whose form works on a case. While it's on, Android
  phones can't open those forms. A project space admin can turn it off on the
  project space's Case Search page, and an app that runs in Web Apps only
  doesn't need it.
- **CommCare Supply turned off**, for an app with an advanced menu whose case
  list is its own menu item. CommCare HQ adds a step to that menu where it's
  on, and only Dimagi Support can turn it off.

Nova keeps your answer with that project space, so the next publish there
doesn't ask again. A publish that stops for another reason keeps nothing, and
the dialog keeps your ticks until one goes through. Nova can't see a later
change to the plan either: if the project space loses something you confirmed,
choose **Withdraw** beside it on the project space's card in **App setup →
Publishing**, and the next publish asks again.

#### The CommCare version

Each app on CommCare HQ is set to a CommCare version, and Nova's apps need 2.57
or later. Where the app already on the project space is set lower, the publish
stops before it sends anything and names the version. You can raise it in that
app's settings in CommCare HQ and publish again. Phones on an older CommCare
can no longer install or update the app after that. Saving that settings page
can also set the app's other settings there, so the next publish may show you
what changed before it sends anything.

Nova also reports useful guidance that does not stop the publish. For example,
the project space may be able to run the app while large Search results open
more slowly, or a persona may be missing worker information that CommCare HQ
will ask for later. Read [Project-space compatibility](/docs/project-space-compatibility)
for the complete check.

#### Application profiles

In CommCare HQ, an app can have application profiles, each a set of the app's languages for one
group of phones. Nova keeps them as they are and can't change them. If you remove a language in
Nova that a profile there still includes, the next publish to that project space stops before
it sends anything and names the profile and the language. You can take the language out of the
profile, or remove the profile, on the Application Profiles tab of the app's Releases page in
CommCare HQ, then publish again. That tab shows only where the project space's plan includes
application profiles. On any plan, removing the language on the Languages tab of the app's
settings in CommCare HQ takes it out of every profile too, and the next publish may show you that
change before it sends anything. A language you add in Nova joins no profile until you add it
there.

If someone added the language in CommCare HQ since Nova's last publish, the publish first shows
you that as a [change made in CommCare HQ](#changes-made-in-commcare-hq). Publishing over it takes
the language out of the app there, so the profile is then held to the app's languages too.

### Data in place

Two things go on the project space before the app's content does, because the
app reaches for them by name while somebody is using it. Content that arrived
first would install and then misbehave.

This step only appears when your app has one of them.

The first publish to a project space makes an empty app there first, named for
your app, then puts the lookup tables and places in place, and then fills the
app in. The empty app holds nothing that reads a table or a place, and CommCare
HQ makes no version of it. If the publish stops anywhere between making the
empty app and filling it, the empty app stays on the project space, and your
next publish there fills it rather than making a second one.

CommCare HQ sets a new app's CommCare version itself, so Nova checks the empty
app's version before it puts a table or a place there. If it is below 2.57, the
publish stops with nothing of yours on the project space but that empty app.
Once you raise its version in CommCare HQ, the next publish fills it, and the
raise isn't a change Nova asks you about first.

**Lookup tables.** If your app reads any [lookup tables](/docs/project-data),
Nova puts them there and replaces their rows with the rows in Nova. Tables your
app does not read are left alone.

Nova checks the data and who can receive it just before each lookup workbook
goes to CommCare HQ. If either changed, you can review the table in Project
data and publish again. Edits to a table that’s already uploading can resume
when its upload finishes.

If Nova cannot reliably read the tables already on your project space, it
stops before sending data. Check your CommCare HQ connection, then publish again.

Most tables go in one workbook upload. A table a workbook can't carry exactly,
such as one whose export tag is `types`, a value that starts or ends with a
space, or a value list with an empty entry, goes through CommCare HQ's table
and row resources instead, one change at a time. That way works for a table
shared with every worker that has no indexed columns. Nova remembers which row
on CommCare HQ is which of yours, so publishing again sends only the rows you
added, changed, moved or removed, and nothing at all when the table is
unchanged. Every app in your Project that reads the table shares that record.

If a change's answer gets lost on the way back, Nova reads that row in CommCare
HQ before it sends anything else to the table, and waits a few minutes where
the change could still arrive. If a row someone else added or changed is there,
or a new row appeared that Nova can't name, the publish stops and names the
table so nothing is written over it. Each later publish reads the table again
first, so once the row is gone or put back in CommCare HQ, publishing again
picks up from there. Changing a table's columns after it's there isn't
something these resources can do safely, so Nova asks you to give the table a
new export tag instead: the next publish puts it there as a new table and
leaves the old one as it is. The CommCare HQ app file can't carry these
tables, since it uploads a workbook: publish from Nova to put them there.

A table that's already on the project space from a workbook stays in one
there, since Nova can't tell its rows apart in those resources. If it now holds
something a workbook can't carry, such as a value that starts or ends with a
space, the publish names it, and you can change those rows in Project data or
give the table a new export tag so it goes there as a new table.

A publish stops before it sends anything when a lookup table with the same tag
in CommCare HQ holds something Nova can't keep yet: field properties, row
attributes or rows limited to certain users. Giving your table a new export tag
in Project data lets Nova publish its own and leave CommCare HQ's as it is.

Where the project space's plan doesn't include Lookup Tables, CommCare HQ takes
none of your app's lookup tables and Nova stops before it sends the app's
content. A first publish leaves an empty app there. Once the plan includes
Lookup Tables, publishing again sends the tables and fills the app in.

**Places.** If your app has an [organization](/docs/organization), Nova creates
and updates its places there, working down from the top so each one can name the
place above it. It sends every place that is not archived, along with whatever
place information you filled in.
Nova keeps other information already stored on those places, including fields
this app does not use. Clearing one of your app's fields clears it on the
project space too.

If a connection drops while data is being sent, Nova reports what it could
confirm and holds back the app's content. Some data may already have arrived. Publishing
again checks what is there and may ask you to confirm which existing resources
Nova can update. If CommCare HQ names an invalid row or place, that detail stays
with the refusal so you can fix it before retrying.

**If something of that name is already there and Nova did not make it**, Nova
stops rather than write over it, and names it. CommCare HQ matches a lookup
table on its export tag and a place on its site code, and two things could be
true: it is yours, from before you used Nova, or it belongs to something else on
that project space. Nova cannot tell, so you choose. Tick the ones that are
yours and publish again, and Nova will keep them up to date from then on. Leave
one unticked and it stays exactly as it is. Closing the dialog or changing the
destination clears those choices. You can confirm them again on your next attempt.

**Nova cannot make organization levels**, so if your places stand at levels the
project space does not have, or your organization skips a rung the project space
insists on, publishing stops and names each place. Add the levels on CommCare HQ
first; the list Nova gives you after a publish has them all, in order.

**Renaming a table's export tag makes a new table on CommCare HQ.** The old one
stays where it is, so nothing anybody else built on it breaks, and Nova names
it so you can delete it there when you no longer need it. Archiving a
place works the same way: Nova stops sending it and names it, and the one on
CommCare HQ stays exactly where it is, because CommCare HQ's API has no way to
archive or delete a place.

### On CommCare HQ

Your app is now on the project space. It is not something workers can open yet.

For an app you brought in, this card is there from the start, and its first
publish updates the app it came from.

The first time you publish an app you brought in, Nova lists what will differ
in CommCare HQ: what workers will notice, and what changes only in how CommCare
HQ stores the app. The same list is shown before you bring the app in.

Publishing again **updates this same app in place**, name included, so the
project space keeps one app that tracks what you build in Nova. There are two
exceptions. If the app was deleted on CommCare HQ, Nova tells you so when you
try, and publishing once more makes a fresh one there. A phone that has the app
from a CCZ still points at the deleted app until it takes the next CCZ through
Offline Update. And if someone stopped publishing this app to that project
space, the next publish makes a new app beside the one that stays.

Each publish keeps every menu's and every form's ID in CommCare HQ. So anything
there that opens a form by its ID, such as an SMS keyword or a scheduled
message, keeps opening it. An app you brought in keeps the IDs CommCare HQ gave
it, in the project space it came from. In any other project space Nova makes a
new app with its own.

CommCare HQ shows each submission under its form's name, in your app's default
language. Saving a form in CommCare HQ's form builder makes the next version
made there send that form to devices again, even when nothing in it changed.

Nova writes every expression in one standard spelling, with one space after each
comma and on each side of an operator. An app whose forms Nova wrote before it
did so sends each form's expressions in that spelling at its next publish, once,
so CommCare HQ keeps a new version of each form and menu they touch. Nothing a
worker sees or collects changes because of it, and CommCare HQ's form builder
shows the new spacing.

CommCare HQ's data dictionary lists the case properties your forms' case
operations write, from the publish that sends them.

If a status check overlaps a new publish, Nova keeps the new publish's status.
Answers about the earlier version cannot replace it.

Before it sends your app's content, Nova reads the CommCare HQ app it is about
to fill or update, and keeps destination-specific behavior it does not own. If
that app cannot be read safely, Nova sends none of the app's content instead of
guessing what to keep. On a first publish the empty app it made is already
there, and your next publish fills it.

In your app's settings you can show workers their saved forms and their
incomplete forms. A publish writes both to CommCare HQ.

Your app also states fifteen more of CommCare's app settings, each at the value
a phone uses when the app sets none, so a publish changes nothing a phone does
from install. A publish writes each of them only where CommCare HQ holds no
value for it, so a setting someone chose on CommCare HQ's app settings page
stays as they chose it. A CCZ always carries the app's own values. Three of
these settings are also a worker's own choices on their phone: fuzzy search,
automatic updates and text to speech. Once CommCare HQ holds them, each app
update on a phone sets them back to the app's values, as it does for any app
whose settings were saved on CommCare HQ.

If a publish is interrupted just after CommCare HQ makes the empty app and
before Nova records it, Nova doesn't know that app, and the next publish makes
another. That leaves an extra empty app named for your app, which you can
delete in CommCare HQ.

**Your app's logo isn't sent with the app.** CommCare HQ shows a logo in apps
built there, and in Web Apps, only once it is added with its own uploader, in
the app's settings. After a publish that has a new logo, Nova offers it to
download, with a link to the app, so you can add it there. That takes a plan
with the Custom CommCare Logo Uploader (Advanced or Enterprise); on other plans,
apps built on CommCare HQ carry no logo, and Web Apps shows its own icon.

Media goes after the app's content. A version made in CommCare HQ between the
two installs and shows no images until the media lands, so make the version
once the publish has finished. If another publish has already updated the app
when Nova is ready to send the media, Nova keeps the later publish's files and
shows a message on the earlier publish.

Nova checks that it can read the media files in your Project before it sends
the app. If CommCare HQ accepts an earlier version while Nova updates the app, you can use **See what changed in CommCare HQ** to compare it with the current version before publishing again.

If a file changes after CommCare HQ accepts the app, Nova checks what now occupies each destination before sending the files. If it can’t verify a destination, the app stays published and its files wait for your next review.
You can review changes from CommCare HQ to see which pictures and sounds it holds.

Nova reuses each file that project space already holds for this app and sends
the rest. After the upload, Nova checks that each file it sent arrived. If the app
arrives but its media upload cannot be confirmed, Nova keeps the published app
and reports which media still needs attention. Publishing again updates that
app and retries its media upload. When CommCare HQ accepts the media but Nova
cannot confirm that processing finished, the warning says so. You can check the
media in CommCare HQ before deciding whether to retry.

Nova never deletes anything on CommCare HQ. So when a publish stops pointing at
something it put there before, whether that is an app it replaced or a lookup
table whose tag you renamed, Nova names it and leaves it to you. A table
is named by the tag it still carries on CommCare HQ, which is what you will
look for on the Lookup Tables screen. Nothing appears here for a table you
simply republished, only for one nothing in your app points at any more.
If a later publish uses an earlier resource again, Nova removes it from this
list. Each unused resource appears only once.

#### Where CommCare HQ keeps your case changes

The first time Nova publishes a form, it records where CommCare HQ keeps each
of its case changes, so publishing again keeps them there and your exports keep
their columns. If a change you make can't stay there, Nova says what moves
before it saves, and undoing the change puts it back. When a project space's
plan doesn't include Save to Case, Nova offers to move the case changes that
don't need it, and the move applies wherever the app is published. See
[Where CommCare HQ keeps each change](/docs/case-changes#where-commcare-hq-keeps-each-change).

### Version made, and Released

On CommCare HQ, open your app and go to **Releases**. Choose **Make new
version**, wait for it to finish, then **star** the new version to release it.

Nova cannot do these two for you. CommCare HQ accepts an API key for putting an
app on a project space but not for building or releasing one, so these are yours
to do there. Nova watches for them instead.

CommCare HQ validates the app again while it builds. If it reports errors there,
they are about the version you just published: fix them in Nova and publish
again.

### Ready for workers

Once a version is released, Nova checks that it actually serves the file a
device installs from, with a valid reference to that released version. An empty
file or sign-in page leaves the version **Released**, with a note that Nova
couldn't confirm it is ready. Choose **Check status** to try again.

The **Open in CommCare HQ** link appears as soon as the app is there, and it
goes to the app's page for you to work on. It is not the link workers use.


## Changes made in CommCare HQ

If you publish the same app to two project spaces, each keeps its own
comparison. You can refresh settings in one space while an edit in Nova is
still waiting to be published. Your next review in either space shows the
changes since the version that space received.

If you've reviewed a picture getting a new name or two file paths becoming one, an unrelated edit in HQ keeps that choice. Nova asks again when the change affects a different question, choice or language. This includes workers who see the default picture because their language has no picture of its own.

A publish can remove an unused file reference in CommCare HQ, including on an app Nova has published before. Nova shows the file's path in the app. If a later save puts a different file at that path, Nova asks again and says that CommCare HQ holds a different file there. To review these changes, open **See what changed in CommCare HQ** on this project space. The review names unused file references the publish would remove. Bring in the review to update the Publishing card, then publish when you're ready. If Nova can't verify the earlier reading, a Project admin or owner can choose **Stop publishing here** for this project space. Once any publish in progress finishes, you can bring the HQ app in as a new Nova app. You can also publish the current Nova app to a different project space. Stopping here affects only this project space. When there are too many changes to show every file in the publish dialog, you can open the full review and choose which version to keep after reading the complete list. Nova checks the file list even when the app sends no new files. If CommCare HQ saves the app while Nova is reading its files, Nova stops before uploading the app. Publishing again checks what changed. If CommCare HQ can’t show the list, you can try the publish again when it’s available.
If HQ adds the same picture to two places under different filenames, the app can
keep showing it in both places under one filename when you bring in the changes.
Publishing the app as it stands in Nova can remove both references. Nova shows
the filenames each choice would remove.


Before your first publish to the space an app came from, its Publishing card
shows which HQ settings that publish will change. Bringing in a later HQ save
updates the card, even when the forms stay the same. If someone puts a
setting back in HQ, bringing that save in removes its warning. This includes
a picture or sound saved in HQ that the app no longer uses. **Refresh from
CommCare HQ** can pick up settings such as fuzzy search directly. When a
change affects the Publishing card, Nova offers to review it with you. A
publish also pauses if it would remove a file reference someone added in HQ
since that review. If
publishing would change the Web Apps switch, Nova asks you to confirm it.

If you restore a deleted app and it can publish to the same CommCare HQ app
again, Nova remembers the version it last sent there. You can start a fresh
review to see what changed while the app was away.

Each publish remembers what CommCare HQ held just after it: the app, each
lookup table and each place. An app you brought in from CommCare HQ starts from
what it held when it came in. Before the next publish sends anything, Nova reads
them again. If something your app publishes isn't the same as when Nova last
published it, Nova stops before sending anything and lists what changed, such
as a form in a menu, the app's name, a table's columns or rows, or a place's
name or site code.

**When the app itself changed, you can bring the change in.** Nova lists what
changed by menu and form. If nothing in this app has changed in Nova since
then, choose **Bring in these changes**: they come in to this app, and
everything else in it stays as it is, including what CommCare HQ never holds,
such as notes, personas and review marks on translations. The app reloads with
the changes in, and the dialog opens again to say so. Your next publish then
goes ahead as usual; if CommCare HQ's version holds a few things Nova writes
its own way, the Publish dialog lists what that publish changes first.

If the changes give cases to the place at a level below their owner and the
places in CommCare HQ have two such places, or none, below an owner, the list
asks who owns those cases, as [bringing an app in](/docs/bringing-in-from-commcare-hq)
does. You can give them to the worker who fills in the form, or change the places
in CommCare HQ and check again. Giving them to the worker is a change your next
publish makes in CommCare HQ too, and the Publish dialog lists it.

**When the app changed in both places, you choose one.** Nova shows a second
list, **What changed in Nova since then**, and doesn't combine the two. **Use
CommCare HQ's version** takes CommCare HQ's changes and removes the ones listed
under Nova, and Nova can't put those back, so **Copy both lists** is there if
you'd like a record first. If you renamed a case property in Nova since then,
you can rename it back if the name still identifies the same property, then
check again. Its saved case values move with it. If a name was reused, Nova lists the
recorded moves. You can check which values the properties hold before deciding
which version to keep. **Publish over CommCare HQ's changes** sends
this app's version and replaces what changed there. An admin or owner of the
Project can also choose **Stop publishing here**, which leaves the app in
CommCare HQ as it is; a later publish there makes a new app. You can also close
the dialog and decide later.

**A picture or sound replaced in CommCare HQ is a change like any other.**
It's listed with the rest. Bringing the changes in takes CommCare HQ's file,
and Nova sends its own file back only when you choose to publish over the
change.

**Some changes in CommCare HQ move only where it keeps something**: the case id
a form files the cases it makes from an answer under, a form's id, or the path a
file is kept at. Nova lists those too, and follows them when you bring the change
in, so your next publish keeps CommCare HQ's version and a key a worker enters
again still reaches the case it reached before.

**Nova also looks when you open an app.** Once the builder is up, if you can
edit the app, Nova checks in the background whether it changed in CommCare HQ,
using your own CommCare HQ connection. Nothing waits on it. If something
changed, **See what changed in CommCare HQ** appears in the builder's header.
Where more than one project space changed, it opens **App setup → Publishing**,
where each card that changed says so and offers **See what changed**. If Nova
can't reach CommCare HQ, it says nothing, and your next publish checks again.

**When Nova can't bring a change in**, it says why and what you can do about
it. Where the change is still there, you can publish over it or stop
publishing there.

**You can also publish over a change.** Tick **Publish over this** beside
each one you're happy to replace with this app's version, then choose
**Publish over these changes**. Leave one unticked and nothing is sent. Each
tick is for the state Nova showed you, so if something changes again in
CommCare HQ before you publish, Nova asks again. Closing the dialog or changing
the destination clears the ticks. A change to a lookup table or a place is
decided this way.

**You can also stop publishing here.** The app in CommCare HQ stays as it is,
this app stops publishing to it, and it can be brought in to Nova again as a
new app once any publish to it that was running has finished. If you publish to
that project space later, Nova makes a new app there. A Project's admins and
owners can do this. The stop is for the app the card showed you: if this app
has started publishing to a different app there since, Nova stops nothing and
asks you to have another look.

Once publishing stops, the project space's card in **App setup → Publishing**
says who stopped it and when, and links to the app it left in CommCare HQ. If
someone has since brought that app in to Nova, or another Nova app publishes to
it, the card says so and leaves the link out, since that app is the way to it
now. Any worker passwords Nova showed on the card stay there until you leave the
page, and Nova makes no more workers on that project space.

**A save in CommCare HQ can leave the app working the same way.** For example,
opening a form in the form builder and saving it can look like a change. When
you review it, Nova reads the app again. If it reads as the same app, Nova
records the save so your next publish can go ahead. Where Nova can't
bring changes in from that project space, such a save is listed like any other
change.

Some changes read a little differently:

- **Nova couldn't confirm what its last publish left.** CommCare HQ may have
  been unavailable when Nova read it back, or someone may have saved the app
  while Nova published it. When CommCare HQ saves the app a second time only to
  remove the unused picture or sound references Nova expected, Nova recognizes
  that save as part of the publish and says nothing. Your publish
  landed. If Nova could read the settings at the version CommCare HQ reported,
  your download, Preview and the Publishing card still use those settings.
  Nova asks before writing over the app on the next publish.
- **A lookup table CommCare HQ no longer has.** Publishing makes it again.
- **A lookup table with a new tag in CommCare HQ.** Publishing makes a new
  table under your tag and leaves that one where it is.
- **A place CommCare HQ no longer lists.** It was archived or deleted there.
  Publishing makes it again if it was deleted. If it was archived, CommCare HQ
  refuses the publish while the place stays archived there.
- **The app changed while Nova was putting its lookup tables and places in
  place.** Nova stops before sending the app's content. Publishing again checks
  what is there now and lists anything that changed.
- **A publish interrupted after CommCare HQ took the app's content and before
  Nova recorded it.** The next publish lists the app as changed, though the
  change is Nova's own. Publishing over it sends this app again.

**A publish keeps what was set in CommCare HQ for things Nova doesn't hold**: UI
translations, add-ons and Auto Capture Location, along with the app settings
above that Nova only writes where none is set. It replaces what Nova holds: the
app's name, each language's name, and the saved and incomplete forms settings.
It also sets the Web App setting from where the app runs, asking first where it
differs ([A note on Web Apps](#a-note-on-web-apps)). What it keeps is what
CommCare HQ held when the publish last read your app.

A publish reads your app in CommCare HQ and then writes to it, and CommCare HQ
gives Nova no way to write only if nothing changed in between. So a change
saved in CommCare HQ in the moments a publish runs can slip past Nova's check:
a setting can go back to what it was, or Nova's value can replace it at this
publish or the next, with no question asked. Saving in CommCare HQ when no
publish is running avoids this. If a save and a publish did overlap, the app in
CommCare HQ shows what is there now, and you can make the change again.

**After a publish that replaced the app without knowing it unchanged**, such
as one over a change to the app you chose to publish over, Nova adds a note to
the result. CommCare HQ keeps each form's last check for up to 7 days. If a form had failed
that check in CommCare HQ before this publish replaced it, App Preview there can
keep refusing to open the app for that long, with the old error. Making a new
version in CommCare HQ checks the app afresh. Saving the form once in CommCare
HQ's form builder clears the old check, and Nova's next publish then asks before
replacing that form.

## Lookup tables and places managed in CommCare HQ

Before a publish to the project space that manages them, Nova checks the lookup
tables CommCare HQ manages for the app. When nothing the app reads is missing,
Nova sends none of them there and refreshes its own copy. When a table changed
in CommCare HQ in a way the app depends on, such as a column it reads being
removed, Nova stops before sending anything and shows you what changed. Nova
never changes the places CommCare HQ manages in that project space either.

Any other project space you publish to gets Nova's copy of those tables and
places, as tables and places Nova made there. [Project data](/docs/project-data) and
[Organization](/docs/organization) say what "managed in CommCare HQ" means for a
table and for places.

## What stays as it is in CommCare HQ

Some of an app's settings are CommCare HQ's to keep: how often phones update,
fuzzy search in case lists, your rewording of CommCare's own screens, your
Android logos and a few more. Nova doesn't change them when it publishes, so you
can keep setting them on the app's Settings page in CommCare HQ. The Publishing
section lists the ones your project space holds differently from a new app,
with the date Nova last read them, and **Refresh from CommCare HQ** reads them
again. A CCZ you download for that project space follows them. Two things it
can't carry, your Android logos and a practice mobile worker, it tells you about
when you download it, and so it does for wording or a setting stored in
CommCare HQ in a form a CCZ can't carry. A custom base URL is the one setting a
CCZ never follows, because it decides where phones send workers' passwords and
forms. While your project space's app holds one that points somewhere other
than the server the app is published on, there's no CCZ for it, and your
workers can install the app from CommCare HQ. An app you brought in from CommCare HQ keeps these
settings exactly as it had them, including the ones it never set. Nova fills in
its own defaults only on an app it created there.

## Making workers

Publishing sends an app. It does not create anybody an account, because handing
out a credential is not something to do by accident.

Once the app is on a project space, that project space's card in
**App setup → Publishing** has a **Workers** list, one row per persona. Tick
the ones you want, adjust the username Nova suggests, and choose Make workers.
Each account carries that persona's worker information and the places it
stands in.

**Every new account comes with a password, shown once.** Copy them before you
leave the page. Nova keeps no copy, so a password you lose has to be reset on
CommCare HQ.

Ticking a persona that already has an account brings that account into step with
what the app says now, rather than making a second one. Its password is
untouched. An account Nova made follows its persona entirely: worker
information the persona has no value for is cleared, and so are its places when
the persona stands nowhere. An account you had Nova take over changes only where
its persona says something: the worker information the persona or its role has a
value for, and its places when the persona stands somewhere. Everything else on
it stays as CommCare HQ holds it.

Occasionally CommCare HQ breaks off partway through making an account without
saying whether it made one. An unreadable response or a connection that times out
can leave the same uncertainty. Nova shows that row with the other passwords, marked
**Account unconfirmed**, and keeps it on screen through everything you do next. Copy it
anyway: if the account turned out to be real, that is the only password it will
ever have. Then look for that username on your project space. If it isn't there,
choose Make workers again. If it is, give CommCare HQ a moment to notice its own
new account first, and then Make workers offers you the one already there.

Passwords stay with their own server and project space. If more than one attempt
is unconfirmed, Nova keeps every possible password for that username. Taking over
an account confirms that it exists; a password Nova has not verified is marked
**Password unconfirmed**. **Copy all** includes these labels. **I have this**
removes only the selected candidate from this page. If the same username now
belongs to a different account, the previous password becomes unconfirmed too.

If CommCare HQ stops responding during a publish, Nova stops waiting and keeps
the last confirmed result. A timed-out upload may still have changed the project
space. The publishing result explains what Nova could confirm before a retry.

If the connection to Nova breaks before the answer reaches this page, some workers
may already exist without their passwords reaching you. You can check their
usernames in CommCare HQ before trying again. A password that never reached this
page will need to be reset there.

If a lookup table you previously took over is deleted in CommCare HQ, the next
publish asks before it makes the table again, and recreates it once you say so.
Nova records the new table as created by Nova and keeps the earlier takeover in
its history.

Four things Nova will refuse rather than guess at:

- **A username somebody already has.** Nova shows you the account and takes it
  over only if you say so for that exact one. A shared name is not evidence it
  is yours.
- **A worker at a level nobody confirmed takes workers**, where the app's places
  are managed in CommCare HQ. CommCare HQ doesn't tell Nova which levels take
  workers, and its own pages refuse a worker at a level that doesn't. Nova lists
  each level with the personas who would stand there; you can check
  **Organization Levels** in CommCare HQ (the **Has Users** column), tick the
  levels that take workers and make the workers again. If another check stops
  you there, the levels that still need your answer keep their ticks. Once
  those checks pass, Nova remembers your answer for that project space. You
  can withdraw it from the project space's card to have Nova ask again the
  next time someone makes workers at that level.
- **A persona missing worker information you marked required.** CommCare HQ will
  not save a worker without it. Publishing still works; only making the worker
  stops.
- **A persona standing in a place that is not on the project space yet.**
  Publish the app there first, which puts the places there.

Nova never deletes or retires a worker, because CommCare HQ's own delete also
deletes every case that worker owns. Remove a persona and its account is
reported as left behind, still there for you to deal with on CommCare HQ.

## What you set up by hand

Some of what your app needs lives on the project space rather than in the app,
and CommCare HQ has no way for Nova to create it. After you publish, Nova lists
exactly what those are, with a link to the right page on **your** project space
and the values already filled in.

- **Worker information.** One field per piece of information your workers carry,
  on the project's user-data page. Do this before you make workers: CommCare HQ
  validates a worker's information against these fields.
- **Roles.** Nova does not create CommCare user roles. A worker Nova makes has
  no role until you give it one.
- **Organization levels.** The rungs of your organization. Create these before
  you publish, because every place names the level it stands at and CommCare HQ
  will not take a place whose level is not there. Where your places are managed
  in CommCare HQ on that project space, the levels are already its own: the notes
  list them, say which ones you confirmed take workers, and Nova asks before it
  makes a worker at any other. An answer about a level that has since left the
  organization stays listed until you withdraw it.
- **Place information.** One field per piece of information your places carry,
  on the project's location-fields page. Nova sends the values with every place;
  a field the project space has not defined is kept as loose data that nothing
  on CommCare HQ can validate or filter on. Places managed in CommCare HQ carry
  the information CommCare HQ holds, so this step doesn't appear for them.
- **Automations.** Each rule or alert, created on the relevant page. Changing an
  automation in Nova does not change one you already made on CommCare HQ.
- **Finding cases by distance.** CommCare HQ's search measures distance only on
  a case property its Data Dictionary marks as GPS, so a search that finds cases
  within a distance finds none there until each property it measures has that
  data type. Nova names each property, its case type and the searches that read
  it. The Data Dictionary comes with the Advanced and Enterprise plans, and
  Preview finds these cases whatever the type. The import file's README holds
  the same step.

These notes are generated fresh every time you look at them, so they always
match your app as it is now.

## If something goes wrong

A publish that could not finish says so plainly, names what stopped it, and
remembers where it stopped.

What to do next depends on where it stopped, and Nova says which:

- **Before the app's content reached CommCare HQ** (a connection problem,
  something in the app itself, or a table or place Nova would not write over):
  fix it and publish again. A publish that stopped on the data never sent the
  app's content, so trying again picks up from there. If it was the first
  publish to that project space, it left an empty app there, which the next
  publish fills. Places go out in groups, one level at a time, and each
  group either lands whole or not at all, so a publish that stopped partway left
  the groups above it in place and the next one carries on from there rather
  than making a second copy.
- **After it got there** (a version that would not build, a release Nova could
  not confirm): the app is already on your project space. Sort it out on
  CommCare HQ, then choose **Check status**; there is no need to publish
  again.

### When a publish asks for place IDs

CommCare HQ imports external IDs through its organization workbook. If a place needs its ID set on a destination, **Download place ID workbook** prepares a private file for that project space. Open **Organization** in the named space and import each workbook in the download. Check the affected places, confirm the import, then publish again. Nova reads the saved IDs there before it sends the app. A different destination has its own place IDs and its own file.

If a workbook would change another value in that space, the publish names the place and field. Set the exact ID on that place in CommCare HQ, then publish again. When the ID and destination data already match, Nova carries on immediately.

## Updates to review

When Nova changes how it stores, checks or writes apps, where they run, or where
workers go after a form, an app it changed shows an update to review in the
builder's header. Open it to see
what changed in the app and what the next publish to each project space does
once. For example, links to a project space that you already shared keep
working, and new ones are ready after the next publish there.

The notes about a project space also show on its card under Publishing, because
that is where you decide the next publish. They stay there after you dismiss the
update, until a publish to that project space has happened since. Dismissing an
update hides it for you alone; other members of the Project see it until they
dismiss it too.

If Nova read a project space with your saved CommCare HQ key during such a
change, to keep its apps' IDs steady, your home page says which project spaces
and when, even where you no longer reach the app.

## A note on Web Apps

Nova sets the app's **Web App** setting on CommCare HQ from where the app runs,
at every publish: on for an app that runs in Web Apps, off for one that runs
only on Android. If the setting there differs, because you changed where the
app runs or someone changed it in CommCare HQ, the publish asks you before
changing it, and says which it was. CommCare HQ makes a new app with Web Apps
on only where the project space's plan includes it, so a first publish of an
app that runs in Web Apps to a plan without it stops after making the empty
app. You can then set the app to run on Android only, if its content allows it,
or confirm the plan again once it includes Web Apps, and the next publish fills
in the same app.

## Sharing deep links

An app can have named entry points for modules, case lists, and forms. After
publishing and releasing the app, its Publishing card lets you generate and
copy a link. Nova checks the released entry point each time you generate or
copy it. Cases for these links use IDs from that CommCare HQ project space.
When the app or destination changes, Nova clears earlier links and check messages.
See [Deep links](/docs/deep-links) for Preview testing and release behavior.

## Downloads

**A CommCare mobile app file (CCZ) is made for one project space the app is
published to.** It signs workers in there and sends their forms there. When
your app is published to one project space, the download is made for it; with
several, you choose which one. An app that isn't published anywhere has no CCZ
yet, so publish it to a project space first. An app that runs in Web Apps only
has no CCZ either, because a CCZ installs an app on Android phones. If its
workers use phones too, you can set it to run on Android as well, in App
settings. A CCZ always signs workers in on the server the app is published on,
so a project space whose app in CommCare HQ has a custom base URL pointing
somewhere else has no CCZ while that setting is there. The list of project
spaces shows such a space with the address it points at, and you can't choose
it; your workers can install the app from CommCare HQ instead. If Nova learns
of the setting only as you download, the download says so and the list shows
it from then on.

A newer CCZ for the same project space keeps every form's identity, so a phone
that updates to it reopens the forms a worker saved incomplete.

A CCZ needs CommCare 2.57 or later. Each project space's CCZ is its own app to
CommCare: a phone that already has it won't install it a second time, and a
CCZ of the same app for another project space installs beside it. A newer CCZ
for the same project space reaches that phone through Offline Update, on
CommCare's update screen. Offline Update replaces the open app with the file it
is given, whichever app that file was made for, so a CCZ for another project
space would point that app at the other project space.

If a phone installs your app from CommCare HQ and also from a file downloaded
here, CommCare keeps them as two separate apps.

A CCZ of a Connect app records the worker's location with each form, as
CommCare HQ's build of the app does.

**The CommCare HQ app file is a ZIP** you can import by hand. It holds the app,
a README with the steps for importing it, and, where your app has them, its
lookup tables and its media. After the download, Nova shows the same steps. You
can choose a server for it so that links to case attachments open there.

Neither download checks a project space's capabilities; publishing performs
that check against the destination.
