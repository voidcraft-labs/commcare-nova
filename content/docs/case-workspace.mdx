---
title: Case search, results, and details
description: Configure how people find, compare, and open cases in the Nova builder.
---

The case workspace controls how people find a case, compare the results, and
understand the case they open. It is split into three focused tabs so you can
work on one part of that experience at a time.

## Design the journey directly

| Tab | What you configure |
| --- | --- |
| **Search** | The action people use to continue, plus any questions they can answer to narrow the cases themselves. |
| **Results** | Which cases are available, the information people scan, and which cases appear first. |
| **Details** | The information people see after opening a case. |

Each tab is a picture of that part of the app, not a list of technical
settings. Add information in the canvas, drag it into place, and select a row
when you want to change its properties.

The tab strip stays in place while you work. Only the active tab's body
scrolls, and each tab remembers where you were when you switch away and back.

### Grouping details into tabs

Under **Details**, **Group fields into tabs** lets you give related information a title, such as “Household” or “Visit history.” Each field belongs to one tab. Moving a tab moves its fields together. You can give a tab a display condition when only some cases need it. The condition reads the case the worker opened.

A tab can show the selected case, its open child cases or rows from a Project
data table. For example, a household can have a **Members** tab that CommCare
shows with one row per open member. A tab can show child cases of a type a form
of this case type adds, such as members a household form adds, which is what
CommCare HQ keeps when the app is saved there. A table-backed tab can add fields from the
table when you choose it. Those fields show the value from each row. The
running app shows a tab of records by its title for now, without its records.

**Save tabs** applies the layout in one change. You can preview it by opening a case in the running app. To return to one list of fields, choose **Edit tabs** and **Show fields without tabs**.


### Keeping case information visible

A Results tile and a Web Apps Details tile have separate placements. You can
arrange fields differently after someone opens a case. Android shows the
Details fields as labeled rows. A Results tile can also give ten fields fixed
image and text positions.

**Case context above a form** can show one value, this menu’s Results tile
or a tile from another menu for the same case type. With expandable Details,
selecting a case opens its form. The worker can open the tile to see more.
For example, a visit can use a directory menu’s layout while continuing to
show the person chosen for this visit.

## Search with an Android app

In **Results**, **Add lookup** connects a case list to a companion app on the
worker’s Android device. Set its Android action, lookup name, the text it
receives, and the response names it can return. Each named value can be
fixed text, the worker’s username, or the worker’s ID. The Android toolbar
calls the action **Scan Barcode**. You can attach a Project image to identify
it. When a companion sends the primary text answer, CommCare searches the
current list. If it declares a text response without a primary value,
CommCare uses the first returned value in your response-name order.

In a list with rows, **Show match confidence** adds a confidence column. Use this for a
companion that returns keys with confidence levels. Android matches record IDs
by default. When the list uses one record type, you can also choose a custom
text property that holds the companion’s keys. Each available case with a matching
value appears with the same confidence, even when several cases share that value.
A blank returned key can match cases where the property is blank or missing.

In an Android-only form that opens directly from one case list, a calculation
can read **Companion lookup count**. It counts distinct keys the companion
returned, including keys outside the worker’s case list. The value is blank
when there is no identification response and zero when the companion
returns an empty result. Browser Preview leaves the value blank.

You can open the companion when the list first appears or let workers open
it when they need it. The worker’s device needs the companion installed,
and the project space needs to support Android case lookup. In browser
Preview, the action explains how to check it on a device. Web Apps opens the
ordinary case list.

## Choose a parent first

In Results, **Choose a parent first** lets people pick a record from a menu for
a different record type. They then see the records linked to their choice.
For example, a clinic list can lead to the patients linked to that clinic,
even if this app usually registers patients under a household.
**No parent selection** opens a flat list that can include records with or
without a parent. Other Results filters still apply.

If the module also has a registration or survey form, its forms show first,
and people choose the parent once they pick a form that opens an existing
record. Picking the parent moves straight on, without the parent list's
details, in Web Apps and on Android alike.

This choice is separate from placing a module in a submenu. It changes how
people find existing records; it does not link new registrations to a parent.
A form on the selected parent can create a child by saving answers to the
child record type, including captured evidence.

A rule that runs after a case is chosen in an earlier menu can read that case.
In **Cases available**, a search field's rule or a form's display condition,
choose **The case chosen in** that menu, then the case itself or one of its
properties, for example to search only the households of the village chosen
first. Nova keeps the menu itself, so renaming it keeps the rule. In a menu
whose forms read the search, a case the worker found but didn't already have joins
their cases when they choose a form, so until then a form's display condition
reads its properties as blank, on a phone, in Web Apps and in Preview alike.

## Arrange information in the canvas

Under **Other record types**, choose any other kind of record with a menu in this app. A worker can open those records from the same list, whether they browse their device or search. A follow-up form saves changes to the record they chose and keeps its type.

Under **Search filters**, you can include another record type in the search request alone. A form that reads the search can use those matches. They count toward the project space’s result limit and only appear as choices if the menu also offers their type.

In the search settings, **Record ID to follow** includes the record named by a property on a match. **Related records** lets you include the linked records used by details or the whole hierarchy. A detail can read a related record, including a closed one, without offering that record as a choice.

Choose **Add search field**, then select the case information people should be
able to search. Nova puts Case name first as a useful suggestion, but does not
choose a property for you. The new field gets a suitable field type and match
behavior after you make that choice. Search fields can then be dragged into the
order people should answer them. Results and Details use the same direct
arrangement: the row you move is the row the person using the app will see in
that position. You can also focus a drag handle and use the arrow, Home, or End
keys.

Results and Details have separate arrangements. Moving an item in Results does
not move it in Details, so each screen can follow the reading order that makes
sense there.

The normal canvas stays focused on what people will see. **Add information**
always asks what you want to show; it never picks a case property for you. If
the same information was already set up for another screen, choosing it keeps
that label and formatting. Previously configured information stays mixed into
the same familiar groups instead of becoming a prominent “hidden fields”
concept. Less-common choices sit quietly at the bottom: **Calculated value**
for information derived from other values, and **Show information another
way** when the same property needs a second label or format.

To show a detail such as the current worker’s district beside each case, choose
**The worker’s record** under **From**, then choose the information to display.
Every row reads that worker’s record. For a case’s **Owner**, choose **Name** to
show the name of its case-sharing group or the current worker’s username for a
case they own. An owner outside the worker’s synced groups appears blank.
**ID** shows the stored owner identifier.

Calculated values and filters using `today()` follow your local day in Preview,
just as form questions do. On a device they use the device’s local day. This
keeps a case due today from appearing overdue because the server is already
on tomorrow’s date. Search rules, and Results filters that CommCare HQ's server
runs during a search, use the same day, the worker's own, so a search and the
list it opens agree on what today is.

A calculated value can use `here()`, the worker's current location
(**Where you are now** in its value menu), for example to show where the
worker is, or to mark the cases within a set distance of them with
`within-distance`. It works in an app that runs only on Android, because Web
Apps never shares where the worker is with a case list. In Preview playing
Android, your browser asks to share your location the first time a list on
screen needs it. Until it does, those values stay blank, as they do on a device
that has no location yet. As on an Android phone, the value holds four numbers,
the latitude, the longitude, the altitude and the accuracy, and the list updates
after you move more than 30 metres. Nova uses your location only to run the list
and the case's details, and doesn't save or log it.

Select a Results or Details row, then use **Hide from Results** or **Hide from
Details** at the bottom of its properties when you only want it off that
screen. Hiding is reversible. An item hidden from Results stays part of the
list, so the list's search still matches its value; a tile works a little
differently (see [Lay results out as a tile](#lay-results-out-as-a-tile)).
You can turn **List search matches this** off for a hidden field, and then
only Details shows it and Default order can't sort by it.
**Delete information** removes that display
setup from both screens and Default order, if used, but never deletes the case
property or saved case data. Results must keep at least one item so people can
recognize and choose a case. Search fields can be removed from the bottom of
their own properties. Removing the final field removes the questions people
can answer, but an intentionally configured Search action can remain.

If another rule uses that field's answer, Nova does not silently rewrite or
discard the rule. The removal dialog groups every place the answer is used and
opens the exact spot, a condition in Results, another search field's condition
or starting value, a calculated column's formula, Assigned cases, or the
Search button's display condition.
After each update, return to the field to see the remaining uses. Once none
remain, the dialog closes and **Remove search field** is ready for you again.

## Show a choice label or its saved value

For a text column that reads a choice, **Show choices as** offers **Choice labels**
and **Saved values**. A label follows the worker’s language. A saved value shows
the code from the case, including a value the app no longer offers. A list can
show both side by side. When you order by one of these columns, it uses the
version you chose for that column.

## Show information from a linked case

A column can show information from another case, such as a household's
address beside each member. In the column's **From** menu, choose the
household link, then choose the address. **Follow another link** lets you
continue from the household to another case.

An app can also have older cases with links its current forms never create.
**Choose another link** lets you enter the link name those cases carry.
**Use a property by name** lets you enter the information to show when the
destination is unknown. A missing link or property leaves the cell blank.

In a menu with Search, Results reads the linked cases included in the
search result. A worker can see a blank cell there when the related case
is available only on the device.

A **Calculated value** can use wording that changes with the worker’s language. Choose **Translated text** as the display, then **Add translated text**. Enter the phrase and select it as a value in your calculation. The same phrase can appear more than once. Its translations live in **Languages**. Workers see and sort by the result in their own language.

For each **Value images** entry, choose **One of the saved choices** or **The entire saved value**. The first matching entry supplies the image. Choose **Show no image** when a rule should hide an icon, even when a later rule also matches. Web Apps can still show its image description. You can also give the image a description for Web Apps. In the entry, describe what the image tells the worker. Other app languages can supply their own wording in **Languages**.

## Show how far away a case is

For an app that runs on Android, choose **Distance from worker** and the information that holds the case coordinates. The worker sees the distance in kilometers, rounded to the nearest tenth. If the worker has not shared a location, or the case has no coordinates, the distance stays blank. In Preview, you can share your own location to try the list.

## Put cases on a map

Choose **Map location** for information that stores coordinates. The coordinates stay out of the Results table. A worker can open a map of the cases on Android. In Web Apps, a project space with the case list map enabled can show the first location in Results. Details shows the saved address, with **Show address** on Android.

If a case can have more than one location, arrange them in the order a worker should use. Android looks for the first usable one on that case. In Web Apps, a case with a blank first location has no marker.

On Android, you can also show a boundary around a case or add points near it. Choose **Map layer**, then pick the information for the layer and its case location. A color layer also needs the boundary or points it colors. The setup saves these choices together. Boundaries and point sets use a series of latitude and longitude pairs. Point colors follow the same order as the points.

## Show a link to a file

**Link** turns a property that holds an address into something a person can
open, labelled with wording you choose rather than the address itself. Its
usual companion is an attachment question saving to a case, which stores a
link to the file it captured (see [Attachment questions](/docs/attachments)).

Two things about it are worth knowing before you add one.

**The wording is the same in every language.** CommCare renders a link cell
through its markdown renderer, and that kind of cell has nowhere to carry a
translated label, so one phrase serves every app language. Pick something that
reads plainly wherever the app is used.

**It is a link in CommCare Web Apps only.** The CommCare Android app shows the
cell as plain text, so a worker there sees the address written out instead of
a tappable word. If your workers use the Android app, that is the trade: they
still see that something is there, and they can still read the address, but
they cannot tap it.

## Lay results out as a tile

A result is normally one row: each piece of information gets a column, and the
columns run left to right. A **tile** is the other way to lay Results out. The
result becomes a card, and each piece of information takes a rectangle on a
grid, a name across the top, a status in the corner, a date underneath. The
grid is 12 columns wide and has a row for each piece of information the tile
shows, and at least six, the rows CommCare HQ's own case list page keeps. When
you remove or hide a piece of information, the tile loses a row once it has
more than six, and anything sitting below the new bottom moves up into free
space.

Reach for a tile when the row runs out of room or stops reading well: when a
name deserves to be larger than everything beside it, when two short values
belong together on one line, or when people are scanning for a shape rather
than reading across. Keep the row of columns when every piece of information
is short and people compare the same value down the list, a row is easier to
scan that way, and it needs no arranging.

Turning the tile on and placing the information happen together. Every piece
of information shown in Results needs a place on the grid, so give each item a
place or hide it from Results first.

Hiding works a little differently on a tile. An item hidden from Results needs
no place on the tile, and Default order can still sort by a hidden item: the
list carries the value without showing it, and the list's search matches it.
Two hidden items can't order a tile list: a calculated value, and Record ID.
Place either on the tile to order by it. A hidden item that doesn't order the
list isn't part of the tile at all, so the list's search doesn't match it yet.

Give an item a place by choosing where it starts and how far it reaches, the
column and row it begins at, and how many columns and rows it spans. Two items
may never cover the same square. Because of that, a swap is a single
rearrangement, not two moves: the halfway state where both items sit on one
square is not a layout Nova will keep.

Each placed item can also carry how it looks: where its text sits inside its
own rectangle, its text size, and whether it gets a border or shading. Two of
those behave in ways worth knowing up front:

- **Border and shading are tile-wide.** Turning either on for a single item
  puts the whole tile into a boxed layout, which changes the spacing of every
  other item on the tile, not just the one you set. Decide them for the tile,
  not for one piece of information.
- **Every item has a text size.** A new item starts at Medium, and Small or
  Large make it recede or stand out. A tile's text has its own three sizes and
  doesn't follow the rest of the list.

The tile is the layout for Results everywhere Results appear, so the list
people search into looks the same as the list they browse. You can also ask for
the tile to stay on screen once a case is chosen from the list, so the person
can always see which case they are working on: above the menu of forms the case
opens, above each form, and above the screens after it, a search included in
Web Apps. Where cases are chosen from more than one list, the first chosen
case whose list keeps its tile is the one shown, as CommCare does. When a
menu's forms read its search, the tile shows the case as that search found it,
even before the worker's device holds it. On
Android, a case's details on the list show that case's tile above them too,
while no other chosen case's tile is on screen. The details of a case a
Search action found show none until it is chosen. Details keeps its own
arrangement either way.

Going back to a row of columns keeps every placement. Nothing you arranged is
lost, so you can try a tile, switch back, and switch to it again without
redrawing the layout.

### Group cases under a connected case

A tile can also **group** its cases. Cases that are connected to the same case
appear together, under one heading: the visits of a household under that
household, the deliveries on a route under that route.

You choose two things. The **connection** to group by, which is the saved name
of the link between the two case types, such as `parent`, `site-parent`, or `site.parent`. And how many of
the tile's top rows form the **heading**. Those top rows are drawn once for the
whole group, from the first case in it; the rows below them are drawn for every
case. Nova offers only the depths that cut the tile cleanly, with something
above the line, something below it, and no piece of information crossing it.
In an app that runs on Web Apps, map location fields and fields marked
**Show this tile value only on Android** can sit in the heading. Web Apps
would show their values below the heading, so Nova keeps those fields out
of the group body.

Four things to know before you turn it on:

- **Choosing a group uses its first case.** With Several cases, each group has
  one checkbox and adds its first case. The other rows are there to read, not to
  choose. When someone filters the list, a group shows only the cases that
  match, so its first case is the first match: the heading is drawn from it,
  choosing the group uses it, and the groups are ordered by it. If people need
  to choose every case separately, keep the ungrouped tile.
- **Cases with no such connection all appear in one group.** That is what a
  device does with them, so Nova shows the same thing. The grouping settings
  tell you how many of your cases that is right now.
- **Pages count groups, not cases.** A page holds whole groups, so a page can
  be long when the groups are large.
- **A form left unfinished for a case with no such connection can't be reopened
  on Android.** CommCare stops when the worker picks it from incomplete forms.
  That is CommCare's own behavior, the same for apps built in CommCare HQ.

Grouping is a Web Apps capability. CommCare on Android reads the setting and
ignores it, so a grouped list there is an ordinary tile list, one tile per case.

Grouping is part of the tile, so turning the tile off turns grouping off with
it.

## Choose your list's own words

**List wording** in Results lets you say what an empty list shows, in place of
"List is empty.". When people can choose several cases, it also names the
button they press after choosing, in place of "Continue". Each language can
have its own words, and you can translate them in Languages like any other
text. Web Apps shows both. Android keeps its own wording. To use your own empty
list text, the project space you publish to needs CommCare HQ's empty case list
text setting, and Nova checks for it before it publishes.

## Load slow values faster on phones

A calculated value or a link can choose **Loading on phones** in its
inspector. **Keep between visits** reuses the value the phone worked out last
time, **Work it out after the list shows** opens the list first and fills the
value in, and **Both** does the two. Choosing one turns on faster loading for
the case list. Returning the last such value to **As the list shows**, or
removing its column, turns it off.
Web Apps loads the whole list later instead and keeps nothing between visits.
The project space you publish to needs CommCare HQ's case list optimizations
setting, and Nova checks for it before it publishes.

## Let people work with several cases at once

Open **Case selection** in Results and choose **Several cases** when one form
should apply the same work to more than one case. Set **Most cases a worker can
choose** to the largest safe batch for that workflow, from 1 to 100. A single
Web Apps list can use 101 if its only form closes the selected cases and
returns to the app home. This form can have Hidden Values with constant
calculations. Preview can close the batch when its selected records fit
within the device payload limit. Keeping
**One case** gives the usual Results → Details → form journey. Several cases
runs only in Web Apps, so Nova offers it in an app that runs only in Web Apps
([Where workers use your app](./where-workers-use-your-app.mdx)).

Nova shows the complete effect before changing the setting. If a form opens a
linked workflow directly, that workflow's Case selection may need to change in
the same save so the complete selection can continue. Nova names every linked
module and its new limit first. It also names any Results tile that will stop
staying above forms, plus any starting value or calculation that can save an
answer without someone entering it. If a form condition, case action, shared
case read, or after-submit link needs an author's decision instead, nothing
changes and the review opens the exact form item to repair.

When **Several cases** is on, Results uses a checkbox for each row or tile and
keeps Details as a separate action. The selection bar shows the total and lets
the worker review the complete set before choosing **Continue**. The choices
stay in their original order while the worker searches, changes pages, opens
Details, or goes Back. A changed maximum never removes a choice silently.
Continue waits and states how many cases need to be removed.

**Choose matching cases automatically** opens the shared form or the menu of
forms with every eligible case, even when the list would show them on several
pages. If more cases match than the maximum allows, the app stops before opening
the form. An empty list still offers its usual search or registration options.

Use several-case selection only when a follow-up or close form can run over the
complete set. That form can belong to the module itself. A parent menu that is
only its case list can also carry the set into a child that uses the same case type, also chooses
Several cases, allows at least the parent's maximum, and has the form. The form
submits once. A question that saves to the selected case starts blank instead
of borrowing a value from one case. Each answer someone enters is saved to
every selected case, while leaving it blank preserves each case's existing
value. A configured starting value or calculation is also saved to every
selected case when it produces an answer. A capture reaches a case as a link
to its file, saved to every selected case when the submitted form provides a
file. Preview leaves that link empty, so trying the form there leaves every
selected case's link unchanged. Explicit
case changes run for every selected case too, and any failure leaves every case
unchanged.

A formula in that form can read the whole selection: for example,
`count(instance('selected_cases')/results/value)` shows how many cases the
worker chose. Reading the selection where one value is needed is refused,
because the form runs over every case in it. Only the form's questions read the
selection, so an after-submit link can't, and a CommCare Connect setting can
read a hidden value that holds the count.

When a child uses a related case type, Results combines the direct children of
every selected parent before the worker makes the child's own selection.

A tile can still group cases, but it cannot stay pinned above a several-case
form: that banner has room for one current case, not a batch. When several-case
selection is enabled, Nova turns off **Keep the tile on screen once a case is chosen** and explains
the change before saving it.

## Choose which cases people can find

Search owns the action people use to continue and any **Search fields** they
can fill in themselves. Select a field to change it, or choose **Edit Search
screen** for the screen copy. The action can exist without any fields: when
**Cases available** already narrows the list, Results can open automatically;
without that rule, the input-free Search action remains a real button on the
case list. Its button reads “Search All Cases”, in every language: that is
CommCare HQ's own text, so the action has no label of its own to edit.
Removing the final field does not discard an authored availability condition,
which stays under **More settings**.

A search field's starting value and the Search action's availability
condition are decided before anyone has picked a case, so they work with
fixed values and current-user information. Case information belongs in the
field's own match behavior or in **Cases available**, which run against each
case.


**Address search** lets workers choose a place in Web Apps. A text field or
a multiple-choice field can fill from part of that address. Its
**Fill from an address** setting lets you pick the address field and the
parts to try in order. A multiple-choice field adds a choice when exactly one label
matches. Workers can also enter or change those answers themselves.
The project space needs advanced case search and the Geocoder plan feature.
On Android, workers enter the linked fields themselves.
When you remove an address field, Nova shows the fields that fill from it.
Review each link and choose a different address field or **No address field**.

In Preview, barcode search fields accept camera scans when Preview runs as
Android and your browser supports scanning, and typed codes on both. A scan
replaces the current answer; cancelling keeps it.

On Android, an answer that holds both `'` and `"` finds nothing.

### Group Search fields

Choose **Add Search heading** on the Search tab, then give the heading a
name. You can move fields to another heading and change the order of the
headings. Removing a heading keeps its fields. You can translate a heading
in **Languages**.

In Web Apps, workers can collapse each group and keep the answers they
entered. Android shows the same fields in order and omits the headings.

### Search filters and project space matching

Use **Add search filter** when you want to send a value with every search. You
can find it in **Results**, under **Cases available**, once you choose
**Online search**. That choice appears when the menu has a search field or
search settings. For example, match the worker's assigned district while
letting them search for a household by name. Choose the information to match,
enter its starting value, then open the value editor to choose a search answer,
an earlier selection or information about the worker. You can edit and reorder
individual filters. Filters for the same information send their values together.
To keep particular owners' records out of the online results, or to choose which
matches arrive first, see [Choose which matches Search sends](#choose-which-matches-search-sends).

A search field can also send its answer under the field's own name. Choose
**Use project space matching** when your project space manages how to compare
that information. A project space can ignore particular text or match similar
words. Existing search fields keep the matching rules they were created with.
Project space matching also lets a date or a date range search information your
forms save as text: the project space finds the cases whose saved text it reads
as a date in that range, and Preview does the same.

A text field can use project space matching for information on the parent
case. Fields brought in with two or three parent links search information on the
grandparent or great-grandparent case. In Web Apps, a single-date Search field
can also match the date saved on the direct parent. It matches the exact saved
date, so a date and time on that day won't match. Changing the field’s name in Nova keeps
the information it searches. Preview uses the settings you confirm for the project space. It shows
when a needed record is absent or the project space matches similar words for
this field.

Turn on **Also find blank** to let workers include cases where the field's
information is blank. In Web Apps a box appears under the field, and workers can
tick it with or without an answer. Android shows the field without the box. The
option is offered on a field that searches its own information under the same
name, with exact matching or a date range, and on a field with project space
matching on the current case, except one that searches the case owner. A form that
reads the search answer sees the blank before the answer, the way CommCare sends
it.

Turn on **Hidden in Web Apps** to search with a field's starting value without
showing the field. Web Apps leaves the field off the Search screen and searches
with the starting value as it stands. Android still shows the field, where
workers can change it. A hidden field has no hint, requirement, check or
**Also find blank**, since nobody in Web Apps can see them, and a hidden text
field searches the information of its own name with exact matching or project
space matching. For a value the search never matches by its name, add a
**Hidden value** instead.

Preview uses the selected destination's search settings. A search returns up to
500 records, or 1,500 when the destination has the higher limit. When a form
uses those results, a condition on the device can hide a record that the
search found. Clearing the condition lets you see what came back. A date
condition on **Date opened**, **Date closed** or **Last modified** can depend on
the destination's time zone. The worker's day and the project space's day can
differ.

If Preview needs an unconfirmed search setting, choose the destination and
confirm the setting there. If similar words or a tie at the last result could
change which record is returned, Preview explains why the exact result is
unavailable. A more specific search can make the result clear. A search for an
empty link can also depend on earlier changes to that record. An isolated App
Test with newly created records lets you exercise the empty, linked and cleared
states. These searches remain available on the published app.

### Use a search supplied by a project space

If your team already has a search in its CommCare HQ project space, a menu can
send answers to that search and show the cases it returns. In the Search
inspector, **Where matches come from** lets you name the search or choose one
another menu already uses. You can also describe it to the Solutions Architect.

The project space decides which cases match. Switching an existing menu shows
which field matching rules will be replaced. Each question keeps its name,
label and answer. **Send this answer** lets the search use it directly. A
field with that setting off can still supply a named value. For example, a
region question can supply the value the search expects under `district`.
Named values are sent in order. A supplied empty value can mean something
different from leaving a name out.

The team that manages the search can change its results without editing the
Nova app. Preview tells you when a search needs the project space. To try the
worker journey, open the published app there. Each destination has its own
search connection in the Publish dialog.

### Hints, required fields, and checks

Each search field can carry a **Hint**, a short line under its label that
says what to type or why it matters. A field can also be **Required**, always
or only while a condition holds, with a message of your own or Nova's default.
A **Check on the answer** is one rule a filled-in answer must pass, with the
message shown when it does not. Leave the check's message blank and people see
CommCare's own "Sorry, this response is invalid!". People see that same
message if Search checks the answer before using it. A field brought in
from CommCare HQ can also be required
with no message at all: in Web Apps its search then waits until the field is
answered, and the field shows as needing attention without saying why.
**Show a message** gives it Nova's default.
Both the required condition and the check are
decided on the Search screen itself, so they can look at this field, the other
search fields (a field that has not been answered reads as blank), fixed
values, and current-user information, but not at case information. They are
also the one place a **matches a pattern** condition is available: it tests
the answer against a regular expression, anchored with `^` and `$` when the
whole answer must fit, which is the natural shape for an ID number or a phone
number.

Required fields and checks are enforced in the browser app. Preview checks them
when it runs as Web Apps. On a phone the search runs either way, so treat them
as guidance for web workers rather than a guarantee.

### Choice fields

**Single choice**, **Multiple choice** and **Checkboxes** offer answers from a
Project lookup table. Choose the column that holds the saved value and the
column that holds the label. Checkboxes let workers tick several choices on
Android or Web Apps. Multiple choice offers a selection list in Web Apps. Nova does not offer a typed-in list of choices on
the Search screen, so a fixed yes/no choice is a two-row table you own. A
multiple-choice field finds cases whose value is any of the chosen answers.

A phone reads every choice field's table as the Search screen opens, before a
menu that opens on its results runs its search. If the table has no rows, the
search doesn't open, and Preview shows why in its place. A starting value the
table doesn't offer is left blank, as a phone leaves it, on a search with more
than one field. On a search whose only field is that choice field, a phone
can't set the choice aside, so the search doesn't open either, and Preview
names the field so you can give it a starting value its table offers.

A search field's rule can also compare a case value with a list of values. A
case matches when its value is any one of them, and a value in the list can be
one you type or a search field's answer.

**Sort choices by** picks the column whose text orders the choices, and starts
as the label column. The choices are listed in that column's order character
by character, the same on every device: digits come before capital letters,
capitals before lower-case letters, and rows with the same text keep the
table's order.

### Names CommCare keeps for itself

CommCare reads some names as part of the search request rather than as a case
property, such as `case_type`, `include_closed` and `_xpath_query`. A search
field or hidden value with one of those names would never search the property
it names, so Nova asks for another name and says why.

### Hidden values

**Add search field** also offers a **Hidden value**: a value carried with the
search, such as the time of the search or the worker's id. Web Apps never shows
or asks it, and it never narrows the results; it exists so other conditions can
read it by name. Android shows it on the Search screen as an ordinary field,
where the worker can change it.
A hidden value works with fixed values, the current date and time, and
current-user information, and cannot read case information or another search
field. It can also start with no value: Web Apps keeps it blank, and Android
shows it empty for the worker to fill in.

In Preview, each new search uses the current worker and data to resolve these
values. Editing answers keeps the previous search's hidden values until you
search again.

### When this menu opens

Some workflows should never show a list before anyone has searched: a
registry too large to scroll, or a program where finding the right person
comes first. **When this menu opens**, in the Search panel, decides what a
worker sees first.

**Search again after clearing** refreshes the results when a worker clears the fields on a desktop Web Apps screen. A required field still needs an answer before Search can run. On smaller Web Apps screens, Clear empties the fields. Android has no Clear button.

A menu that shows its forms in the menu above can keep an ordinary search. The case list has no Search or Register button there. To let workers open Search from the list, give the menu its own screen. Forms that read the search also need their menu to have its own screen.

A menu that searches can open on **Search first**, the Search screen; **Results
first**, the matches of its search as it opens; or **Case list first**, its case
list, offered only in an app that runs on Android only, because CommCare HQ no
longer offers it for a menu that searches in Web Apps. Android opens a menu that
searches on its case list whichever you choose. Under **Search first** or
**Results first**, **Forms read the search** runs the search again as each of
the menu's forms opens, so the form reads what was searched for and found; Web
Apps runs it, and an app that also runs on Android can't use it.

Each choice says what workers see:

- **Search first**: workers search before they see any cases, and Results shows
  what the search finds. Nothing is listed until a search completes, and
  Results then shows only what that search found, with **Search again** at the
  top to start over.
- **Results first**: workers see the cases the search finds with its starting
  values, and can search again to narrow them. Coming back to the list from a
  form without submitting it, or with the browser's Back, keeps the search the
  worker ran. In Web Apps the browser's Back to the list runs it with the
  answers the worker last gave that search, as Web Apps keeps only the latest
  answers, so after a second search an earlier page shows the second search's
  answers, and after the search fields were shown empty it runs with none,
  hidden fields included;
  on Android a search kept on the way back keeps its own. Leaving it behind starts the search over, as
  Web Apps does: after a breadcrumb to the menu or above it, a submitted form,
  or Home, the list opens on the menu's starting search again. The same goes
  for **Search again**: the search fields stay until the worker searches or
  leaves the list behind. In Preview it also starts over when you start
  Preview again, run it as another worker, or change where it runs, since each
  of those starts a new session.
- **Case list first**: workers see their cases and can search from the list. In
  an app that runs in Web Apps the choice says **Not available in Web Apps. You
  can open this menu on Search first, which Android still opens on its case
  list, or change where this app runs in App settings.** For an Android-only
  app, **Request default search results** keeps that preference when you publish.
  On Android workers still open the search fields and press **Search All Cases**.
- **Forms read the search**: each form runs the search as it opens, so it can
  read what was searched for and what was found. In an app that runs on Android
  the switch says **Not available on Android. You can change where this app runs
  in App settings.** Where something else in the menu keeps it off, the switch
  says what and how to change it.

In Preview, **Search again** returns to the search fields. Choosing a field
keeps your typing there, even while the screen finishes opening.

[Where workers use your app](./where-workers-use-your-app.mdx) lists what each
platform runs.

A menu you give Search with no visible search field opens on
**Results first**, so workers never land on a Search screen with nothing to
fill in, and removing the final visible search field from a menu set to
**Search first** turns it to **Results first** in the same change. You can still
choose **Search first** without a field: workers then see a Search screen with
only its Search button, and the canvas says so. Under **Results first** with no
field, the canvas says the menu opens on the cases the search finds, and
**Cases available** decides what workers see. While a saved Search button
condition is false, a menu whose forms don't read the search opens on its case
list.

A Search button condition can count the cases the worker has on their device.
Choose a record type and add conditions to count only the cases that fit. The
count uses cases available on that device. It does not count online matches.

A Search button condition can read only what the case list itself loads
wherever it shows. CommCare HQ loads, for each screen that shows the list, what
that screen's case selection, its list and its return after the form read, and
never what the button's condition alone reads. So a condition on the worker's
session or user information works where the list's filter reads it, or where
every form that shows the list returns to it with the chosen case, and Nova
asks you to change it anywhere else, since the list wouldn't open once the app
is on CommCare HQ.

**Forms read the search** is offered when every form on the menu works on an
existing case, or when the menu is a case list with no forms. A menu with a
registration form on it can't use it, because its first
screen doesn't choose a case; the one exception is a registration form offered
only after an empty search (below), which is on no menu. While the menu's forms
read the search, two settings go away: there is no Search button to show or
hide, so **When Search is available** has no effect, and **Previous screen** is
not an after-submit destination for the menu's forms, because the previous
screen was the search itself. After submitting, those forms return to the menu
by default, which reopens Search.

A form can read the search that helped a worker choose its parent record. For
example, a worker might search for a household by village, choose a household,
then search for a member by village. The form can use either village answer.
The expression picker shows which menu supplied each one. In chat you can ask
for “the village entered when choosing the household.”

Nova gives the searches separate names when you connect the menus. You can
change the **Search results name** in Search’s **More settings**, or in
**Module settings** while Search is off. Formulas follow the menu if its search is renamed. A form opened without
the parent search has no answer from that search. A submenu that only groups
forms does not run a parent search.

A form in a menu whose forms read the search can read what the search found,
for example how many cases it returned, with
`count(instance('results:inline')/results/case[not(commcare_is_related_case = true())])`.
CommCare's search returns up to 500 cases, and Preview reads the same 500.
Cases CommCare adds only to show related details aren't part of what the
search found. The search returns its cases in no fixed order, so a formula
that picks the first or last result, or joins them in order, is refused; you
can count them or check for a particular case instead. While a form reads what
the search found, turning **Forms read the search** off or moving that form to
another menu is refused, and Nova names the form that reads them.

### Register when nothing matches

A menu whose forms read the search can offer a registration form only when a
search finds no matches. In the Search canvas, under **When no cases match**,
choose **Offer a registration form** and pick one of the menu's registration
forms (in Nova's tools, `case_list_registration` on the form), and it leaves
the menu: Results shows a **Register** action, named after the form, only after
a search completes with nothing found, including when the app has no records
yet. The form opens with that search's answers, so a field can start from what
the worker typed: a default value of `#search/patient_name` seeds the name from
the name search field, and a hidden search field's value, such as a search
time, can be saved to a case property as a record that the search happened.
After submit, choose **Continue with the new case** to open the menu’s forms
with that case selected, or return to Results. Web Apps shows those Results
with no record and no **Register**. Search again to find the registered case.
Both returns need the form to create the record every time. If creating the
case is optional, choose **First menu** after submit. A menu with no forms of
its own returns to Search or to its automatic Results. A menu with multiple-case selection requires
**First menu** because CommCare cannot return the newly registered case as a
multiple-case selection. The form has no after-submit links and no display
condition, and no other form can link to it. One such form per menu. Offering a
form turns on **Forms read the search**: each form in this menu runs the search
as it opens. Making it a menu form again (in Nova's tools,
`case_list_registration: null`) turns **Forms read the search** off with it,
because a form on the menu can't open from the search, and removes the
starting values its fields read from the search; the fields themselves stay.

You can offer this same form on another menu’s case list under **Form button on
the list**. Each list keeps its own button text and return destination. If the
form reads an answer from the first menu’s search, Nova names the question to
change before the second menu can offer it.

**Add a new registration form**, beside the menu's registration forms, adds one
named after the case type, with a field for each search field filled in from
its answer and a name for the new case. A review names what changes before
anything commits: **Forms read the search** turns on if it was off, the form
leaves the menu, and where the form returns after submit. **Only the notice**
returns the form to the menu after a review of its own: **Forms read the
search** turns off, and the starting values read from the search go. The
form's own settings carry **How this form opens**: the **Results action
label**, **Add fields for the search answers** (one field for each search
field the form does not carry yet), and **Make it a menu form again**, the
same reviewed change. A menu registration form in a menu with Search offers
**Open after a search finds no matches** in the same place. The structure tree marks the form with a search icon.

Because the form depends on the search, Nova refuses to remove a search field
one of its fields reads, to turn **Forms read the search** off, or to remove
Search while the form is offered; make it a menu form again or clear the field
first. Removing such a search field lists the form field that reads it and
opens it from the review. In Preview, opening the form by its address without a
completed empty search shows why it is not available and offers **Go to
Search**. **Forms read the search** runs only in Web Apps, so this form belongs
to an app that runs only in Web Apps. Publishing to CommCare HQ needs the
project space to allow registration after an empty search (listed in the setup
artifact).

An empty task list can be an expected result, such as when every loan has been
returned. Preview distinguishes cases that do not meet a task's conditions from
an app with no case data; an empty task does not mean its settings need repair.

In Results, **Cases available** holds the rules for finding records. **Device
list** chooses which records a worker sees when browsing. **Online search**
chooses which records the project space can return. For example, a worker can
browse active households and search online for a household that has left the
program. Each edit applies to the selected surface. A form that opens its own
list inside search results also applies the device list condition to the
returned records. Choose **Add condition** for another rule,
then decide whether **all conditions must match** or **any condition can
match**. You can group conditions, exclude matches, use a search answer only
when it has been filled in, follow connections to related cases, and combine
those ideas at any depth. Opening a group gives it the full canvas; Back and
the location trail return you to the surrounding rule. Nova keeps the exact
structure you authored instead of flattening it into a simpler filter. Summaries
keep nested groups in parentheses so you can read that same structure.

Changing a condition asks for confirmation before removing an authored text
pattern or other values. Conditions on a connected case use that case's choices
and value controls. Switching a saved connection between child-only and either
direction keeps its name and destination. A connection that cannot use the
saved condition is unavailable until you remove or change that condition.

Calculated conditions preserve the grouping of nested arithmetic. Blank checks
also work on calculated values, so a condition can match when a calculation
has no result. A search rule can also read a Project data table and convert its
text to a date or number for another calculation, such as adding a table’s
number of days to a starting date. A number converts to a date too, counting
days from 1 January 1970. These rules travel with the exported app.

Cases available and search rules can also choose between conditions: **Depends
on a condition**, under **Add condition**, uses one condition or another,
decided by something like a search answer. A condition can compare **Case
type**, the record type of each case, with record types of your app. A distance
condition offers nine units, from millimeters to nautical miles, and its
distance and unit can each come from a value, such as a search answer, through
**Use a value**. On CommCare HQ, a search measures distance only on a property
its Data Dictionary marks as GPS, so after you publish, Nova lists each property
a search measures for you to set there (see
[What you set up by hand](/docs/publishing#what-you-set-up-by-hand)). A condition on a multiple-choice property can
match choices that come from a value as well as fixed ones, through **Add a
value from**.

Dividing two whole-number values gives a whole-number result, dropping the
fraction toward zero: `10 ÷ 3` gives `3`, and `-10 ÷ 3` gives `-3`. A decimal
value on either side keeps the fractional result.

Nova also checks fixed results in calculated search values. A result using both
single and double quotation marks needs one kind removed so the search can run.
A fixed value in a branch that can never run does not block the rule.

To intentionally make one condition include everything or nothing, open that
condition's matching menu and look under **Special conditions** for **Always
match** or **Never match**. These whole-condition choices stay out of **Add
condition**, so the common path still begins with a useful comparison.

You can remove or rearrange conditions independently. Removing the complete
rule confirms that cases it excluded can appear in Results. This keeps simple
rules quick to scan without preventing the complex rules an established
CommCare app may need. If a condition needs attention, Results and that
condition show the finding where it can be fixed.

The always-on rule and a search field may use the same property. Nova combines
them: leaving the field empty keeps the always-on rule, a compatible value
narrows the cases further, and a value that disagrees can legitimately return
no matches.

When a calculated Results or Details item shows one parent property by itself,
Search brings that property along automatically. The same applies when the
property controls Default order. The parent stays out of the choices and does
not open with the selected case's form. Preview reads the current shared case
data directly, so there is nothing else to configure.

When Search reaches cases that are not already available in the app, the
destination project space needs **Case search** support. Nova checks for that
support before a direct publish and sends nothing if it is missing or cannot be
confirmed. That check never holds back a download: the CommCare HQ app file
stays available for any app CommCare HQ can take, so you can choose and check
the destination later, and for an app that runs on Android, a CommCare mobile
app file is there for each project space the app is already published to. See
[Project-space compatibility](/docs/project-space-compatibility).

Nova also includes faster handling for large Search results automatically when
the project space supports it. That performance check never blocks publishing.
It does not add a second copy of the case data or a refresh step. Preview keeps
reading the current shared cases, and Nova adds no data-refresh setting to
manage.

For dates, **Exact value** means the complete selected calendar day, including
datetime values later that day. Choose **Between dates** when people should
enter both a start and an end; Nova changes the field to one paired **Date
range** control automatically. Under **Starting dates**, **Choose dates**
sets the first and last days together. Both dates stay the same when the app
runs in another time zone. **Use a calculation** can fill the dates from
worker information. Preview shows the dates the selected worker will see.
A date calculation brought in from CommCare HQ can start a day earlier on
an Android device west of UTC. Choosing fixed dates avoids this shift.
An imported starting value can show a single date or more than two dates on
Web Apps. If Search asks for a valid range, pick a start and an end and search
again. You can also change the field’s starting dates in the Builder.
The running search keeps the dates it opened with while the worker checks the results.

A date can be compared with before or after, or searched between two dates. A
time of day can't: CommCare compares these as numbers and a time is not one, so
the comparison would never be true. The conditions in **Cases available** and
in a search field's match rule offer before, after and between for a number or
a date, and not for a time of day.

Two dates and times compare by the moment each names, in Results, in Search and
in Preview alike, however each was written, so an equal comparison finds the
same moment written another way. A search field's own matching rule can also
use **Date closed**, when a case was closed. Only CommCare HQ's search knows it,
so Results, Details and form conditions use **Case status** instead.

Under **Cases available**, open **More availability settings** to decide what
happens to **Cases assigned to the person using the app**. Choose **Show in
Results** for the usual experience, or **Hide from Results** when people should
not see work already assigned to themselves. If an app you brought in from CommCare HQ has a
different assignment rule, Nova keeps it unchanged and explains that some cases may be
hidden. A saved rule that tries to read a case before one has been selected is
marked for replacement. Replacing a saved rule with either simple choice requires confirmation,
because the rule it came with cannot be recovered from the builder afterward.
This is a Results-availability setting, not a Search action: it applies whether
people browse Results directly or arrive through Search, and it never adds a
Search action by itself.

### Register from the list

A case list can offer a registration form at any time, so people look for a
case before adding a new one. In Results, under **Form button on the list**,
choose a registration form from another menu. It stays on its own menu too. You
can choose where people go after registering from the list: **Back to this
list**, or **Continue with the new case**, which goes on to this menu's forms
for it. Back to this list returns to the list, where the new case now shows, or
to the menu's forms where people choose a form first there. A form that has its
own After submit goes there instead. Nova offers this on a list whose menu's
forms all open an existing case. In Nova's tools this is
`register_from_case_list` on the menu.

A form can create more than one kind of record. For example, if a form registers a household and its first member, a member list can offer the form and continue with the new member. The setting shows the name of the case change that creates that record. If the form skips that change, the worker returns to an ordinary list. A return that fetches the new record for Search needs that change to run every time. Where the list sits under a household chosen earlier, it comes back under the household the form registered.

A list that starts by choosing a parent can offer a follow-up on that parent. For example, a worker looking at a household’s members can open **Edit household** directly from the list. The form opens with the chosen household and uses its own After submit setting.

Under **Show the form button**, choose when the button appears. A condition can use a record chosen before the list, and information about the worker, the worker's records or a data table where the list itself reads it, such as in its filter: CommCare HQ loads nothing else for the button, and Nova says when a condition reads more. A condition can count the worker's records but not read one record's value, since several can match and CommCare then stops the list. A menu whose forms read its search can show the button only after a completed search finds nothing. The destination project space must support conditional list buttons and parent follow-ups to publish either setting.

### The case list in the menu

**Show the case list in this menu**, under **Case list in the menu** in the
menu's settings, lists the menu's case list as an entry of its own, beside its
forms or as the menu's only entry. Choosing a case there shows its details. In
Web Apps the case list shows again. On Android, choosing a case returns to the
home screen when the list has no case details, and with them, **Done** returns
to the list. The entry shows only while its case is still to be chosen, as in
CommCare. A menu that asks for its case first, because every form on it opens
the same existing case, lists its forms and its submenus once that case is
chosen, without the entry. A submenu whose case a menu above it already chose
doesn't show the entry either. A menu CommCare HQ receives as an advanced one
(see [Case changes](/docs/case-changes#when-a-forms-link-opens-the-case-it-creates)) chooses the entry's case apart from
its forms', so there people choose a form or the entry before any case.
You can give the entry its own label, icon and spoken label; with
no label it takes the menu's name. A menu with no forms and no submenus is its case list, so the
switch stays on until the menu has a form.

## Choose which matches Search sends

A broad search can match more records than the worker receives. Under **Search filters**, **Which matches arrive first** sets which records the server sends. Pick a property, how to compare its values and a direction. Comparing a priority as a number puts 2 before 10 in ascending order; compared as text, 10 comes first. You can choose a property that Search indexes from any record type this search requests. Search does not index the record’s location. Add a tie-breaker to decide between records that share a priority. Your list can still show the records it receives in its own order.

This order uses advanced case search in your CommCare HQ project space. If your project space doesn't have it, **Add order as a search filter** sets the same kind of order among the search filters instead. When a search has both, the server applies the filters' orders first, then the one above. An app you bring in from CommCare HQ keeps each order where it was. If an older order repeats a direction sign, publishing keeps the same sort direction.

For a Search that opens on results for one record type without Search fields, related records or a separate order, an order filter can compare one property as **Numbers, dates, then text**. It sorts ascending with missing values last. This filter replaces earlier order filters. Later filters still break ties.

To keep particular owners' records out of the online results, add a search filter and choose **Owners to leave out of Search**. Its value names the owner IDs, separated by spaces, and can come from the worker's Search answers. It applies to the online search only: **Assigned cases** still decides which records the device list shows. A search takes one such rule, so name every owner in its value.


### Choose which records appear and which supply information

Choose additional record types for the menu when workers should be able to open them from its list. Each type needs a menu in your app. Under **Search filters**, **Include another record type in the request** adds matches to the search without changing the types a worker can open. A form that reads that search can use the extra matches.

In a Web Apps menu where workers start with Search, a Details-only calculated value can show the text they submitted for one Search prompt. With a plain calculated value that starts from literal text, choose the prompt under **Submitted Search answer**. You can add text before or after the answer, and set the text that appears when the worker opens an ordinary case. An unanswered prompt contributes empty text.

Use **Related records** in Search's settings to include the related hierarchy or the records used by Details. **Record ID to follow** includes the case whose ID a matched record holds in a property that Search can read. Related records can supply case details without appearing as selectable matches.

## Choose which cases appear first

Results keeps **Default order** directly below Cases available and beside the
information it affects. Choose **Set order** the first time, or **Change order**
once it is configured, to expand the editor in the canvas. Then add the
information to sort by, choose a friendly direction such as A to Z or newest
first, and drag the rules into priority order. The first rule decides first;
when two cases match, the next rule breaks the tie. The information used for
ordering can stay hidden from both Results and Details.

Choose **Add calculation** to order the list by a value that workers don’t need
to see as a column. For example, an appointment number saved as text can put
appointment 2 ahead of appointment 10. Choose **Whole numbers**, then add the
case name as the next item to break ties. **Name in Sort by** gives workers a
way to choose that calculation themselves. Publishing checks that the project
space can keep calculated order rules.

In an app that runs only on Android, a location can order cases by distance
from the worker: open the rule of an item that holds a location and choose
**Distance from worker**. Web Apps never shares where the worker is with a case
list, so in an app that runs there the choice stays unavailable until you
change where the app runs in App settings. Distance needs a value that holds a
location, so an item holding numbers, dates or choices can't order by it.
Preview uses the worker location selected for the run. A case with no location comes
last in nearest-first order. Without a worker position, all located cases tie,
so the next rule determines their order.

To sort a number saved as text, open its rule in **Default order** and choose
**Whole numbers** or **Decimals**. For example, a visit count of 2 comes before
10 in number order. Choose **Text** for a code that workers look up
alphabetically. **Use field order** follows the kind of value the field holds. A
comparison you choose stays with the rule if the field's kind changes later, so
change it back to **Use field order** whenever you'd like the rule to follow the
field again.

When you order by a calculated value, Results uses the same case values for
display and ordering, including information from a supporting parent case in
Search results.

Every device, Preview, and every way you publish or download the app order a
list the same way:

- **With no rules,** cases are listed by the first item Results shows,
  ascending.
- **Cases with no value** come first in a rule that goes up (A to Z, earliest,
  lowest) and last in one that goes down.
- **Each item orders by what it is.** A date orders by the date, whatever style
  shows it. A choice shown on Results orders by the labels it shows. **Value images** and labels for each saved choice sort by the matching row’s
  position. **The first matching label** sorts by the label the worker sees.
  A case with no match has a blank sort value.
  A time since a date orders by the text it shows. A calculated value orders by
  its result, and a link by the saved address. An item hidden from Results
  orders by the saved value.
- **A list keeps one rule for each value.** Two column rules over the same property go to its first matching field.
  Independent calculations can give workers different named choices over the same value.
  Where two items read one property and order it differently, such as a plain
  item and its Value labels, the rule belongs on whichever comes first in
  Results. **Add to order** still lists a choice like that, with the reason it
  can't be added.

Workers can also reorder a list themselves from its **Sort by** menu. It lists
each item Results shows under its heading. An item hidden from Results is
listed there only under a name you give it: type one in **Name in Sort by** on
its rule in Default order, such as "Feeling sick" for an item that orders the
list by whether a patient feels sick. Leave the name empty to keep it out of
Sort by. Android lists every named item, and Web Apps lists them only in the
Sort By menu of a list laid out as tiles. When a list has several named
calculations or extra tile fields, **Sort by position** arranges the choices
within that group. Workers can see “Next appointment” first while the list
itself opens with the most urgent cases first. When you show the item on Results
again, its heading takes over and the name is cleared. Preview's running list has the
same menu, so you can try a name there; [Preview on Web Apps and
Android](/docs/building-with-nova#preview-on-web-apps-and-android) says how
each platform's menu works.

**Time since or until** shows whole days, weeks, months or years since a date.
For a due date, choose days, weeks or months until it. The count turns negative
after the date passes. An empty date stays blank. A month is one twelfth of
365.25 days. Ordering this item uses the saved date.

**Formatted text** shows a case property's Markdown. A calculated item can
also show its result as formatted text. On Web Apps, workers see the formatted
result in the list and Details. Android shows the saved wording and formatting
marks in a list and renders Markdown in Details. An Android tile reads inline
HTML formatting instead.

An **Overdue marker** shows an asterisk when a date is missing or its deadline
has passed. A threshold of zero marks a case starting the next day. A threshold
of two marks it on the third day. A negative threshold moves the marker earlier.
Results shows a narrow marker. Details also shows the heading you chose.

In **Value labels**, a saved value can be one word or a sequence such as
**follow up**. The label appears wherever that whole sequence falls between
spaces or at the ends of a response. A blank key labels an empty response and
also matches an extra space at either end or between words. Keys can't hold `&`, `<`, `>`,
`"` or `'`, because CommCare HQ's ID mapping has no way to store one.

Choose **The first matching label** to show one label for an entire saved value
or a condition. For example, a visit count above three can show **Frequent visitor**.
Put the most specific rule first. Workers see the first matching rule’s label in
their language, and the list sorts by that label. With no match, the cell is
blank. An image rule also takes the first match. It can match one of the saved
choices, the entire saved value, or a condition. You can give the image a
description in each app language.

On an app that runs only in Web Apps, a value image on **Results** can
submit a form for the case a worker taps. **When a worker taps the image**
offers forms that open with that case and submit automatically from a
question label. The form needs a deep link that takes one case. The worker
returns to the same Results.

## Use the sidebar for properties

Select a search field, result item, or detail item to edit its data source,
label, matching behavior, or formatting in the right sidebar. Returning to a
display format within the same open editor restores its settings when the
information still supports them, while keeping your current heading and visibility.
Screen options
that do not have a visible row also live there. Less-common settings stay
behind **More settings**. Arrangement does not: screen membership, row order, and
the Cases available and Default order sections each have one home in the
center canvas.
When a search field needs a custom matching condition, a required condition,
or a check, or the Search button needs a display condition, the sidebar shows
its summary and opens the same full condition editor in the center. The
condition is never duplicated in both places.

A custom **Date style** can use any CommCare date pattern but a straight
apostrophe (`'`), which CommCare HQ's date column has no way to store. A curved
one (’) works.

For a menu that is only its case list, use the settings button beside the
module name for appearance. **App home tile** controls how the module looks on
the app's main menu; **Case list in the menu** controls the distinct entry that
opens the list. Those two values stay separate, and Results does not offer a second copy of either
setting.

Property menus use the labels people recognize and offer each built-in value
once. For example, Case name and External ID appear as single choices even
though older CommCare wire formats have alternate spellings for them.
**Case status** is the built-in open-or-closed lifecycle value. A separate
`current_status` property appears only when the app has intentionally created
one; Nova does not treat it as a second spelling of Case status.

Changing a search field's internal name keeps rules that use its answer
connected to that field. You do not need to find and rename those references
yourself. Renaming a case property works the same way: Nova updates every
formula that reads it, including queries of your records in form formulas,
and the rename review counts those places too.

## Manage the data used for testing

Use **Case data** in the builder's breadcrumb bar to see the complete,
unfiltered number of cases for the module's case type. That population is
shared across the app, so every module that uses the same case type sees the
same cases in Preview. When there are none, you can choose **Add sample cases**
to create a realistic set. When cases already exist, choose **Replace case
data** and review the case-type-qualified confirmation before deleting
anything.
That confirmation is important: replacement includes cases entered by hand
or through Preview, not only generated examples. If another case type contains
cases linked to the replaced cases, Nova preserves those cases and clears the
links whose old targets no longer exist. It never silently deletes the linked
case or assigns it to an unrelated new sample case.

Sample cases include readable names and unique external IDs, so the complete
Search → Results → Details journey is useful as soon as you enter Preview.
While Nova creates the cases, Case data keeps the progress visible and pauses
case-type changes, property management, and data review until creation finishes.

Case-data controls stay outside Preview. Preview contains only the app a
frontline user will run, so every button there behaves like a real app button.

## Review data after a property change

When a case property changes type, for example, a free-text date of birth
becomes a real date field, Nova converts every saved case value it can. A
value that doesn't fit the new type is kept instead of deleted, and its case
is held out of the app: it leaves case lists, search, and forms until you've
decided its waiting values on the **Data to review** screen. Holding the
whole case keeps the app honest: no form opens onto a silently blank
required field, and no calculation runs over a hole.

Conversions that could set values aside ask first. Before a risky
conversion, one where some saved values may not fit the new type, Nova
checks the saved data and shows what would happen: how many values can't
convert, what they look like, and how many cases would be held. Nothing
changes until you confirm, and a conversion with nothing at stake proceeds
without the question. The same check applies when the assistant converts a
property in chat, it relays the impact and waits for your go-ahead. A type
change that happens without a convert action, say, pointing a number field
at a property that used to hold dates, skips the question, but the same
safety net catches it: the values that don't fit are kept, their cases are
held, and the notice points you at Data to review.

You'll see a notice the moment it happens, and the **Case data** button
carries a dot while any cases are held. Open Case data and choose **Review
data** to see them, one card per case. Each value states in a few words why
it's waiting, "Isn't a date", "The property was removed", checked against
the property as it is right now. **View case** on any card opens everything
the case currently holds, so you can decide with the whole record in front
of you. Everyone in the Project sees the same list, so a teammate's
conversion is just as visible as your own.

For each value you can:

- **Put it back**: saves the value on its case again. Offered when the value
  fits the property's current type.
- **Overwrite** it, enter a new value in the property's current type, saved
  straight to the case. The original moves to the **Dismissed** list.
- **Dismiss** it, move it to the **Dismissed** list, where it stays readable
  and can be moved back at any time.

Once a case has nothing left waiting, it returns to the app on its own. You
don't have to resolve values one by one either: if the property's type
changes back, waiting values that fit again return automatically.

## Preview without starting over

Edit mode stays focused on the screen's structure, labels, and reading order;
it does not place one arbitrary case value beside every field. To inspect real
data and try the complete experience, use **Preview** in the builder header.
Preview runs the configured journey against the same case data. When Search is
configured, it appears before Results and Details. Entering a search leaves the
current results in place until you choose the screen's Search button, matching
the app people will ultimately use. Preview searches the app's open records in
the current Project, including matches the worker does not hold yet. Search
applies its result limit before Results filters those matches. When the worker
chooses a match, Preview can claim it for that worker. Use **Release claimed
cases** in the worker menu to remove those claims. A one-case row opens that case. In a
several-case workflow, its checkbox adds or removes the case and **Details**
opens it without changing the selection. Other actions inside the row, such as
calling a phone number or checking why a value is shown, work independently.
The Results filter matches the text a device's search reads, which is mostly
the text people see, including formatted dates and choice labels, and ignores
accents, so "jose" finds "José" as it does on a device. Where a cell draws
something else, the filter reads what the device holds: a link column's
`[text](address)`, the address of the image file a column shows, and a calculated
answer as `true`, `false`, or a date written year first. If an older case contains a choice value
that is no longer in the app, Nova leaves that saved value visible instead of
hiding the data.
Large result sets appear 50 cases at a time with **Previous** and **Next**.
When paging is active, the quick filter is labeled **Filter this page** and
explains its scope, so an empty page filter never claims that no matching case
exists elsewhere.

Nova keeps the running preview in its flipbook. Switch back to edit a setting,
with **Back to edit**, then return to Preview and continue where you left off
instead of restarting the app and retracing every step.

When the open form updates, answers you are editing stay in place, including
an answer you have just cleared. You can finish typing before Nova shows
validation for that field.

If a case-data refresh brings back the same values, your open controls and
draft answers stay in place.
Open calendars keep their current month and keyboard focus as other fields
finish updating.

## Working with the sidebars

The workspace is designed to remain readable with both sidebars open. Use the
left sidebar to keep your place in the app and the right sidebar for chat or
the settings of the selected item. On narrower desktop windows, both open
sidebars compact to preserve useful canvas space. On short windows, selecting
an item gives its properties priority and condenses chat to a return bar. You
can collapse either sidebar when you want more room; the canvas reflows without
moving a setting to a different place. Scrolling stays inside the active tab's
body, so the Search / Results / Details strip remains available even on a short
window.

## Built-in record information

Case name, record ID, owner, external ID, opening date, last modification date,
and open or closed status already belong to each record. A form that opens a
record can read these values from it or its parents without adding custom
properties. Forms and Results or Details columns read the two dates at
calendar-day precision, matching CommCare devices. Stored timestamps and server
search retain their time. Because a device keeps only the day, Nova refuses a
formula or filter that runs on a device and compares either date with a moment
such as `now()`, or checks it for an exact date and time. You can wrap both
sides in `date()` to compare days instead. A clock format cannot recover time
from these built-in
column values. An event whose time of day workers need to see can use its own
saved datetime property.

A Results or Details column of record IDs shows each case's own ID on every
device. A tile list orders by Record ID only while that column is on the tile.

The owner controls sharing and sync, and does not identify who last edited a
record. Closing a case normally removes it from a worker's next sync, though an
open related case can keep it as a dependency. A separate property can describe
business stages such as awaiting approval. An approval date or approver that
must survive later edits needs its own saved value.
