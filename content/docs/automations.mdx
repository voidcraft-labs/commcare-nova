title: Automations
description: Describe case updates and conditional alerts, check current matches, and follow exact CommCare HQ setup guidance.
---

Automations let a CommCare HQ project update cases or send messages when cases
match a rule. In Nova, open **App setup → Automations** to describe the rule once
using the same app vocabulary as the Builder, Solutions Architect, and MCP API.

Nova does not run automations in Preview, and publishing an app does not install
them in CommCare HQ. Each saved automation produces a fresh setup guide for a
person to apply in the target project space. CommCare HQ currently provides
HTML setup pages for these rules, not a REST resource Nova could safely drive.

## Automatic case updates

An automatic case update can set a property to fixed text or copy another
property from the case, its parent, or its host. It can also close the case.
Criteria can apply HQ's four value comparisons or four date comparisons to a
property on the matching case, its parent, or its host. A rule may also require
the standard parent case to be closed and may use HQ's separate
server-modified-age boundary. Date conditions compare the current date directly
with the property date plus a signed day offset; for example, an offset of `-2`
means the property date minus two days.

The CommCare HQ form accepts one standard closed-parent condition per rule. It
does not expose another case-index name or relationship for that condition, and
it does not expose a location or regex condition for automatic updates.
Equality values and fixed update values are the exact nonblank text HQ stores:
omit surrounding whitespace and matching outer quotes. Rule names must also be
nonblank and already trimmed.

Keep authoring standard metadata with Nova names. The generated HQ guide
translates `case_name` to `name`, `date_opened` to `opened_on`, and
`last_modified` to `modified_on`; `owner_id` and `external_id` are unchanged.
This applies to criteria, copied values, update targets, recipients, schedule
dates, and message-template tokens. Case `status` is not available in an
automation property slot because Nova's `open`/`closed` text is not HQ's
boolean field, and these rules already inspect open cases. The standard date
fields support date and blankness conditions, not text equality or regex.

The setup guide gives both the exact route template
`/a/<domain>/data/edit/automatic_updates/` and its breadcrumb,
**Data → Edit Data → Automatic Case Update Rules**.
These rules require CommCare HQ's **Data Cleanup** privilege (Pro or higher).
CommCare HQ's hourly task visits each project space once each day, at midnight
UTC by default. One run processes at most 10,000 updates per project space,
case type, and database partition unless that project has a different limit.
Reaching the limit stops that run; the next daily sweep tries again.

HQ's deprecated `RUN_AUTO_CASE_UPDATES_ON_SAVE` switch is project-wide, not a
property of one rule, so Nova does not store or offer it per automation. If a
target project has that switch enabled, saving a case evaluates every active
automatic-update rule for that case type. Treat that global blast radius as a
separate deployment decision; the daily sweep remains the recovery path.

## Conditional alerts

A conditional alert sends one or more scheduled events to case-relative or
explicit recipients. Supported content includes SMS, email, SMS survey,
Connect messages and surveys, and instance-registered custom content. A timed
schedule can start when the rule matches, on a fixed date, or from a case date
property. Nova keeps each schedule to one content type and each timed schedule
inside one setup form CommCare HQ can actually save: Custom Daily events share
one timing mode and stay ordered, Weekly events share timing and content, and Monthly events share timing and
content while using days 1–28 or the final three days of the month. Weekly and
Monthly day pickers exclude days already selected, keep HQ's canonical order,
and stop offering another event when every available day is used. HQ stores a
Weekly event as an offset from the schedule's start weekday. Nova shows the
resulting weekday name and remaps those offsets when the start changes, so a
selected Wednesday remains Wednesday. Fixed and
random event starts are at least five minutes apart, and random windows cannot
overlap.
Survey definitions include their 1–168 hour expiration, reminder intervals,
partial-submission choice, and whether partial submissions carry case updates.
Reminder intervals must total less than the expiration window; the case-update
option is available only when partial submission is on.
For a timed schedule, **Restart when this case property changes** is available
only when the schedule starts from the rule trigger. In the HQ guide, a single
zero-delay immediate event selects **Immediately**; delayed or repeated
immediate events select **Custom Immediate Schedule**.
Historical IVR definitions additionally preserve the maximum attempts per
question.

An email event chooses one body form:

- **Plain text** targets a project where the domain-level **Rich text emails**
  toggle is not enabled. HQ ignores this field when that toggle is on.
- **Rich text HTML** requires the toggle. HQ sanitizes the submitted markup and
  CSS, wraps the result in its own HTML shell, and derives the plain-text
  alternative. The guide therefore prints the HTML source to enter and tells
  you to review the saved rendering; it does not promise byte-exact HTML or a
  separately authored plaintext body.

All email events in one schedule use the same form. Restart-on-property-change
and case-property event times accept custom case properties only because those
two HQ fields do not read standard case metadata.

Alert conditions use the four direct-case value comparisons or a portable
regular expression. The alert form does not accept date comparisons,
parent/host property references, a closed-parent condition, a location
condition, or server-modified age. Regex patterns must be nonempty and remain
inside Nova's shared HQ/Postgres subset.

The setup guide gives both `/a/<domain>/messaging/conditional/` and
**Messaging → Conditional Alerts**. Conditional
alerts require **Reminders Framework** (Standard or higher). SMS delivery also
requires **Outbound SMS** when the message is sent; an email-only alert does
not. Current CommCare HQ retains IVR and SMS/callback to display historical
configurations but refuses new activation, so Nova makes that refusal visible
instead of presenting those types as deployable choices.

Recipient filters can use the app's custom worker information or the user case.
Message templates may use case, owner, parent, host, and recipient values. HQ's
current alert form has no representable web-user recipient. Connect messages
and surveys also cannot target the matched case, parent case, all child cases,
an email stored on the case, or a case group; Nova refuses those combinations
before save. HQ's checkbox-style, case-property, and custom recipient choices
can each appear once; worker, group, and location lists may contain distinct
targets only. Descendant controls appear only for a location recipient, and
location-level filtering appears only when descendants are included. Each
worker-information filter has one value list. A custom recipient or content handler must already be registered
on the target HQ instance; Nova cannot create one.

## Current matches

Preview can count the real, open Nova case rows that currently match the parts
of a rule it can evaluate. The count is information only. It never changes a
case, sends a message, advances a schedule, or predicts the next HQ sweep.

Nova can count each kind's ordinary property comparisons, including
automatic-update parent and host reads, plus the automatic-update
closed-parent condition. Three HQ-only inputs have no honest local equivalent:
a UCR filter, an instance-registered custom criterion, and automatic-update
server-modified age. Store UCR and custom criteria as setup-only instructions;
Nova stores server-modified age as its own case-update field. When a rule mixes
countable and setup-only criteria, the screen names every omitted part beside
the count instead of presenting a partial count as complete.

Preview follows HQ's value typing at this boundary: equality compares exact
stored text rather than coercing the configured value through Nova's property
type; a missing parent/host relation does not satisfy equality or inequality;
surrounding whitespace is blank for **has value / has no value**; and regular
expressions test strings only rather than coercing numbers or booleans to text.

Closed cases are always excluded. A rule with no ordinary criteria is valid;
for example, a claim-cleanup rule can use only HQ's server-modified boundary and
the close action. That boundary measures the latest server modification, not a
business date such as when a claim was created.

## Applying the guide

Open the automation and choose **Copy setup guide**. The guide is regenerated
from the current canonical rule, including current form, worker-information,
and place names. Apply it to the intended CommCare HQ project space and review
its privilege, cadence, cap, and instance-specific caveats before saving.

Schedule dates use Nova's calendar picker and times use locale-friendly clock
entry while the saved rule remains canonical. Removing an item from any
repeated rule section keeps keyboard focus on the next or previous item, then
on that section's add action when the list becomes empty.

Removing or changing an automation in Nova does not alter a rule previously
configured by hand in CommCare HQ. Keep the two in sync until Nova's Deployment
work can track the setup artifact against an explicit target.
