---
title: Reuse one list across every app in your Project
description: Keep the lists your apps share, facilities, districts, products, in data tables, and offer their values as answer choices.
---

Most apps lean on a list that isn't case data and isn't part of any one form:
the facilities you work in, the districts they sit in, the products you hand
out. **Project data** is where those lists live, as **data tables** you fill in
once.

A data table belongs to the Project, not to the app you happen to have open.
Every app in the Project reads the same tables and the same rows, so correcting
a facility's name corrects it in all of them at once.

## Ask Nova to make a shared table

When you describe a new app in chat, tell Nova when a list should be reusable or
maintained in one place. Nova also proposes a data table when the same set of
values serves more than one question, case-list value, or other app surface. A
one-off list can stay directly on its question.

The table is part of the reviewed app design: its name, columns, value types,
rows, and every place that will use it are checked together. Nothing changes in
Project data while Nova is drafting or revising that design. Once the reviewed
design is accepted, Nova creates the approved table before it starts building
the app and keeps the table's stable identity for every reference.

Nova can reuse a table that already exists. Because changing one affects every
app in the Project, Nova does not alter an existing table merely because its
name looks suitable. It describes the Project-wide change and asks for your
approval first. If construction later stops, an accepted table remains in
Project data and the same build resumes against that table instead of creating
a duplicate.

You can also ask Nova in chat, or an agent connected through MCP, to create,
read, edit, reorder, replace, or remove Project data. The same access rules and
app-reference checks used by the builder apply to those changes.

## Open Project data

Project data sits in the builder's left sidebar, below the app structure. Open
it from the expanded sidebar, from the icon rail when the sidebar is collapsed,
or, on a phone, from the same panel the app structure opens in.

The workspace has its own address, so you can send a teammate a link that lands
them straight on a table.

## What a table is made of

A table has columns and rows. Each column carries three things:

- **A name people see.** This is the heading you read while you work, and you
  can change it whenever a better word comes along.
- **A name used in exports.** It's also the heading Nova looks for in a CSV, so
  changing it means every CSV you import from then on has to carry the new
  heading. Changing it needs admin access, and the table itself has one of these
  names too. The table's export tag appears on both the table list and the table
  itself, so you can verify the contract before sharing a CSV or integration.
- **A type of value**: Text, Whole number, Decimal number, Date, Time, or Date
  and time.

You can give a table an export tag like `locations` even if the app also uses
worker locations. Nova gives the form a separate name for reading that table.
A tag can hold up to 32 characters, and an export name up to 255. Both start with
a letter or an underscore and go on with letters, digits, underscores, hyphens
and periods, so `site_code`, `école` and `site.name` all work. A name can't
start with lowercase `xml`, and a row or value detail can't be named `xmlns`.
Some places in an app read only plain names: CommCare HQ changes a period in a
case list filter or a display condition, a menu reads a table only by a tag of
letters, digits, underscores and hyphens, and Android reads a narrower set of
characters than Web Apps. A name like `site_code` works everywhere. CommCare treats the lowercase words
`casedb` and `ledgerdb` anywhere in a tag as a request for case or stock data.
You can use `case_db`, `ledger_db` or a spelling such as `CaseDB` for your table.
Nova names a conflict when you create or rename a table. If an older table has a conflicting
tag, exporting an app that uses it pauses until an admin changes that tag. The
table's rows and its references in Nova keep their identities.

## Repeated values and row details

A row detail describes the whole row. For example, a clinic can have a district code even if the table has no columns. **Edit row details** lets you name and reorder those details. A repeated text column holds an ordered list. Each item can have its own details, such as the language of a clinic name.

When creating a table or adding a text column, select **Allow several values per row** to give it a list. **Add value detail** names information each value can carry. A column's **Edit value settings** also lets you index it for lookup. When a definition changes, Nova checks the apps using it and preserves the identities of the details you keep.

In a row's properties, **Add value** appends one item. You can move it up, remove it or edit its exact text. Two items can have the same text and different details. **Use an empty list** gives the worker zero items. When you leave the list unspecified, CommCare reads one empty value. A listed item containing empty text also counts as one item.

**Add rows from a file** appends rows to a table with repeated values or row details. Choose a JSON file up to 256 KiB. For example, this file adds one row to a clinic directory. The export names identify the scalar column, the row detail, the repeated column and its value detail.

```json
[
  {
    "cells": [{ "name": "clinic_code", "value": "007" }],
    "content": {
      "attributes": [{ "name": "district", "text": "North" }],
      "occurrences": [
        {
          "name": "clinic_names",
          "values": [
            { "text": "Hill Clinic", "properties": [{ "name": "language", "text": "en" }] },
            { "text": "Clinique Colline", "properties": [{ "name": "language", "text": "fr" }] }
          ]
        }
      ]
    }
  }
]
```

Use a quoted string for a text code such as `"007"`. A number in a whole-number or decimal column uses a JSON number. Each row needs a value for every row detail, which can be empty text. CSV replacement is available for scalar tables.

## Find and edit a row

Rows open in pages of 25. **Find a row** searches the whole table, including row details, repeated values and their details. When you open a match, **Order in table** shows its position among all the rows.

Select a row and it opens in the properties panel on the right, where each value
gets the control its column's type calls for, a date picker for a date, a clock
field for a time. Nova preserves text exactly, including leading or trailing
spaces and an intentionally empty piece of text. It also keeps that distinct
from a value that was never present.

The row's properties include **Move up** and **Move down**. A column's properties
use **Move left** and **Move right**. Save or discard an open value edit before
moving that row or column. Reordering changes where it appears without changing
its identity or any app reference.

For a large row, choose a column or a row detail to read it. **Open text editor** lets you page through a long value, edit the displayed part, or replace it with a UTF-8 text file. **Replace the whole value** applies the replacement from beginning to end. A smaller row offers the same controls under **Edit a single value or import text**. For a missing text value, you can set it to empty text first. If the connection breaks, **Resume edit** continues the same upload. **Cancel upload** leaves the saved value available.

Times and dates stay human-readable while you edit. Nova keeps the timezone and
fractional seconds required by storage behind the clock control, so opening and
saving a row does not change the moment, its precision, or its offset. If a
column changes type and a date picker cannot display the old text, Nova shows
that retained text beside the picker so you can copy it until you deliberately
choose a replacement. Malformed date-time text stays available for correction;
Nova does not save only the part it recognizes.

When you enter a local time that repeats as daylight saving ends, Nova uses its
first occurrence. A time skipped as daylight saving begins moves forward by
the size of that jump. A value with an explicit offset keeps that offset.

An unsaved row stays with the table if you close Properties, press Escape, open
another row or column, or leave and come back. Nova marks retained drafts in the
table and lists every draft or unresolved save/delete decision under **Row work
to review** on the Data tables screen. The work stays in that builder tab until
you save it or explicitly discard it.

Your draft stays available as you change the window size, and **Review row work**
reopens its properties.

If a teammate removes the row first, the same draft can be saved as a new row.
If anyone removes the whole table, even while you are looking at another one , 
Nova keeps a read-only local row copy from the last version you could see. You
can copy it before choosing **Discard local copy**. Recreating a table with the
same name does not attach that old work to the new table. If your edit access
changes, the retained text remains readable and copyable, and the discard action
still removes only your local copy.

## How much a table can hold

One CSV import or replacement takes up to 5,000 rows and 8 MB. A table can grow
past that as you add rows, and a table from CommCare HQ can be any size: Nova
reads a large one in pages when you refresh it. Project data shows the row count
and stored size of each table.

## Replace every row from a CSV

You can replace a table's rows all at once by importing a CSV. Its headings have
to match the table's export names exactly: one heading per column, none missing
and none extra.

The import replaces every row in the table. It doesn't merge with what is
already there, and it doesn't add to the end.

If a teammate changes the table after Nova checks your file, Replace pauses.
Review the same file against the latest columns and row count, then confirm
again. Nova never retries a whole-table replacement on its own.

## When two people edit at once

If a teammate saves the same row while you have it open, Nova doesn't overwrite
either version. It shows what is already saved and lets you reconcile your row
against the table's current columns. New columns appear, values must fit any new
column types, and values from removed columns stay visible until you copy what
you need and acknowledge that those columns no longer exist. If their change
was to a different row, your save goes through as usual.

If they delete the row, your draft remains available. You can save it as a new
row, and Nova opens that new row for you. A failed save leaves the draft and the
decision on screen.

## Offer a table's values as answer choices

A single-select or multi-select question can take its choices from a data table
instead of from a list you type out. Choose the table, the column whose value
gets saved, and the column people read on screen.

Once both columns are chosen, **Add row rule** lets the question offer only
matching rows. For example, compare the table's District column with the district selected on an
earlier question, so the next question offers only facilities in that district.
The condition editor knows it is checking one row of this table: it offers that
table's columns, fixed values, worker information, and eligible earlier form
answers. It does not offer case data, Search answers, later questions, or an
answer from a child or sibling repeating section.

When the earlier answer changes in Preview, the available choices update
immediately. A selected value that the new row rule no longer offers is cleared,
so the form cannot submit an answer hidden by its current filter.

A table needs at least one row before a question can take its choices from it.
A phone won't open a question whose table has no rows, and the same goes for a
Search screen whose field takes its choices from one, so Preview shows that in
place of the form or Search screen, and downloading or publishing the app waits
until the table has a row. A row rule that leaves no choices is fine: the
question opens with nothing to pick.

Switching between a table and a typed-in list replaces the question's complete
choice source. Nova opens the new source for editing and saves the switch only
after that source is complete; cancelling leaves the current source unchanged.
If the saved table becomes unavailable, it stays selected with an explanation
until you choose another source.

A Search field's choices also have a column they are sorted by, the label
column unless you choose another under **Sort choices by**. That column counts
as one the Search field uses, like the saved-value and label columns.

## Changes that other apps can block

Deleting a table, removing a column, and changing a column's type each need
admin access, and Nova refuses them while any app in the Project still uses that
table or column, including a column a Search field sorts its choices by. An app sitting in the trash counts.

Before it makes the change, Nova names the apps that would break. Point those
apps at something else first, then come back and make the change.

If Nova cannot check those references, the change stays disabled and offers
**Try again**. A failed check never claims that no apps use the table.
If Nova knows an app still uses the table but cannot load that app's name, the
change stays blocked and offers **Check references again**.

If the table changes while that confirmation is open, Nova refreshes the table
and checks its app references again before you can confirm the change.

Renaming a table's export tag, or the export name of a column, row detail or
value detail, is checked against every app and accepted app design that uses
it. Where an app reads it somewhere the new name won't work, such as a period
in a case list filter, Nova refuses the rename, names the app and the place,
and suggests a name like `district_code`. You can use that name, or change how
the app uses the data first. Removing a row detail or value detail an app reads
is refused the same way.

## What happens to a table when you publish

Nova prepares each table for the place your app will run.

- **A downloadable app** carries tables shared with everyone. If its rows belong
  to particular workers, groups or places, Nova checks that the named project
  space has the right table. Each worker receives their own rows when they
  sign in and sync the installed app.
- **Publishing to CommCare HQ** puts them on the project space before the app's
  content goes, and replaces their rows with the rows in Nova every time you publish.
  If a table was edited in CommCare HQ since Nova last published it, the next
  publish stops and asks before it replaces the edit, so the values you keep
  here stay the ones your app reads. A table a workbook can't carry exactly,
  such as one tagged `types` or with a value that starts or ends with a space,
  goes row by row instead and keeps every value as you typed it, unless the
  project space already holds it from a workbook
  ([Publishing](/docs/publishing) has the details).
  A table managed in CommCare HQ is different: Nova never writes it in the
  project space that manages it, and checks before each publish that it still
  holds what your app reads. When several of your Project's apps read one
  table, each of them publishes it without being asked to take it over.
- **The CommCare HQ app file** comes as a zip. Its README names the lookup
  workbooks to upload on the project space’s Lookup Tables page. A large app
  can have several workbooks. Each contains complete tables. A reusable file
  includes setup instructions for worker assignments. An editor can choose a
  named project space in Publish to include that destination’s verified
  assignments. Complete tables with verified column settings come in one workbook
  per source project space, such as `lookup-tables-managed-in-acme-health.xlsx`.
  The README names any table whose settings or assignments still need verification.
  In its original project space, the app uses that existing table. In another space,
  an admin can use CommCare HQ’s current export of the selected table to prepare its
  tag, indexes, rows and worker assignments, then verify the intended workers’ rows.
  If you want a different design, create a table in Project data and connect the
  app’s fields to it before downloading a new app file. A table only a publish
  from Nova can carry exactly, such as one tagged `types`, keeps an app from
  coming as an app file; Nova names it, and you can publish from Nova instead.

If a cell contains a character CommCare cannot preserve, Nova stops the export
and names the table and column. You can remove the character or retype the
affected values in Project data, then try again. Nova keeps your stored values unchanged.
For a table managed in CommCare HQ, you change the value there instead, then
refresh Nova's copy on the table's page.

One thing worth knowing before you rename an export tag: CommCare HQ finds a
table by that tag, so renaming makes a **new** table there and leaves the old
one where it is.

If the project space already has a table with the same tag and Nova did not make
it, publishing stops and asks you which of them are yours rather than writing
over somebody else's data. [Publishing](/docs/publishing) has the details.

A row can have its own details, such as a district code. A column can hold several values in order. Each value can have details of its own, such as the language of a place name.

In a question or Search choice list, you can choose a row detail as the saved answer and a different value as its label. For a column with several values, **Match a value detail** narrows the list. **Position** chooses one of the remaining values, starting at one. A French label and an English label can share the same saved district code. A worker can reopen that answer after you change its label.

Nova checks the rows that each worker can receive. Each saved value must be distinct within those rows and contain no spaces, tabs or line breaks. Each label needs visible text. If a worker’s source has no rows or a selected detail has several matching values, Preview names the affected data. If the source has rows and your question’s filter matches none, the question shows no choices.

A device file can include tables shared with everyone. Assigned data needs a verified worker connection on its own project space. Project data shows where to reconnect or check the rows that the worker receives. When an upload needs a workbook, Nova checks that the target can retain its row details, value order, indexes and assignments. An additional value that CommCare HQ would lose needs a different way to deliver the table.

## Tables managed in CommCare HQ

When you bring an app in from CommCare HQ, the lookup tables it reads come with
it, marked **Managed in CommCare HQ**. Each one lives in its project space on
CommCare HQ. Nova keeps a copy so your apps and Preview can read it, and never
changes it there.

Project data distinguishes the complete source inventory from the rows an individual worker receives. A table can stay linked to its project space while a large inventory is refreshed. If a source read stops partway, Nova keeps the last completed inventory and labels it with the time it was read.

Project editors can open **Check source access** and enter a mobile worker’s username to read the data that worker’s device currently receives with their own approved HQ connection. Leaving it blank checks the connected account. A web account receives every row of a global table and no assigned rows. A mobile worker’s rows follow their own assignments, groups and primary place, including its ancestors. A worker check reports a time, complete row count and a small sample. A protected table needs fresh worker data before a dependent action can run.

In the same dialog, **Check and record workbook** accepts an HQ download containing this table alone, up to 768 KiB. Nova compares the table definition, row identities, order and workbook values to the source. It checks named workers, groups and places in that project space. The resulting historical receipt records the indexed columns and how many rows had assignments at the time of the check. A new check is needed when a destination or management change depends on current assignments.

You can change the table on CommCare HQ's Lookup Tables page, then choose
**Refresh from CommCare HQ** on the table's page in Nova. Nova refreshes its copy
before each publish too, and the page shows when the copy was last refreshed.
While CommCare HQ manages a table it stays read-only in Nova, for you, for Nova
in chat and for an MCP agent alike.

For a large table or one with assigned rows, a Project editor can open **View source inventory**. It shows the date and row count of the completed copy. **Read first row** opens the values and their details in order. Exceptionally long rows open in parts. **Check inventory** shows how far your refresh has read. **Cancel my refresh** drops your unfinished read and keeps the last completed copy available. If a connection breaks, **Refresh from CommCare HQ** can continue from a verified point.

A worker’s Preview uses the rows available to that worker. The Project editor’s source inventory is a separate view.

**Manage in Nova** hands the table to Nova. From then on you change it in Nova,
and each publish to that project space replaces the table there with Nova's
columns and rows. If someone changes it in CommCare HQ after that, your next
publish there stops and shows you what changed before it sends anything. A
Project admin can choose this, and Nova names the apps that read the table
before you confirm. For a large global table, the admin first refreshes the source inventory with their current connection. Nova checks the full table and its indexed columns against what a device receives from the table right now. After transfer, the same rows and columns can be edited in Project data, including text larger than one screen.

**Let CommCare HQ manage it again** hands it back. Nova takes CommCare HQ's
columns and rows as they are right then and stops changing the table there.
Changes made in Nova that were never published there are replaced, and every
column becomes text, as CommCare HQ holds it.

Either change is made only over the table you confirmed. If someone edits the
table, or another app starts reading it, while you're deciding or while Nova
reads CommCare HQ, Nova changes nothing and shows you the table as it stands
now, so you can confirm again. The same goes for your own access: if your role
in the Project changes in that moment, Nova leaves the table as it was.

If a column your apps read is gone in CommCare HQ, Nova keeps the column in its
copy, with no values, so those apps keep opening. Their next publish to that
project space stops until the column is back in CommCare HQ or the apps stop
reading it.

## Take the table from CommCare HQ, or make a separate one

A table you made in Nova and published lives in that project space too. If
someone changed it there, your next publish stops and shows you what changed.
You can publish over the change, or choose **Use the table from CommCare HQ** on
the table's page. Choose the project space whose table to take. Nova reads that
table and shows what taking it does: the rows it has, the columns that come in
or go, the columns that become text, and the apps that read the table. Once a
Project admin confirms, Nova's table holds that table's columns and rows, and
CommCare HQ manages it from then on, as a table brought in from there is. Its
id stays the same, so no app changes, and the next publish to that project
space leaves the table there as it is. Nova changes nothing if the table, the
apps that read it, CommCare HQ's table or the publish that put it there moved
while you were deciding.

A table someone else's project space manages can't always travel to yours: if
CommCare HQ never told Nova which of its columns are indexed, a publish to
another project space stops and says the table needs a verified table there.
**Create a separate table** makes a new Project table from the columns and
rows a table has now, under its own name and export name, and points the apps
you choose at it instead. The old table and every other app stay as they are.
The new table is Nova's: it indexes only the columns you choose on its page,
and each publish of those apps sends it. A Project editor can choose this for a
table every worker receives.

## Choosing who receives rows

In Project data, **Who receives this table** shows how the app shares the table. **Use row assignments** starts with every row hidden from workers. An editor can open **Who receives this row** and choose people, groups and places. A worker receives a row once if any of its assignments match. Assigning a place includes workers whose primary place is there or below it. Their additional places do not extend this access.

**Worker groups** lets you add people from the Project's apps, see the app beside each worker's name and decide whether a group can own cases. A group can receive rows whether or not it owns cases. An admin can choose **Share with every worker** after reviewing the apps that read the table.

A connected project space needs its own worker, group and place bindings. In a group's settings you can review its connection by name or identifier. Nova checks its current membership before sending assigned data. A worker with the same name in another space has a separate identity.

To take over a source table with assigned rows, download just that table in its project space and attach the file to **Manage in Nova**. Nova checks the source row identities, the worker, group and place connections, and the device data for the connected workers. If these have changed, you can refresh the table and download a current copy. The last workbook check in **Check source access** shows when that earlier copy was observed.

## Who can do what

- Anyone who can open the app can read its table definitions. A Project editor with an approved source connection can inspect protected source inventory.
- **Edit values, add rows, add columns, reorder rows or columns, and import a
  CSV**: edit access.
- **Delete a table, remove a column, change a column's type, and change the name
  a table or column uses in exports**, admin access.
