**Nova agent design: research, measurements, and a proposed direction**

Prepared September 12, 2026 against commit `558e7069e7418108ea1248d9ae152869614d8251`. This assessment began as read-only research. The subsequent [authoring pilot](agent-authoring-pilot-2026-09-12.md) records the implementation, paid comparisons, failures, and interface decision. The delivery plan is [Improve agent authoring](../plans/agent-authoring-quality.md).

Nova should redesign the interface through which a model authors an app. The present interface asks the model to make useful design decisions, reproduce decisions the server has already made, encode storage representations, and administer its own orchestration protocol. Much of the context exists to explain those last three responsibilities. Better prose matters, but its lasting benefit depends on making the job itself clearer.

The valuable foundations are already present: one canonical document, stable references, shared mutations, validation before commit, an independently reviewed design, durable execution, and explicit ownership of external resources. The proposal below builds on them. It does not require a new persistence model, weaker validation, or importing CommCare HQ's authoring conventions.

Research began with official OpenAI guidance, followed by two engineering articles written by Anthropic's own teams, current repository sources, and local durable run records. The objective is better apps through an interface that supports good model decisions. Token counts diagnose unnecessary burden; they do not define success. CommCare is useful orientation and belongs in the prompt. Nova's original authoring model and CommCare's execution and export requirements should both be explained accurately.

**What the guidance establishes.** OpenAI's current GPT‑5.6 guidance favors clear outcomes, completion conditions, relevant context, and leaner instructions over accumulated procedural direction. It recommends removing repeated instructions and measuring whether examples or additional rules actually improve the task. That supports rewriting from the intended job, rather than editing the existing prompt sentence by sentence. It does not establish a universally optimal token count. [GPT‑5.6 guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)

GPT‑6 Astra's guidance is particularly relevant to Nova's accumulated recipes. Eric Provencher's official article explains why instructions that helped an earlier model can constrain a stronger one, and favors small entry points that explain applicability and link to relevant material. This is a reason to evaluate the instruction set against each model, rather than assume that Astra and Luna need identical scaffolding. Plain, direct prose can express firm requirements without an elaborate role persona. [Rethinking skills and prompts for GPT‑6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), [Astra guidance](https://developers.openai.com/api/docs/guides/latest-model)

Function definitions are an interface designed for a model, not automatically the same interface a backend developer would expose. OpenAI advises omitting arguments code already knows and combining operations that always occur together. Its guidance to keep the initially available function set small is a heuristic, not a feature limit. Anthropic's tool-design article independently makes the case for designing operations and their returned information around an agent's task. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

The useful concept is the amount of relevant information and decision-making work in context. Anthropic's context-engineering article treats instructions, tools, retrieved material, and history as one system. Its authors are Applied AI practitioners Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, and Jeremy Hadfield. Their guidance is useful architectural evidence, not proof of a particular GPT model's behavior. [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

The user's concern about overwhelming schema is justified by the measurements below. One detail needs correction: OpenAI renders function definitions into a model-facing syntax, so the model does not necessarily receive the literal JSON that Nova counts. Next-token prediction also does not imply that a large schema will make a model unable to reason. The defensible claim is narrower: Nova exposes a large amount of repeated representation and protocol, and that is work we can remove from the model's job. Quality improvements must then be measured.

**The central redesign should give the model a coherent authoring language.** Nova's internal validation schemas serve storage and implementation. The agent needs a compact way to express a workflow: what a worker sees, which record is selected or created, what answers mean, what changes on submission, and what happens next. The model should see those concepts directly, with precise references and clear feedback.

I would build a small authoring library over the existing domain and mutation system, with shared types for fields, expressions, references, and text. Define each concept once. Ordinary labels should accept ordinary strings, which code can normalize into `ProseTemplate`; expressive labels should have an explicit richer form. Reference helpers should produce the existing typed AST, preserving stable identity through renames. The server should bind app, Project, current transaction, known identities, and already accepted mappings. The agent should not have to restate them throughout its arguments.

This library would be the shared model-facing boundary for SA, build, and MCP. It would lower into the existing mutation and authorization boundaries. It would not become a second canonical app document. Existing external integrations would need a migration path, and the full feature surface would remain reachable.

Compare a compact native-function interface with a bounded authoring library using familiar JavaScript and shared type documentation before selecting a transport. The latter can express composition and reuse types, but it may add a language the model does not need. Native operations are the initial reference candidate, especially for writes whose authorization and failure boundary must remain clear. Select the interface on complete task quality and repair behavior. Type reuse is a reason to investigate the library, not evidence that code execution will outperform native calls for Nova.

Simply putting the existing 94 tools behind an `execute` tool would preserve the problem. So would an untyped `payload` parameter, a new arbitrary mini-language, or moving 200,000 tokens of definitions into files that the model must subsequently read. Count all the signatures, examples, and reference material needed to use the interface. Preserve exact omitted-versus-cleared edit semantics, schema validation, and useful error paths.

Atomic construction is essential. `createModule` and `createForm` currently include content because an empty intermediate form would violate Nova's contract. A redesigned authoring transaction can collect construction data, resolve internal references, and submit a complete valid mutation batch. It must not commit an invalid skeleton and hope later calls repair it. Identity resolution, authorization, external resource ownership, and the reviewed plan's allowed scope remain server responsibilities.

OpenAI's Programmatic Tool Calling can coordinate predictable tool sequences and reduce intermediate output. It does not inherently shrink tool definitions, and direct calls remain appropriate when each result requires a new semantic decision. Use it for work whose dependencies can be expressed in code, with defined failure and completion behavior. [Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

**The executor should stop reproducing facts the compiler already knows.** The [accepted execution brief](../../lib/agent/build/executionBrief.ts#L1023) includes exact record mappings, module and form composition, layout lowering, field IDs, and icon decisions. The [executor instructions](../../lib/agent/build/executorPrompt.ts#L76) then teach the model how to copy those decisions through individual calls.

Have code realize those known choices. Reserve model work for unresolved semantics: a condition, an expression, a useful field arrangement where the design has not fixed one, or wording that requires judgment. This requires making the unresolved parts explicit. Arbitrary prose in today's semantic contract is not automatically executable; the compiler cannot infer an unstated clinical rule, business calculation, or record lifecycle. The design output should distinguish an actual typed decision from an open decision requiring model or user judgment.

This should shrink the need for a general-purpose executor on simple builds. A substantial app can still use workflow slices for recovery and meaningful progress. Choose those units around a coherent worker task and dependency structure. Do not assume every small build benefits from repeated full-context slice setup.

Keep the independent reviewer and durable completion authority. The change is to what models must do inside that system. For example, `finishDesign` currently produces a receipt telling the agent to call `requestReview`. Submitting a design should let the server run that deterministic next stage. On success, tools should return useful changes, bound identities, and a revision. On failure, return the exact rejected path, reason, and information needed for the next decision. Repeated encouragement to continue is not state. [Current review transition](../../lib/agent/design/loop/tools.ts#L2123), [empty-step nudge](../../lib/agent/build/executorLoop.ts#L623)

**Write the prompts as a short product guide.** The central teaching should explain the few distinctions that determine a good app: the worker's task, record identity and lifecycle, current values versus a history of events, selected-record context, and how navigation and form flow support that work. Tell the agent what makes an app useful and where judgment is welcome. Put syntax beside the relevant operation and use a few carefully chosen examples when evaluations show that they help.

The current editing prompt contains a roughly 12,000-token shared technical tail. Feature rules also appear in tool descriptions, design constraints, and executor instructions. This creates maintenance risk in addition to length. One current example: the editing prompt says search-before-register forms have no `post_submit`, while `createForm` documents explicit `app_home`, including the multiple-selection requirement. A rule repeated across prose surfaces has already drifted. [Editing guidance](../../lib/agent/prompts.ts#L387), [current tool contract](../../lib/agent/tools/createForm.ts#L106)

Here is the register I would use for the authoring role. This is a proposed core, not a complete production prompt:

> You are the Solutions Architect in commcare nova. You help people design and build CommCare apps for data collection and case management.
>
> Start with the worker's task: what they need to know, what they record, and what should happen next. Design around that flow. Use the person's vocabulary, keep related questions together, and make the next step easy to find.
>
> Preserve the requirements the person has given you. Ask when an answer would change the workflow, the records it keeps, or an important rule. Choose sensible defaults for smaller details. Make assumptions clear when they affect how the app behaves.
>
> Decide what each record represents and how it changes over time. Keep a history when earlier events matter; update a record when only its current state matters. Reuse information the app already knows so people do not have to enter it twice.
>
> Use Nova's authoring tools to make the app, then walk through its main tasks. Check what the worker sees and what the app saves. Explain the result in everyday language, including anything that still needs attention.

An executor that is still needed can have a similarly direct role: “Implement the accepted workflow in the private workspace. Preserve its agreed behavior and wording. Resolve the open implementation decisions identified in the brief. If a requirement cannot be represented, return the conflict so the design can be revised. Submit the candidate when the workflow is complete.” The final sentence describes a product action; recovery, allowed calls, and completion authority belong in code.

A prose review should judge clarity, precision, tone, and whether each sentence changes a useful decision. It should remove unnecessary personas, repeated prohibitions, internal metaphors, and instructions to narrate a prescribed reasoning process. Some constraints are firm and belong in writing. They should be stated once, close to where they apply.

**Treat state, sources, and continuation as part of the same interface.** The executor currently begins with an accepted brief, a full private Blueprint checkpoint, and a focus/inventory packet; compaction reseeds those three. Send the relevant workflow, its dependencies, authoritative decisions, and unresolved work. Make the rest available through bounded inspection. A projection must include dependency closure and support retrieval of omitted material, so saving tokens cannot hide a referenced record, shared option source, or cross-workflow effect. [Current checkpoint construction](../../lib/agent/build/executorLoop.ts#L768)

The extraction pipeline makes its extract the architect's only account of the source, including images the architect cannot revisit. That architectural bottleneck helps explain its defensive 5,672-token prompt. Preserve accessible source material and give the architect reliable retrieval by section, range, table, or figure. Use a compact requirements index and explicit provenance to guide reads. Exact options and formulas must remain retrievable; a shorter lossy summary would be a regression. [Current extraction contract](../../lib/agent/documentExtraction.ts#L175)

Nova also needs an updated reasoning-continuation policy. The current sanitizer drops historical reasoning based on the older premise that it is ignored. GPT‑5.6 instead defaults to using available compatible earlier reasoning; its guidance also explains when to select `current_turn`, family compatibility, and stateless replay. Preserve compatible reasoning for continuing work, deliberately reset irrelevant prior reasoning, and retain the required response-item pairing rules. Do not indiscriminately retain everything or discard everything. [Current sanitizer](../../lib/chat/sanitizeReasoningParts.ts#L16), [current reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning)

Use deferral after making individual capabilities coherent and compact. Namespaces can keep unrelated capabilities out of the initial context; loaded tools are appended, which supports stable cached prefixes. Deferral does not reduce the definition that appears once a tool is loaded. The installed OpenAI provider supports discovery and programmatic calling, but it explicitly rejects deferred/namespaced tools in the existing `tool_choice.allowed_tools` mechanism. The executor's policy integration therefore needs redesign, with server dispatch authorization preserved. [OpenAI tool search](https://developers.openai.com/api/docs/guides/tools-tool-search), `@ai-sdk/openai/src/responses/openai-responses-prepare-tools.ts::prepareResponsesTools` (installed source inspected at the recorded baseline)

**Give the agent evidence of whether the app works for a person.** The inspected shared tool registry and executor profile provide authoring and inspection, but no operation to walk a workflow through the running Preview and observe its effects. The completion checks are valuable evidence of structural and export correctness. They are not sufficient evidence that a worker can find the right record, understand the questions, complete the task, and produce the intended data.

Add a bounded way to exercise the actual Preview and inspect what a scenario saves. Use isolated disposable data through the production runtime and persistence boundaries. Avoid writing test scenarios into an existing user's working data, and avoid a second evaluator that could disagree with the real app. Observe form visibility, preloads, calculations, navigation, and created/updated/closed records. For visual quality, include the rendered form and list. This is the feedback an agent needs to improve an app beyond getting a valid document.

Some scenario assertions should be deterministic; semantic and visual judgments can use an independent reviewer and human-calibrated evaluation. The planner should not be the sole judge of whether its own interpretation was right.

**How to establish that the redesign is better.** I would start with a complete vertical prototype using the two referral requests, an event-history workflow, a more complex search/child-record workflow, and an edit to an existing app. Include lookup data, conditions, grouped forms, references, and recovery so the prototype cannot win simply by omitting the expensive features. Preserve the current implementation as the baseline.

Run the same requests against the current interface, the compact native-function interface, and the shared authoring-library interface. Hold the model and effort constant for that comparison, then compare model/effort choices separately. Current production uses Sol at medium effort for design and review and Luna at xhigh for editing and execution. Astra is a useful candidate, not an assumed cure. Repeated runs matter because a single attractive app or fast build is weak evidence.

Judge the completed app: requirements preserved, correct record effects, understandable forms and navigation, useful defaults, edit fidelity, and successful recovery. Have people review app quality without knowing the variant. Measure time and cost per successful task, repair work, rejected operations, and user questions alongside provider-counted context. Existing software tests still protect invariants; they do not replace app-quality evaluations. I found translation evaluations and substantial test infrastructure, but not a comparable app-building quality suite in the inspected material. [Evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

The proposed measurements should count the whole burden. The user gave 5,000 instruction tokens and 20,000 authoring-interface tokens as illustrations of the ambition, not acceptance thresholds. Count imperative guidance embedded in briefs, shared signatures, and required reference material. Keep additional context when it demonstrably improves the app or supports a necessary decision. Separately measure initial loading, the largest newly loaded capability, cumulative loaded definitions, and state/history growth. App-specific facts and source documents need a separate relevance and retrieval policy; their necessary size varies with the task.

There is no hard prompt or tool token ceiling in the delivery plan. The design author's present provider-counted tool contribution is already near 20,000, while the editor and executor require much larger structural changes. Functionality parity and better app outcomes are release conditions. A tiny schema with a poor error model or a hidden manual is not success.

Finally, extend `/agents` from a useful anatomy view into a request-level evidence tool. Capture the exact payload at the provider boundary, version the prompt/schema artifacts, and link each recorded step to its actual versions. Keep local estimates, server counts, and reported usage/cache figures distinct. Show loaded definitions, state additions, and protocol-only exchanges over time. Make it possible to see which information was present when a design decision or repair occurred. Avoid retaining credentials in these artifacts and apply the existing access boundaries to user content.

The recommended next unit of work is the measured authoring-interface prototype in the delivery plan, followed by the compiler and orchestration changes it validates. Rewrite the prompts against that clearer job. Integrate completion verification with the existing Unit F plan and substantial reviewed edits with Unit G; do not create parallel conformance or edit authorities. The intended outcome is an agent that spends its context choosing and checking a useful app, with a compact, well-written interface through which to express those choices.
