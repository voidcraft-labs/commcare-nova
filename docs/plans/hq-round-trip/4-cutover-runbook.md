# HQ round-trip platforms cutover: the operator runbook

The exceptional operator runbook of step 4's direct maintenance cutover (`docs/architecture/contracts.md`, "Direct maintenance cutover"), for the tool `hq-round-trip-platforms.cjs` on its own Job `commcare-nova-hq-round-trip-platforms`. Its design is part 09 of step 4's plan (`docs/plans/hq-round-trip/4-platforms/09-cutover.md`, §13 and §14); what follows is that part's window as commands. The pipeline holds no maintenance posture code, so the posture is these hand-run commands. The cutover reads Nova's database and media bucket and no CommCare HQ state; it decrypts no key and needs no KMS grant.

The scan and the migrate script print one JSON object a line, each with `report: "hq-round-trip-platforms"`, its `mode` and its `section`, each line as soon as it is made: `fleet` first (apps, deleted apps, changed apps, `planDigest`, null in the scan, `fleetSeqDigest`, database size, peak RSS, plan milliseconds, and `ledger`: whether the migration ledger already holds the validation migration, `validatedApplied`, and every `pendingMigrations` name), then `declarations`, `splits`, `clock-keeping-dates`, `session-context`, `schema-drift`, `media` (ready media rows by kind and stored MIME, and `needsBytes`, the rows whose stored bytes the Job must read, by MIME in `needsBytesByMime`; under the dry run and later modes the rows by format and by cause, the asset ids of `missing` and `too-large` rows, the objects and bytes read, and the references removed by cause, carrier and format; `classified: false` in the scan), `deployments`, `holders`, one `blocker` line per code, under `--rehearse` and `--execute` a `writer` line (each numbered fleet step's milliseconds, the database growth and WAL, `migrationsApplied`), and `outcome` last: `ok`, `already-applied`, or `stopped` with any of `blocker`, `holder`, `app-changed`, `media-changed`, `digest`, `ledger`, or `error` with its `errorClass` (`media-read` among them). `--prove-media-read` prints one `media-read` line, `ok`, `no-media` or `failed`. A run that throws still prints its last `outcome` line; its stderr holds this cutover's own message or the error's class alone, never a database error's text. Every line is content-free: app ids, asset ids, deployment ids, migration names, feature ids, formats, codes and counts, never a name, a file name, an expression or a value.

**Two artifacts from two trees.**

- The **maintenance image** is built by hand from the head commit of pull request 14's branch (`<14>`), the one beneath the removal. That commit never reaches `main`, because the merge squashes. The scan, `manage-deployment.py job` and `deploy-cloud-run.py --execute-job` all run from a checkout of that same commit, because the tool, its Job contract, its allowlist arm and the scan exist only there.
- The **migration image** and the **application image** are built by Cloud Build from `main`'s tip after `gh stack merge <top> --squash`, whose tree is pull request 15's (`<15>`).

## Checks

1. **The trees.** `git diff --stat <14>..<15> -- lib app` names only `lib/db/designSessions.ts`, whose one export the removal makes module-private again; otherwise the gate that migrated is not the gate that probes. It runs on a stack rebased on `main`'s current tip.
2. **`main` is frozen** from the image build to the merge. `git ls-remote origin refs/heads/main` prints the same commit at step 1(b) and at step 9. A rebase of the stack after the image is built changes `<14>`, so the image is built again, both Jobs are made again from it, and the dry run is repeated.
3. **No deploy from `main`** between the execute run and the merge: the ledger then names migrations `main` does not hold, and Kysely's `Migrator` refuses a ledger with an executed migration it cannot find. For a retried build, `gcloud builds list --project=commcare-nova --region=us-central1 --filter='create_time>"<execute start, RFC 3339 UTC>"' --format='value(id,substitutions.COMMIT_SHA,status)'` lists no build before the merge commit's.
4. **The advisory dry run is at most three days old** when the window opens (its evidence file name carries its moment). Where the window slips past three days, step 1(c) to (e) are repeated before it opens.

## The window

It runs as long as its steps: about 5 minutes to open, up to 70 to drain, 10 for the restore point, up to 15 for the grant and its check where step 5 makes one, the dry run, the execute run, 10 for step 8, about 20 for the deploy, 10 for the drift writer and its two scans, and 10 to resume. The dry run and the execute run each take about the advisory dry run's duration, so the operator plans 2 hours 30 minutes plus twice that. A stop before the commit (a blocker, a holder, a moved app, media row or digest, a ledger, an error) closes the window with nothing written and no DDL applied: reattach, resume, and revoke any grant step 5 made.

Where the advisory dry run's `fleet` line's plan milliseconds exceed 3,600,000, the window is not opened: the Job contract's `timeout` becomes twice the measured seconds plus 1,800, rounded up to a whole minute, in pull request 13's `config/deployment-jobs.json`; `--wait-seconds` below moves with it (the contract's `timeout` plus 60); the image is built again, and step 1 repeats.

## The commands

Each runs from a checkout of `<14>`, the maintenance image's commit, unless the step names another tree, signed in with `gcloud auth login` and `gcloud auth application-default login` as one account that may administer the project, with `npm ci` run in every checkout used. `<...>` is a value the step before printed or the operator supplies. `$IMAGE` is the maintenance image's digest reference; `$JOB` is `commcare-nova-hq-round-trip-platforms`; `$DRIFT_JOB` is `commcare-nova-case-type-schema-retirement`, whose contract admits `schema-drift.cjs --execute` with an optional `--app <id>`; `$BUCKET` is `gs://nova-multimedia-prod`; `$SA` is `serviceAccount:nova-migrate@commcare-nova.iam.gserviceaccount.com`; `$EVIDENCE` is a local directory whose files go to `gs://commcare-nova-cutover-evidence/hq-round-trip-platforms/` at each step's end; `$MAIN_TREE` is a checkout of `main`'s tip. The load balancer's names are the repo's (`scripts/infra/setup-cloud-armor-lb.sh`): backend service `nova-backend` (global), serverless NEG `nova-neg` (`us-central1`).

Forms every step uses:

- **Run the tool:** `python3 scripts/rollout/deploy-cloud-run.py --execute-job --project=commcare-nova --region=us-central1 --job=$JOB --image="$IMAGE" --wait-seconds=7260`, which is the dry run (the Job's stored arguments); for an override, the same with one `--execution-arg=<word>` per word of an admitted shape, the first being `hq-round-trip-platforms.cjs`: `--prove-media-read`; `--settle-holders`; or `--execute`, `--expect-plan-digest`, `<digest>`. The arm refuses every other shape, `--rehearse` among them, before any request. `--wait-seconds` is the contract's `timeout` plus 60. The command prints `NOVA_JOB_EXECUTION={...}` when the tool exited 0 and fails with "Cloud Run Job execution failed or was cancelled." when it exited 1, which is an ordinary result for a dry run that meets a blocker; either way the report is read as below.
- **The execution and its report:** `gcloud run jobs executions list --job=$JOB --project=commcare-nova --region=us-central1 --sort-by=~metadata.creationTimestamp --limit=1 --format='value(metadata.name)'` names it; `gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="commcare-nova-hq-round-trip-platforms" AND labels."run.googleapis.com/execution_name"="<execution>" AND jsonPayload.report="hq-round-trip-platforms"' --project=commcare-nova --order=asc --limit=1000000 --format=json > $EVIDENCE/<execution>.json` saves its report lines; `jq -r '.[].jsonPayload | select(.section == "fleet") | .planDigest' $EVIDENCE/<execution>.json` prints its digest, and `jq` by `section` reads every other line (`ledger` inside `fleet`, `media`, `schema-drift`, `writer`, `outcome`).
- **The scan:** `npx tsx --conditions=react-server scripts/scan-hq-round-trip-platforms.ts --prod > $EVIDENCE/scan-<moment>.jsonl`, `<moment>` the UTC time as `YYYYMMDDTHHMMZ`. `jq -c 'select(.section == "holders")'`, `jq -c 'select(.section == "blocker")'` and `jq 'select(.section == "media") | .needsBytes'` over that file read its parts. The scan stops on any holder at all, live or not, as the write does.
- **The bucket policy, the grant and the revocation:** the policy read is `gcloud storage buckets get-iam-policy $BUCKET --format=json > $EVIDENCE/bucket-policy-<moment>.json`, over which `jq '[.bindings[]?.members[]? | select(contains("nova-migrate@"))] | length'` prints `0` before a grant and after its revocation; the grant is `gcloud storage buckets add-iam-policy-binding $BUCKET --member=$SA --role=roles/storage.objectViewer --condition='expression=request.time < timestamp("<expiry>"),title=hq-round-trip-platforms-<advisory or window>'`; the revocation is `gcloud storage buckets remove-iam-policy-binding $BUCKET --member=$SA --role=roles/storage.objectViewer --all`, which removes every binding of that role and member whatever its condition.
- **The NEG:** `gcloud compute backend-services remove-backend nova-backend --global --network-endpoint-group=nova-neg --network-endpoint-group-region=us-central1 --project=commcare-nova` and `add-backend` with the same flags, each followed by `gcloud compute backend-services describe nova-backend --global --project=commcare-nova --format='value(backends[].group)'` into `$EVIDENCE/neg-<before or after>.txt`.
- **The Scheduler job:** `gcloud scheduler jobs pause commcare-nova-capture-cleanup --project=commcare-nova --location=us-central1`, and `resume` with the same flags.
- **The evidence:** `gcloud storage cp -r $EVIDENCE/* gs://commcare-nova-cutover-evidence/hq-round-trip-platforms/`. The bucket is private to the project, with no lifecycle rule and nothing deleted from it (`docs/architecture/deployment.md`, "Historical repairs"). `--debug-details` output never goes there.

## Rollback

Before the commit of step 7, nothing needs restoring: the DDL and the backfill roll back with the fleet, and the bucket is only read. The window closes by reattaching and resuming, revoking any grant step 5 made, and `main` may deploy.

After the commit and until the merge, the ledger holds migrations `main` does not have, so any deploy from `main` fails at its migrate Job. A window that closes in that span without merging restores the restore point of step 4 before `main` deploys again:

1. `gcloud sql backups restore <backup id> --restore-instance=nova-cases --project=commcare-nova`, `<backup id>` from step 4, and wait for `gcloud sql operations list --instance=nova-cases --project=commcare-nova --limit=1 --format='value(operationType,status)'` to print `RESTORE_VOLUME	DONE`.
2. The tool's dry run, whose `fleet` line's `ledger.validatedApplied` is `false`.
3. The revocation and the policy read where step 5 made a grant; the Scheduler job resumed (if step 8 has not resumed it); the NEG reattached. The old revision serves again.

What is lost is only what the capture-cleanup worker removed after step 8. Once the merge's deploy has started, the only way is forward: a probe failure at step 9 leaves ingress closed, and the fix ships as a pull request whose deploy passes the probe.

## Local databases

A local database goes through the same script from a checkout of `<14>`, with the local bucket in `NOVA_MEDIA_BUCKET`: `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-platforms.ts --rehearse` (which leaves nothing, the DDL included), then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-platforms.ts --execute --expect-plan-digest <d>` with the `planDigest` a dry run prints, then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-schema-drift.ts --execute` for the drift its `schema-drift` line counted. A database made fresh from the migrations needs nothing. One that still holds unrecorded media after the merge stops at the validation migration with its message, and is made again from the migrations.
