# HQ round-trip case writes cutover: the operator runbook

The exceptional operator runbook of step 5's direct maintenance cutover (`docs/architecture/contracts.md`, "Direct maintenance cutover"), for the tool `hq-round-trip-case-writes.cjs` on its own Job `commcare-nova-hq-round-trip-case-writes`. Its design is part 09 of step 5's plan (`docs/plans/hq-round-trip/5-case-writes-forms-navigation/09-cutover.md`, §6, §10 to §16, §18 and §20, with the review rule of §21.3); what follows is that part's window as commands, in the form step 4's runbook ran in. The pipeline holds no maintenance posture code, so the posture is these hand-run commands. The cutover reads Nova's database alone: no media bucket, no CommCare HQ state, no KMS key, so the window makes no bucket grant and decrypts nothing.

The scan and the migrate script print one JSON object a line, each with `report: "hq-round-trip-case-writes"`, its `mode` and its `section`, each line as soon as it is made: `fleet` first (apps, deleted apps, `planDigest`, null in the scan, `fleetSeqDigest`, the digest of every `[appId, mutation_seq]`, `ledger` with `horizonApplied` and every `pendingMigrations` name, plan milliseconds, peak RSS, database size), then `structure` (per structure step, apps and entities changed), `steps` (per semantic step and change kind, apps and entities), `placements` (published apps, deployments by baseline kind, units held by target and by source, units not held by class, `frozenChecked`, `frozenDisagrees`), `path-moves` (per cause, deployments and forms), `notice` (per reason, entries and apps), `schema` (per planned cause, apps, case types and properties, and the count the drift scan will count), `holders`, `private-work`, one `blocker` line per code (count, app ids, finding codes), under `--rehearse` and `--execute` a `writer` line (each writer step's milliseconds, the WAL and growth, `migrationsApplied`), and `outcome` last: `ok`, `already-applied`, or `stopped` with any of `blocker`, `holder`, `app-changed`, `baseline-changed`, `digest`, `ledger`, `partially-applied`, `lock-timeout`, or `error` with its `errorClass`. A run that throws still prints its `outcome` line; its stderr holds this cutover's own message or the error's class alone, never a database error's text. Every line is content-free: app ids, deployment ids, migration names, step ids, codes and counts, never a name, a label, an expression, a property or a value.

## Definitions

- `<1>` is the head of pull request 1 (`hq-round-trip-case-writes/01-lane-mechanics`), where the pre-step fixtures and the facts `main` derives landed.
- `<15>` is the head of pull request 15 (contracts and public docs), the commit beneath the removal. That commit never reaches `main`, because the merge squashes.
- `<16>` is the head of pull request 16 (the removal), whose tree `main` holds after `gh stack merge <top> --squash`.
- `$IMAGE` is the maintenance image's digest reference, `us-central1-docker.pkg.dev/commcare-nova/cloud-run-source-deploy/commcare-nova/maintenance@<digest>`.
- `$JOB` is `commcare-nova-hq-round-trip-case-writes`.
- `$DRIFT_JOB` is `commcare-nova-case-type-schema-retirement`, whose contract admits `schema-drift.cjs --execute` with an optional `--app <id>`.
- `$EVIDENCE` is a local directory whose files go to `gs://commcare-nova-cutover-evidence/hq-round-trip-case-writes/` at each step's end.
- `$MAIN_TREE` is a checkout of `main`'s tip.

**Two artifacts from two trees.**

- The **maintenance image** is built by hand from `<15>`. The scan, `manage-deployment.py job` and `deploy-cloud-run.py --execute-job` all run from a checkout of that same commit, because the tool, its Job contract, its allowlist arm and the scan exist only there.
- The **migration image** and the **application image** are built by Cloud Build from `main`'s tip after `gh stack merge <top> --squash`, whose tree is `<16>`.

## The operator's environment

As step 4's window ran:

- every `gcloud storage` command runs with `CLOUDSDK_PYTHON=/opt/homebrew/bin/python3.11` (the evidence copies and listings);
- the installed gcloud has no `gcloud builds retry`, so a retry is the REST call `curl --fail --silent --show-error -X POST -H "Authorization: Bearer $(gcloud auth print-access-token)" -H 'content-type: application/json' --data '{"name":"projects/commcare-nova/locations/us-central1/builds/<id>","projectId":"commcare-nova","id":"<id>"}' https://cloudbuild.googleapis.com/v1/projects/commcare-nova/locations/us-central1/builds/<id>:retry`, whose answer names the new build;
- after the NEG is reattached the load balancer answers 200 only after about 2.5 minutes, so each public probe of step 10 retries every 15 seconds for up to 5 minutes before it counts as a failure.

Every command runs signed in with `gcloud auth login` and `gcloud auth application-default login` as one account that may administer the project, with `npm ci` run in every checkout used. `<...>` is a value the step before printed or the operator supplies.

## Checks

1. **The trees.** `git diff --stat <15>..<16> -- lib app ':(exclude,glob)**/__tests__/**'` names only `lib/db/designSessions.ts`, whose two exports the removal makes module-private again; otherwise the gate that migrated is not the gate that probes. Tests are excluded because pull request 16 also edits `lib/db/__tests__/runHolderWriteGuard.test.ts` (its allowlist entry for the cutover's writer), which changes no gate. It runs on a stack rebased on `main`'s current tip.
2. **`main` is frozen** from the image build to the merge: `git ls-remote origin refs/heads/main` prints the same commit at step 1(b) and at step 8. A rebase after the image is built changes `<15>`: the image is built again, both Jobs are made again from it, and the dry run is repeated.
3. **No deploy from `main`** between the execute run and the merge: the ledger then names migrations `main` does not hold, and Kysely's `Migrator` refuses a ledger with an executed migration it cannot find. `gcloud builds list --project=commcare-nova --region=us-central1 --filter='create_time>"<execute start, RFC 3339 UTC>"' --format='value(id,substitutions.COMMIT_SHA,status)'` lists no build before the merge commit's.
4. **The advisory dry run is at most three days old** when the window opens (its evidence file name carries its moment); past three days, step 1(c) to (f) repeat.
5. **Pull request 1 changed no product code of the cutover's**: `git diff --stat 2f985ed6..<1> -- lib app ':(exclude,glob)**/__tests__/**'` names nothing, so the facts `main` derived are `main`'s.

## The commands

Each runs from a checkout of `<15>`, the maintenance image's commit, unless the step names another tree. The load balancer's names are the repo's (`scripts/infra/setup-cloud-armor-lb.sh`): backend service `nova-backend` (global), serverless NEG `nova-neg` (`us-central1`).

Forms every step uses:

- **Run the tool:** `python3 scripts/rollout/deploy-cloud-run.py --execute-job --project=commcare-nova --region=us-central1 --job=$JOB --image="$IMAGE" --wait-seconds=7260`, which is the dry run (the Job's stored arguments); for an override, the same with one `--execution-arg=<word>` per word of an admitted shape, the first being `hq-round-trip-case-writes.cjs`: `--settle-holders`; or `--execute`, `--expect-plan-digest`, `<digest>`. The arm refuses every other shape, `--rehearse`, `--prod`, `--app` and `--debug-details` among them, before any request. `--wait-seconds` is the contract's `timeout` (`7200s`) plus 60 and moves with it. The command prints `NOVA_JOB_EXECUTION={...}` when the tool exited 0 and fails with "Cloud Run Job execution failed or was cancelled." when it exited 1, which is an ordinary result for a dry run that meets a blocker; either way the report is read as below.
- **The execution and its report:** `gcloud run jobs executions list --job=$JOB --project=commcare-nova --region=us-central1 --sort-by=~metadata.creationTimestamp --limit=1 --format='value(metadata.name)'` names it; `gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="commcare-nova-hq-round-trip-case-writes" AND labels."run.googleapis.com/execution_name"="<execution>" AND jsonPayload.report="hq-round-trip-case-writes"' --project=commcare-nova --order=asc --limit=1000000 --format=json > $EVIDENCE/<execution>.json` saves its report lines; `jq -r '.[].jsonPayload | select(.section == "fleet") | .planDigest' $EVIDENCE/<execution>.json` prints its digest, and `jq` by `section` reads every other line (`ledger` inside `fleet`, `placements`, `path-moves`, `schema`, `blocker`, `writer`, `outcome`).
- **The scan:** `npx tsx --conditions=react-server scripts/scan-hq-round-trip-case-writes.ts --prod > $EVIDENCE/scan-<moment>.jsonl`, `<moment>` the UTC time as `YYYYMMDDTHHMMZ`. `jq -c 'select(.section == "holders")'` and `jq -c 'select(.section == "blocker")'` over that file read its parts. The scan stops on any holder at all, live or not, as the write does. Each blocked app's places come from `npx tsx --conditions=react-server scripts/scan-hq-round-trip-case-writes.ts --prod --app <id> --debug-details`, on the operator's terminal only, never into the evidence.
- **The NEG:** `gcloud compute backend-services remove-backend nova-backend --global --network-endpoint-group=nova-neg --network-endpoint-group-region=us-central1 --project=commcare-nova` and `add-backend` with the same flags, each followed by `gcloud compute backend-services describe nova-backend --global --project=commcare-nova --format='value(backends[].group)'` into `$EVIDENCE/neg-<before or after>.txt`.

- **A retried probe:** `ok=0; for attempt in $(seq 1 20); do if <probe>; then ok=1; break; fi; sleep 15; done; test "$ok" = 1`, which tries every 15 seconds for 5 minutes.
- **The evidence:** `CLOUDSDK_PYTHON=/opt/homebrew/bin/python3.11 gcloud storage cp -r $EVIDENCE/* gs://commcare-nova-cutover-evidence/hq-round-trip-case-writes/`. The bucket is private to the project, with no lifecycle rule and nothing deleted from it (`docs/architecture/deployment.md`, "Historical repairs"). `--debug-details` output never goes there.

## The window

It runs as long as its steps: about 5 minutes to open, up to 70 to drain, 10 for the restore point, the dry run, the execute run, 10 for step 7, about 20 for the deploy, 10 to converge, and 15 to resume (the load balancer's 2.5 minutes and the probes' retries inside it). The dry run and the execute run each take about the advisory dry run's duration, so the operator plans 2 hours 30 minutes plus twice that. A stop before the commit (a blocker, a holder, a moved app or baseline, a digest, a ledger, a lock wait, an error) closes the window with nothing written and no DDL applied: reattach and resume.

Where the advisory dry run's `fleet` line's plan milliseconds exceed 3,600,000 (gated run G3's outcome B), the window is not opened: the Job contract's `timeout` becomes twice the measured seconds plus 1,800, rounded up to a whole minute, in pull request 14's `config/deployment-jobs.json`, under the review rule; `--wait-seconds` moves with it (the contract's `timeout` plus 60); the image is built again, and step 1 repeats.

## Rollback

Before step 6's commit, nothing needs restoring: the DDL rolls back with the fleet. The window closes by reattaching and resuming, and `main` may deploy.

After the commit and until the merge, the ledger holds migrations `main` lacks, so any deploy from `main` fails at its migrate Job. A window that closes in that span without merging restores step 4's restore point before `main` deploys again:

1. `gcloud sql backups restore <backup id> --restore-instance=nova-cases --project=commcare-nova`, `<backup id>` from step 4, and wait for `gcloud sql operations list --instance=nova-cases --project=commcare-nova --limit=1 --format='value(operationType,status)'` to print `RESTORE_VOLUME	DONE`.
2. The tool's dry run, whose `fleet` line's `ledger.horizonApplied` is `false`.
3. The Scheduler job resumed (if step 7 has not resumed it); the NEG reattached. The old revision serves again.

What is lost is only what the capture cleanup removed after step 7. Once the merge's deploy has started, the only way is forward: a probe failure at step 8 leaves ingress closed, and the fix ships as a pull request with its own review (part 09 §21.3) whose deploy passes the probe.

## Local databases

A local database goes through the same script from a checkout of `<15>`: `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-case-writes.ts --rehearse` (which leaves nothing, the DDL included), then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-case-writes.ts --execute --expect-plan-digest <d>` with the `planDigest` a dry run prints, then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-schema-drift.ts --execute` for the drift its `schema` line counted. A database made fresh from the migrations needs nothing.
