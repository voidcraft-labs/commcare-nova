What every pull request of the stack does:

- A pull request that changes a stored shape adds its transform step under `scripts/lib/hqRoundTripCutover/steps/`, registers it in `transform.ts`, adds its notice reason and renderer, and adds its expectations over the frozen pre-step fixtures, all in that pull request. At every point of the stack the migrate script is therefore complete for the shape that point reads, which is how "a stored-shape change never merges without its migration" holds inside a stack that merges together.
- `transform.ts` holds the steps in one fixed order, which is not the order of the pull requests: `language-wire-codes`, `media-slots`, `hidden-inert-default`, `search-button-label`, `question-ids`, `case-operation-ids`, `connect-ids`, `entry-point-ids`, `option-values`, `empty-forms`, `root-create-id`, `reserved-search-inputs`, `time-ordering`, `hidden-from-menu`, `post-submit`, `id-mapping-keys`, `date-patterns`, `tile-hidden-calculated-sort`, `sort-property-ownership`, `tile-cells`, `app-settings`. A pull request inserts its step at that position, never at the end. The order is identity additions, then removals, then renames (later steps name questions), then semantic moves, then case lists, then the one step that takes values read from HQ. That order is part 10's (The transform steps, in order), which is the registry; where the two lists ever differ, part 10's holds. `time-ordering` runs before `hidden-from-menu`: the first only replaces comparisons and writes no flag, and the second, the only step that sets the flag, must see every `match-none` the first wrote. The table's last-but-one column gives each step id with the notice reasons it mints in brackets; a "no-write" reason is a line for a change that stores nothing (part 10, Changes that write nothing and still get a line), and each reason's copy is where part 10's reason tables say it is.
- A fix moves its entries to the fixed register and retires its rule (the module, its test, its import and its `RULES` line) in its own pull request.
- A validator narrowing runs the corpus emission first (no Docker), diffs `index.json`'s document ids before and after, and rewrites or removes each document it refuses. ## House rules for the stack

1. One `gh stack` chain, cut from the latest `origin/main` and rebased on it before the first pull request opens.
2. Every pull request is undrafted.
3. `/code-review medium` runs on each pull request and its findings are fixed there. Where the review's agents sit idle for about a minute with no notification, their findings are collected by hand.
4. The stack merges together with `gh stack merge <top> --squash`: one push, one deploy. Never pull request by pull request, and never through the merge API.
5. The cutover runs before the merge. The maintenance image is built by hand (`docker build --target maintenance`) from the head commit of pull request 15, the pull request beneath the removal, and the Job is managed from a checkout of that same commit, because the Job contract and the allowlist arm exist only there. `gh stack merge <top> --squash` is expected to land one commit per pull request, which leaves each script in `main`'s history and none on its tip. This was not executed during planning. If the merge lands one commit for the whole stack, the scripts' audit record is the pull requests themselves, and either way the runbook records pull request 15's head commit hash and the maintenance image's digest before the merge.
6. `main` is frozen from the image build to the merge. A rebase after the image is built changes the tree, so the image is rebuilt and the dry run repeated.
7. A rehearsal applies the stack's migrations for real (`runCaseStoreMigrationsWithReport` commits outside the rehearsal's rollback). After the first rehearsal a fix to any migration in the stack is a new migration file, never an edit.
8. The advisory scan runs within three days of the window and writes nothing. It reads HQ with the same credential order as the execute run, so the members whose keys it uses are the same unless membership or a key changed in between. Only the execute run records each member whose key it used, and those rows are what a member is shown; a member whose key only the advisory run used gets no notice line. The runbook states the three-day bound.
9. The capture-cleanup Scheduler job is resumed after the cutover Job commits and before the merge: `scripts/infra/manage-deployment.py::scheduler_findings` requires it enabled, and the deploy's `prerequisites` step fails otherwise.
10. After the merge the deploy check-run is watched on the merge commit with `gh`: list the commit's check-runs first and build the watch from the app name observed there. Pull request CI being green is not a deploy, and this deploy runs the runtime probe because the stack changes `lib/domain` and the validator.
11. The `../nova-plugin` change is its own pull request in that repo: the `upload_to_hq` skill's prose for confirmations, the version floor, the `hq_changed` stop, the logo step and notices; the `show` and `edit` skills relaying a non-empty `notices`; the sweep of `build`, `edit`, `autobuild` and `agents/nova-architect-autonomous.md` for every claim a step 2 tool change makes false (`compile_app` taking only a server, media slot names, hidden values needing a value, operation id and date pattern rules); and `version` in `../nova-plugin/.claude-plugin/plugin.json` going from `2.1.0` to `2.2.0` (new behavior, nothing removed from the plugin's own commands). It merges only after the Nova deploy is live.

Removing the tooling at the top of the same stack, not in a follow-up pull request, is a stated choice: a later removal would be a second deploy that exists only because of the split. The habit it adjusts (run, confirm, then remove) is kept in substance because the run and its post-migration scan precede the merge.
