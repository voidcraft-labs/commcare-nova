## The order plan: `lib/domain/caseListOrder.ts::caseListOrderPlan`

A new pure module in Nova vocabulary, so `lib/commcare` and Preview both import it. It stores nothing: it is derived from the document on every read.

```ts
export type CaseListSortKey =
	| { kind: "property"; property: string }      // the raw value
	| { kind: "option-label"; property: string }   // a select property's shown label
	| { kind: "mapping-position"; column: Uuid }   // index of the first matching entry as text, "" when none
	| { kind: "interval-text"; column: Uuid }      // the interval column's shown text
	| { kind: "link-text"; column: Uuid }          // the link column's shown markdown
	| { kind: "calculated"; column: Uuid };        // the expression's value

export type CaseListComparator = "text" | "integer" | "decimal";

export type CaseListOrderElement =             // the sort element reader 1 writes for a rule (rule 4)
	| { kind: "property"; property: string }      // a sort row over a property name
	| { kind: "positional"; position: number };   // `_cc_calculated_<position>` of the field the rule is authored on

export interface CaseListOrderRule {
	readonly order: number;                // 1-based
	readonly direction: SortDirection;
	readonly blanks: "first" | "last";     // first when ascending, last when descending
	readonly implicit: boolean;            // the rule of an unsorted list (rule 7)
	readonly written: boolean;             // reader 1 writes it as a sort element
	readonly element: CaseListOrderElement;
}

export interface CaseListShortField {
	readonly column: Column;
	readonly position: number;             // 0-based index in the stored short detail
	readonly hidden: boolean;              // visibleInList === false
	readonly wire: "property" | "expression";
	readonly joinText: string;             // the text HQ joins an order rule by: the column's HQ `field`
	readonly key?: CaseListSortKey;        // the sort key the field keeps; absent = none
	readonly comparator: CaseListComparator;
	readonly rule?: CaseListOrderRule;     // present when the list orders by it
}

export interface CaseListOrderCarrier {   // the hidden sort field HQ appends itself
	readonly property: string;             // its raw value is the carrier's text and its sort key
	readonly comparator: CaseListComparator;
	readonly rule: CaseListOrderRule;
}

export interface CaseListAuthoredRule {   // one authored rule, as the ownership rule and its cutover step read it
	readonly column: Uuid;                 // the column the rule is authored on
	readonly joinText: string;             // the text HQ joins its element by
	readonly ownKey: CaseListSortKey;      // the key that column orders by with the rule on itself
	readonly landsOn?: number | "carrier"; // the field that takes the rule, or a carrier; absent where another rule with that text replaced it
}

export interface CaseListOrderPlan {
	readonly fields: readonly CaseListShortField[];
	readonly carriers: readonly CaseListOrderCarrier[];
	readonly authored: readonly CaseListAuthoredRule[];   // every authored rule that has an element, in rule order
}

export function caseListOrderPlan(
	config: CaseListConfig,
	caseProperties: readonly CaseProperty[],
	options: {
		readonly mediaOn: boolean;
		readonly calculatedType: (column: Column) => ResolvedType | undefined;
		readonly expressionText: (column: Column) => string;
	},
): CaseListOrderPlan;

export function comparatorForDataType(
	dataType: CasePropertyDataType | undefined,
): CaseListComparator;                    // int: integer, decimal: decimal, otherwise text

export function casePropertyShowsOptionLabels(
	property: CaseProperty | undefined,
): boolean;                               // a select with options (rules 2 and 3)

export function caseListSortKeysMatch(    // "the same key", as CASE_LIST_SORT_PROPERTY_AMBIGUOUS defines it
	plan: CaseListOrderPlan,
	columns: readonly Column[],
	a: CaseListSortKey,
	b: CaseListSortKey,
	expressionText: (column: Column) => string,
): boolean;
```

Three members of this interface were added from planning's own emitter (the emitter run, below), because the readers could not be written without them. `CaseListOrderRule.element` is what reader 1 writes: a rule that joins another field than the one it is authored on (rule 5) still names the authored field's position, and nothing else in the plan holds it. `CaseListOrderPlan.authored` is what `CASE_LIST_SORT_PROPERTY_AMBIGUOUS` and its cutover step read: each authored rule's own column, join text and key, and where it lands, which rule 4's exceptions decide and no reader should derive a second time. `casePropertyShowsOptionLabels` is the one test of "a select with options" that rule 2, rule 3 and both readers share.

**Inputs.** The list's configuration (columns, `listColumnOrder`, each column's `sort`, `visibleInList`, the tile layout), the case type's property catalog (data types and select options), and three options a domain module cannot compute, because `lib/domain` imports nothing from `lib/commcare`:

- `mediaOn`: whether the export carries a media manifest. The plan reads it through one predicate, `lib/domain/modules.ts::imageMapShowsImages(column, mediaOn)`: an image map is its image column with a manifest, and with none where it has no entries; a map with entries and no manifest is a plain column on both paths, as today (An image map with no entries, below).
- `calculatedType(column)`: the resolved type of a calculated column's expression, `undefined` when it does not resolve. `int` maps to the integer comparator, `decimal` to decimal, everything else and `undefined` to text.
- `expressionText(column)`: the text reader 1 writes as an expression column's HQ `field`. The plan compares these texts for equality and reads nothing else from them.

One helper builds the options for every reader, so no reader can pass different ones: new `lib/commcare/suite/case-list/orderPlanOptions.ts::caseListOrderOptions(mod, doc, mediaOn, lookupNaming?)`. Its `calculatedType` is `lib/domain/predicate/typeChecker.ts::checkExpression` over `lib/commcare/validator/rules/case-list/shared.ts::moduleTypeContext(mod, doc)` (the body of today's unexported `sortKeys.ts::resolveCalculatedSortType`, with `ANY_TYPE` returned as `undefined`). Its `expressionText` is new `orderPlanOptions.ts::hqExpressionFieldText(column, mod, doc, screen, lookupNaming?)` with `screen: "results"`, the function `caseList.ts::projectColumnToDetail` calls for every expression arm. Readers 1 and 2, the validator rules below and the cutover steps call the helper directly; Preview calls it from `lib/preview/engine`, which may import `lib/commcare`.

- **`screen`** is the detail the column is written into. On Results a hidden column that is not calculated prints its raw wire path. On Details a column prints as its kind shows it, whatever Results does with it: a label, interval or link column hidden from Results and shown on Details keeps its expression in the long detail. The plan always passes `results`.
- **`lookupNaming`.** Readers 1 and 2 pass their run's lookup naming, so every stored short column's `field` is the plan's join text itself, and `caseList.ts::projectColumnForShortDetail` throws where the two differ. A caller with no catalog (the validator rules, the cutover steps, Preview) passes none, and the function prints through new `lib/commcare/lookup/naming.ts::identityLookupWireNaming()`, which names every table and column by its own id: two expressions print alike under it exactly when they print alike under any real naming, and the plan compares these texts and reads nothing else from them. Executed during planning (the emitter run): `lib/commcare/expression/onDeviceEmitter.ts::emitOnDeviceExpression` throws on a lookup expression with no naming, and `naming.ts::inertLookupWireNaming` gives every table one name, under which two different lookup columns would join as one, so neither serves.
- **`mediaOn`.** Readers 1 and 2 pass whether their export carries a media manifest. The validator rules and the cutover steps pass `true`: whether a document is admitted cannot depend on an export option. Preview passes `true` (Reader 3). The `true` plan is every production export's plan. An export carries no manifest only for an app that holds no media, which is the manual HQ JSON of such an app (`app/api/compile/json/route.ts`, `lib/mcp/tools/compileApp.ts`); every image map of that app has no entries, and `imageMapShowsImages` gives a map with no entries the same column with a manifest and without one. Only two of the proof's producers, which export a document that holds media with no manifest, reach the other plan.

The catalog is `lib/domain/effectiveCaseTypes.ts::effectiveCaseTypes(doc)`'s properties for the module's case type, the one both today's label projection and today's comparator read (`lib/commcare/validator/rules/case-list/shared.ts::validationContextFor` names the same array `augmentedCaseTypes`), so a standard property carries its type and a writer-derived one its writers'.

The property comparator table moves into the domain: `caseListOrder.ts::comparatorForDataType` replaces `sortKeys.ts::applicableSortTypes` and `APPLICABLE_SORT_TYPES`, which go with `sortKeys.ts::resolveColumnSortType`, `resolveCalculatedSortType` and `mapResolvedTypeToSortType`. The comment in `lib/domain/casePropertyTypes.ts` that names `applicableSortTypes` is updated to the new name.

**Outputs.** `fields`: the short detail's fields in stored order, each with its wire class, its join text, the sort key it keeps, and its rule if the list orders by it. `carriers`: the hidden sort fields HQ appends for rules that join no field, in rule order.

### The rules it encodes

Each rule is a statement of what HQ's build writes for the app Nova sends, and each was executed in the order run. The citation is the comment the rule carries in the module.

| # | Rule | What HQ does (executed), and where |
|---|---|---|
| 1 | **Fields.** Every column of `orderedColumns(config, "list")`, hidden ones included. In a list with a tile layout, a column hidden from Results is not a field (the tile clause below). | The short detail's stored columns are the fields; an `invisible` column is a field at width 0 (`detail_screen.py::Invisible`, `HideShortColumn`). |
| 2 | **Wire class and join text.** `property`: `plain` over a property that is not a select with options, `date`, `phone`, `id-mapping`, `image-map` (where `imageMapShowsImages` does not hold it is a plain column over the raw value, as today), and every hidden column that is not calculated. Its join text is `options.expressionText(column)`, which is `@<name>` for an attribute-backed column that is not a shown link. | A property column's `field` is a property name that `detail_screen.py::PropertyXpathGenerator.xpath` turns into a path; an expression column's `field` is used verbatim (`detail_screen.py::FormattedDetailColumn.xpath`). HQ joins a sort element to a column by that `field` text and nothing else (rule 5). |
| 3 | **The key a field keeps with no rule.** `date`: `property`, text. `id-mapping`, and `image-map` where `imageMapShowsImages` holds: `mapping-position`, text. Shown `plain` over a select with options: `option-label`, text. `interval`: `interval-text`, text. | 4 | **Authored rules become elements**, in `priority` order, ties by Results position (today's order in `buildSortDirectives`). A rule on a property field is a property element, the property name. A rule on an expression field is a positional element, `_cc_calculated_<position>`. Three exceptions. (i) A rule on a SHOWN `link` column over any property but `case_id` is a property element over that property, so a link orders by its raw value under the property's comparator.
