# HQ round-trip emission cutover: the operator runbook

The exceptional operator runbook of step 2's direct maintenance cutover (`docs/architecture/contracts.md`, "Direct maintenance cutover"), for the Job `commcare-nova-hq-round-trip-cutover`. Its design is part 10 of step 2's plan (`docs/plans/hq-round-trip/2-emission-and-publish/10-cutover-notice.md`); what follows is that part's "Deploy order and the operator runbook": the checks, the order, the window and the commands. Each pull request of the stack that adds a step or a blocker adds here only the report rows the operator reads for it. The pipeline holds no maintenance posture code, so the posture is these hand-run commands.

The scan and the migrate script print one JSON object a line, each with `report: "hq-round-trip-emission"`, its `mode` and its `section`: `fleet` first (with `planDigest` in the migrate script), then `steps`, `language-wire-codes` (the apps with a stored localization root, and each language whose stored code is a suffixed one), `behavior`, `holders`, `private-work`, `deployments`, one `space` line per project space, one `blocker` line per code, one `deployment` and `key-use` line per deployment where the run read HQ, and `outcome` last (`ok`, `already-applied`, `no-key`, `failed`, or `stopped` with what stopped it).

**Three artifacts from two trees.**

- The **maintenance image** is built by hand (`docker build --target maintenance`) from the head commit of pull request 15's branch, the one beneath the removal. That commit never reaches `main`, because the merge squashes. The operator runs `manage-deployment.py job --image <digest>` and `deploy-cloud-run.py --execute-job` from a checkout of that same commit, because the Job contract and the allowlist arm exist only there.
- The **migration image** and the **application image** are built by Cloud Build from `main`'s tip after `gh stack merge <top> --squash`, whose tree is pull request 16's.

What has to hold, each a runbook check:

1. Pull request 16 differs from 15 only in tooling paths. `git diff --stat <15>..<16> -- lib app` shows nothing. Otherwise the gate that migrated is not the gate that probes.
2. `main` is frozen from the image build to the merge. A rebase of the stack after the image is built changes the tree, so the image is rebuilt and the advisory run repeated.
3. After the first `--rehearse`, every migration file of the stack "has run anywhere" and is immutable (`contracts.md`, "Instant migration"): its ledger rows commit outside the sentinel rollback. A fix to a stack migration after that point is a new migration file. Nothing is immutable earlier: the advisory run applies no DDL.
4. No deploy from `main` runs between the first `--rehearse` and the merge: the ledger then names migration files `main` does not hold, and Kysely's `Migrator` refuses a ledger with an executed migration it cannot find. The advisory run applies no ledgered migration and writes nothing, so a deploy between it and the window is safe.
5. The advisory run is between 30 hours and three days before the window opens. When the window slips past three days, step 1(c) is repeated before it opens. Reason for three days: the advisory run records no key use, and the short interval is what keeps the members whose keys it sent the same as the members the execute run records ("The key-readers record"). Reason for 30 hours: HQ's day counter forgets the advisory run's limited reads only then, and the window's two runs need the day's whole allowance at the floor ("Pacing").
6. The counts of `unreadable` and `transient` deployments are reviewed before `--execute`. The operator reads them in the advisory run's report (step 1(c)) and again in the rehearsal's (step 5), with each deployment's id and the read outcome that classed it. For an `unreadable` one the only remedy is before the window: a current member of the app's Project saving a key that reads that project space, after which step 1(c) is repeated. Where the Project has one member the remedy is that one person's, and the scan's `no-credential` list names such a deployment before any key is sent, so the request to them goes out first; the operator records, per deployment, that this was done or that the one-time id change is accepted. A `transient` one, a transient table or place read included, stops the first window whatever the operator decides. `--transient-as-unreadable` is passed only in a second window, with the lists of deployments it will class `unreadable` or `no-form-ids` and of tables and places it will give an `unread` baseline read and accepted first. Reason: an unreadable deployment's ids change once at its next publish and no later publish restores them ("Reading HQ"), so the class is a cost fixed at the moment of the cutover, and the digest does not judge it: a plan with forty unreadable deployments is as well formed as one with none.
7. The deployments paired by evidence are read before `--execute`. The scan names, before any key is sent, every deployment that has no published document, with its reason; the advisory run's report and the rehearsal's add those whose HQ copy differs from it, and for each the pairs per stage, the ties, the contested pairs and what stays unpaired. No remedy exists for either kind: a history before a horizon cannot be replayed, and what was changed in CommCare HQ is there. The operator records the list. Reason: a pair made by evidence is an inference ("The matching algorithm", What an evidence pair is), every other pair is exact, and the report is where the difference is written down.

**The window.** It is announced as four hours from the start of step 2: up to 15 minutes to open (the decrypt check waits up to ten), up to 70 to drain (the hour a run in flight may take, then the settle and a scan), 10 for the restore point, up to 51 for each of the rehearsal and the execute run (the Job's 3,000 seconds and its start), 10 for step 7, and about 30 for the deploy, the reattach and the probes. Where the scan names a space whose `2L` exceeds 30, it is announced as five and a half hours, for step 6's 80-minute wait. The clone rehearsal (step 1(e)) must finish inside the Job's 3,000 seconds with the advisory run's read duration added, or the Job would time out in the window; where it does not, the cutover waits for that to be solved before any window is announced. A digest refusal adds one rehearsal; a stop (a transient read, a blocker, a live holder) closes the window with nothing written. Where the window would run past its announced end, the operator closes it as step 6's reason says (reattach, resume, revoke) and announces another the same way.

The announcement (step 1(f)), with `<day>`, `<start>` and `<end>` in UTC and `<hours>` four or five and a half:

> Subject: Nova will be unavailable on <day> from <start> to <end> UTC
>
> Nova will be unavailable on <day> from <start> to <end> UTC, up to <hours> hours, while we update how it writes apps for CommCare HQ. During that time the builder, the assistant and Nova's MCP connection won't respond.
>
> A few things won't carry over the update, so it's worth wrapping them up before then:
>
> - Changes the assistant is still working on and hasn't saved. Your saved apps stay exactly as they are, and you can ask again afterwards.
> - Edits in an open builder tab that haven't saved yet.
> - A build that hasn't saved its first app yet.
> - A question the assistant asked you and is still waiting on. Ask it again afterwards and it picks up from there.
>
> When you next open an app, Nova shows what changed in it. Where an app is published to CommCare HQ, Nova reads it there during the update with a saved key of a member of its Project, to keep its IDs steady, and shows each person whose key it used which project spaces it read.

**The commands.** Each runs from a checkout of pull request 15's head, the maintenance image's commit ("Three artifacts from two trees"), signed in with `gcloud auth login` and `gcloud auth application-default login` as one account that may administer the project. `<...>` is a value the step before printed or the operator supplies; `$IMAGE` is the maintenance image's digest reference, `$JOB` is `commcare-nova-hq-round-trip-cutover`, `$KEY` is `commcare-api-keys --keyring=nova --location=us-central1 --project=commcare-nova`, `$SA` is `serviceAccount:nova-migrate@commcare-nova.iam.gserviceaccount.com`, and `$EVIDENCE` is a local directory whose files go to the evidence bucket at each step's end. The load balancer's names are the repo's (`scripts/infra/setup-cloud-armor-lb.sh`): backend service `nova-backend` (global), serverless NEG `nova-neg` (`us-central1`).

Forms every step uses:

- **Run the Job:** `python3 scripts/rollout/deploy-cloud-run.py --execute-job --project=commcare-nova --region=us-central1 --job=$JOB --image="$IMAGE" --wait-seconds=3060`, for the dry run; for an override, the same with `--execution-arg=hq-round-trip-cutover.cjs` and one `--execution-arg=<word>` per word of the allowlisted shape (`--prove-decrypt`; `--settle-holders`; `--rehearse`; `--execute`, `--expect-plan-digest`, `<digest>`; each with `--transient-as-unreadable` last in a second window). It prints `NOVA_JOB_EXECUTION={...}` when the tool exited 0, and fails with "Cloud Run Job execution failed or was cancelled." when it exited 1, which is an ordinary result for a dry run that meets a blocker; either way the report is read as below.
- **The execution and its report:** `gcloud run jobs executions list --job=$JOB --project=commcare-nova --region=us-central1 --sort-by=~metadata.creationTimestamp --limit=1 --format='value(metadata.name)'` names it; `gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="commcare-nova-hq-round-trip-cutover" AND labels."run.googleapis.com/execution_name"="<execution>" AND jsonPayload.report="hq-round-trip-emission"' --project=commcare-nova --order=asc --limit=1000000 --format=json > $EVIDENCE/<execution>.json` saves its report lines; `jq -r '.[].jsonPayload | select(.section == "fleet") | .planDigest' $EVIDENCE/<execution>.json` prints its digest and `jq '.[].jsonPayload | select(.section == "outcome")'` its outcome.
- **The key's policy:** `gcloud kms keys get-iam-policy $KEY --format=json > $EVIDENCE/key-policy-<moment>.json`; it names `nova-migrate@` nowhere when `jq '[.bindings[]?.members[]? | select(contains("nova-migrate@"))] | length'` over it prints `0`.
- **A grant:** `gcloud kms keys add-iam-policy-binding $KEY --member=$SA --role=roles/cloudkms.cryptoKeyDecrypter --condition='expression=request.time < timestamp("<expiry>"),title=hq-round-trip-cutover-<advisory or window>'`, `<expiry>` two hours after the command for the advisory grant and six for the window's, in RFC 3339 UTC. **Its revocation:** `gcloud kms keys remove-iam-policy-binding $KEY --member=$SA --role=roles/cloudkms.cryptoKeyDecrypter --all`, then the policy read.
- **The scan:** `npx tsx --conditions=react-server scripts/scan-hq-round-trip-cutover.ts --prod > $EVIDENCE/scan-<moment>.jsonl`.
- **The evidence:** `gcloud storage cp -r $EVIDENCE/* gs://commcare-nova-cutover-evidence/hq-round-trip-emission/`. The bucket is private to the project, made once in step 1 (below), and kept for good, with no lifecycle rule: it holds the content-free reports, the key uses and the policy reads, which the window's record needs after the Job and its logs are gone, and its key uses are the one record of a run that writes no row (the advisory run, a rehearsal, a refused run). Its name and its retention are recorded where they outlive this plan and the runbook, in `docs/architecture/deployment.md`, "Historical repairs" ("Block: the cutover", Files, Docs, gives the sentence). `--debug-details` and `--recipients` output never goes there.
