# HQ round-trip expressions cutover: the operator runbook

The exceptional operator runbook of step 3's direct maintenance cutover (`docs/architecture/contracts.md`, "Direct maintenance cutover"), for the tool `hq-round-trip-expressions.cjs` on the Job `commcare-nova-historical-repair`. Its design is part 09 of step 3's plan (`docs/plans/hq-round-trip/3-expressions/09-cutover.md`, §13 and §14); what follows is that part's window as commands. The pipeline holds no maintenance posture code, so the posture is these hand-run commands. The cutover reads no CommCare HQ state, decrypts no key and needs no KMS grant.

The scan and the migrate script print one JSON object a line, each with `report: "hq-round-trip-expressions"`, its `mode` and its `section`, each line as soon as it is made: `fleet` first (apps, deleted apps, `planDigest`, `fleetSeqDigest`, database size, peak RSS, plan milliseconds, and `ledger`: whether the migration ledger already holds the fold-horizon migration, `foldHorizonApplied`, and every `pendingMigrations` name), then `steps`, `behavior`, `schema`, `holders`, `private-work`, one `blocker` line per code, `census` (the scan with `--base-digests` only), under `--rehearse` and `--execute` a `writer` line (each numbered fleet step's milliseconds, the database size and WAL growth, `migrationsApplied`), and `outcome` last: `ok`, `already-applied`, or `stopped` with any of `blocker`, `holder`, `digest`, `unexplained`, `census-incomplete`, `census-stale`, or `error` with its `errorClass`. A run that throws still prints that last `outcome` line, `stopped` by `error`; its stderr holds this cutover's own message or the error's class alone, never a database error's text. Every line is content-free: app ids, deployment ids, migration names, codes and counts, never a name, an expression or a value.

**Three artifacts from three trees.**

- The **base emitter** runs from a checkout of pull request 2's head (`<2>`), whose `lib` and `app` are production's (check 1), so it emits with production's emitter.
- The **maintenance image** is built by hand from the head commit of pull request 14's branch (`<14>`), the one beneath the removal. That commit never reaches `main`, because the merge squashes. The scan, `manage-deployment.py job` and `deploy-cloud-run.py --execute-job` all run from a checkout of that same commit, because the tool, its allowlist arm and the scan exist only there.
- The **migration image** and the **application image** are built by Cloud Build from `main`'s tip after `gh stack merge <top> --squash`, whose tree is pull request 15's (`<15>`).

## Checks

1. **The trees.** `git diff --stat <14>..<15> -- lib app` names only `lib/db/designSessions.ts`, whose two exports the removal makes module-private again; otherwise the gate that migrated is not the gate that probes. `git diff --stat main..<2> -- lib app ':(exclude,glob)**/__tests__/**'` prints nothing (pull request 1 adds one test table under `lib`, which the pathspec excludes); otherwise the base half of the census does not emit with production's emitter. Both run on a stack rebased on `main`'s current tip.
2. **`main` is frozen** from the image build to the merge. `git ls-remote origin refs/heads/main` prints the same commit at step 1(d) and at step 9. A rebase of the stack after the image is built changes `<14>`, so the image is built again, both Jobs are made again from it, and step 1(b) is repeated.
3. **No deploy from `main`** between the execute run and the merge: the ledger then names a migration `main` does not hold, and Kysely's `Migrator` refuses a ledger with an executed migration it cannot find. Check 2 holds this for merges; for a retried build, `gcloud builds list --project=commcare-nova --region=us-central1 --filter='create_time>"<execute start, RFC 3339 UTC>"' --format='value(id,substitutions.COMMIT_SHA,status)'` lists no build before the merge commit's.
4. **The advisory scan is at most three days old** when the window opens (step 1(b)'s file name carries its moment). Its `fleetSeqDigest` is compared with the window's at step 5. Where the window slips past three days, step 1(b) and (c) are repeated before it opens.

## The window

It is announced as two and a half hours from the start of step 2: 5 minutes to open, up to 70 to drain, 10 for the restore point, up to 15 for the census when it reruns, about 10 for the dry run and the execute run, 5 for step 8, about 20 for the deploy and its retry, 10 for the drift writer and its scan, and 5 for the probes. A stop before the execute run commits (a blocker, a holder, a digest refusal, a census stop, an error) closes the window with nothing written and no DDL applied, so `main` may deploy again. Past the announced end, the operator closes it the same way and announces another.

The announcement (step 1(e)), with `<day>`, `<start>` and `<end>` in UTC:

> Subject: Nova will be unavailable on <day> from <start> to <end> UTC
>
> Nova will be unavailable on <day> from <start> to <end> UTC, up to two and a half hours, while we update how it stores and checks expressions. During that time the builder, the assistant and Nova's MCP connection won't respond.
>
> A few things won't carry over the update, so it's worth wrapping them up before then:
>
> - Changes the assistant is still working on and hasn't saved. Your saved apps stay exactly as they are, and you can ask again afterwards.
> - Edits in an open builder tab that haven't saved yet.
> - A build that hasn't saved its first app yet.
> - A question the assistant asked you and is still waiting on. You can ask it again afterwards, and it picks up from there.
>
> When you next open an app, Nova shows what changed in it.

## The commands

Each runs from a checkout of `<14>`, the maintenance image's commit, unless the step names another tree, signed in with `gcloud auth login` and `gcloud auth application-default login` as one account that may administer the project, with `npm ci` run in every checkout used. `<...>` is a value the step before printed or the operator supplies. `$IMAGE` is the maintenance image's digest reference; `$JOB` is `commcare-nova-historical-repair`; `$DRIFT_JOB` is `commcare-nova-case-type-schema-retirement`; `$EVIDENCE` is a local directory whose files go to the evidence prefix at each step's end; `$PR2_TREE` and `$MAIN_TREE` are checkouts of `<2>` and of `main`'s tip. The load balancer's names are the repo's (`scripts/infra/setup-cloud-armor-lb.sh`): backend service `nova-backend` (global), serverless NEG `nova-neg` (`us-central1`).

Forms every step uses:

- **Run the tool:** `python3 scripts/rollout/deploy-cloud-run.py --execute-job --project=commcare-nova --region=us-central1 --job=$JOB --image="$IMAGE" --wait-seconds=3060 --execution-arg=hq-round-trip-expressions.cjs`, which is the dry run; for an override, the same with one more `--execution-arg=<word>` per word of the admitted shape: `--settle-holders`; or `--execute`, `--expect-plan-digest`, `<digest>`. Never run `$JOB` without `--execution-arg=hq-round-trip-expressions.cjs`: with no override the Job runs its stored arguments, the language repair's dry run. The arm refuses every other shape, `--rehearse` among them, before any request. The command prints `NOVA_JOB_EXECUTION={...}` when the tool exited 0 and fails with "Cloud Run Job execution failed or was cancelled." when it exited 1, which is an ordinary result for a dry run that meets a blocker; either way the report is read as below.
- **The execution and its report:** `gcloud run jobs executions list --job=$JOB --project=commcare-nova --region=us-central1 --sort-by=~metadata.creationTimestamp --limit=1 --format='value(metadata.name)'` names it; `gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="commcare-nova-historical-repair" AND labels."run.googleapis.com/execution_name"="<execution>" AND jsonPayload.report="hq-round-trip-expressions"' --project=commcare-nova --order=asc --limit=1000000 --format=json > $EVIDENCE/<execution>.json` saves its report lines; `jq -r '.[].jsonPayload | select(.section == "fleet") | .planDigest' $EVIDENCE/<execution>.json` prints its digest, `jq '.[].jsonPayload | select(.section == "fleet") | .ledger' $EVIDENCE/<execution>.json` the ledger's state before the run, `jq '.[].jsonPayload | select(.section == "writer")' $EVIDENCE/<execution>.json` the writer's timings, and `jq '.[].jsonPayload | select(.section == "outcome")' $EVIDENCE/<execution>.json` its outcome.
- **The scan:** `npx tsx --conditions=react-server scripts/scan-hq-round-trip-expressions.ts --prod > $EVIDENCE/scan-<moment>.jsonl`, `<moment>` the UTC time as `YYYYMMDDTHHMMZ`. `jq -c 'select(.section == "holders")'`, `jq -c 'select(.section == "blocker")'`, `jq -c 'select(.section == "census")'`, `jq -c 'select(.section == "fleet") | .ledger'` and `jq -r 'select(.section == "fleet") | .fleetSeqDigest'` over that file read its parts. The scan stops on any holder at all, live or not, as the write does.
- **The evidence:** `gcloud storage cp -r $EVIDENCE/* gs://commcare-nova-cutover-evidence/hq-round-trip-expressions/`. The bucket exists from step 2's cutover, private to the project, with no lifecycle rule and nothing deleted from it (`docs/architecture/deployment.md`, "Historical repairs"); `gcloud storage buckets describe gs://commcare-nova-cutover-evidence --format='value(lifecycle_config)'` prints nothing. `--debug-details` and `--recipients` output never goes there.

## Rollback

Before the commit of step 7, nothing needs restoring: the execute run applies the ledgered DDL inside its fleet transaction, after every check that can stop, so any stop or failure rolled the DDL back with the fleet. The window closes by reattaching and resuming, and `main` may deploy.

After the commit and until the merge, the ledger holds a migration `main` does not have, so any deploy from `main` fails at its migrate Job (Kysely's `Migrator` refuses a ledger naming a migration it cannot find). A window that closes in that span without merging restores the restore point of step 4 before `main` deploys again, or keeps `main` frozen until the stack merges:

1. `gcloud sql backups restore <backup id> --restore-instance=nova-cases --project=commcare-nova`, `<backup id>` from step 4, and wait for `gcloud sql operations list --instance=nova-cases --project=commcare-nova --limit=1 --format='value(operationType,status)'` to print `RESTORE_VOLUME	DONE`.
2. The tool's dry run (the Job, as in step 6); its `fleet` line's `ledger.foldHorizonApplied` is `false` and its outcome is not `already-applied`, which proves the ledger and the fleet are `main`'s again.
3. `gcloud scheduler jobs resume commcare-nova-capture-cleanup --project=commcare-nova --location=us-central1` (if step 8 has not resumed it) and the NEG's reattach as in step 11; the old revision serves again.

What is lost is only what the capture-cleanup worker removed after step 8, which is expired staged captures. After the new revision serves, the only way is forward.

## Local databases

A local database goes through the same script from a checkout of `<14>`, with the condition every script that reaches `server-only` needs: `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-expressions.ts --rehearse` (which leaves nothing, the DDL included), then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-hq-round-trip-expressions.ts --execute --expect-plan-digest <d>` with the `planDigest` the rehearsal printed (a dry run, the script with no flag, prints the same one over an unchanged database), then `NOVA_DB_WORKLOAD=migration npx tsx --conditions=react-server scripts/migrate-schema-drift.ts --execute`. A database created fresh from the migrations needs nothing. The script exists only up to `<14>`, so one still holding pre-step data after the merge is made again from the migrations (an empty database that `npm run db:migrate` fills).
